\section{VM specification}\label{sec:vm}

Define the following two finite fields:
\[
  \K=\F_{2^{64}}=\F_2[x]/(x^{64}+x^4+x^3+x+1),
  \qquad
  \E=\K[y]/(y^3+y+1),
  \qquad |\E|=2^{192}.
\]

And fix a generator $\gen$ of the multiplicative group $\K^{\times}$, of order $2^{64}-1$.

An element of $\K$ is a polynomial in $x$ of degree below $64$, written in hex with the coefficient of $x^{i}$ in bit $i$, so $\mathtt{2}$ is $x$ and $\mathtt{3}$ is $x+1$. An element of $\E$ is three of those, its coefficients on $1,y,y^{2}$.

An integer $i<2^{64}$ names the element $\intk{i}\in\K$ with that hex writing, the coefficient of $x^{k}$ being bit $k$ of $i$. This is how a register or a memory word holds an integer. It is a bijection and nothing more: $\intk{i+j}$ is not $\intk{i}+\intk{j}$ in general, the field sum being the XOR of the integers.

\vspace{5mm}

The machine is RISC-V: the RV64I base integer instruction set with the M extension~\cite{riscv}, plus custom instructions for the BLAKE2s compression and for the multiplication in the extension field $\E$ (below). We do not restate the instruction semantics, which are the specification's; this section fixes what the specification leaves to the execution environment, and nothing else. A program is a text of $32$-bit instruction words and an entry point, compiled by an ordinary RISC-V toolchain (the repository's guests are Rust, built for \texttt{riscv64im-unknown-none-elf}).

\paragraph{Memory map.} Memory holds $64$-bit words, word $z$ of a region being the bytes $8z,\dots,8z+7$ past its base, little-endian. Three regions exist, each at a base that is a multiple of the region's largest size, so that word $z$ sits at the byte address $\mathrm{base}\oplus 8z$ as well as $\mathrm{base}+8z$:
\begin{center}
\begin{tabularx}{\textwidth}{@{}lllX@{}}
\hline
Region & Base & Size & Holds\\
\hline
text   & $\tbase=\mathtt{0x1000\_0000}$ & $\nprog=2^{\kbc}\le2^{26}$ instructions & the program, readable by fetches only\\
advice & $\abase=\mathtt{0x2000\_0000}$ & $2^{\kadv}\le2^{26}$ words & what the prover supplies (below)\\
RAM    & $\rbase=\mathtt{0x4000\_0000}$ & $2^{\kmem}\le2^{27}$ words & the image, data and the stack\\
\hline
\end{tabularx}
\end{center}
The three sizes are constants of the program. The whole map lies in one $2$\,GiB window, which is what the \texttt{medany} code model reaches from any $\pc$, and all of it but the last $2$\,KiB of a maximal RAM lies below $\mathtt{0x7FFF\_F800}$, the most \texttt{lui} can form, since \texttt{lui} sign-extends bit $31$ on RV64: \texttt{medlow} code and \texttt{li} address that part. Loads and stores must be naturally aligned, each touching one word; the address of a load or a store is computed modulo $2^{64}$ as the specification says, and it is that address that has to fall in RAM or the advice. The text is not data: a load from it is an access outside memory.

\paragraph{State.} The $32$ integer registers $\regs[0],\dots,\regs[31]$, each one word, and the program counter $\pc$, a byte address. Both parties know the initial state: every register is zero and $\pc$ is the program's entry point. A program sets its own stack pointer.

\paragraph{Image and output.} RAM's first words hold the program's \emph{image}, its initialized data, and the rest of RAM is zero. The run ends when it executes \texttt{ecall} with $\regs[17]=93$ (\texttt{a7} holding the number of the \texttt{exit} system call): its public output is then $\regs[10],\dots,\regs[13]$ (\texttt{a0} to \texttt{a3}), four words. An \texttt{ecall} with another number is a trap. A run has no public input: what a program needs beyond its image it reads from the advice, and a statement about more than four words makes them public through the output, as their digest.

\paragraph{Advice.} The advice region holds what the prover chooses, $2^{\kadv}$ words read and written like RAM, and the statement says nothing about them: for one program there is a valid execution per advice. A program therefore has to check whatever it reads there, and this is the one channel through which a witness reaches it.

\paragraph{Traps.} An execution that traps is no execution at all, and has no proof: the prover is refused, not the verifier. The traps are an instruction the machine does not define (a reserved encoding, \texttt{ebreak}, the CSR and \texttt{fence.i} instructions, an unaligned or out-of-text $\pc$, or any $\pc$ in a slot the program left empty), a misaligned load or store, an access outside memory, and an \texttt{ecall} that is not \texttt{exit}. \texttt{fence} is a no-op.

\paragraph{The execution loop.} Fetch the instruction at $\pc$; read its source registers; make its memory access if it has one; write its destination register and the next $\pc$; stop if the instruction was \texttt{exit}. Every instruction reads two registers and writes one, an instruction with fewer reading $\regs[0]$, and one with no destination or with $\regs[0]$ as its destination writing a $33$rd cell, the $\sink$, which nothing reads: this is how $\regs[0]$ is hardwired to zero (\S\ref{sec:e2e-bc}). Reads come before the write, so \texttt{jalr ra, ra} returns to the address it linked from.

\paragraph{The BLAKE2s compression.} The custom instruction \texttt{blake2s rd, rs1, rs2, rs3} (opcode \texttt{custom-0}, \texttt{0x0b}, the four-register R4 form, \texttt{funct3} zero) is the compression function of BLAKE2s~\cite{blake2}. Three registers are pointers: the $32$-byte chaining value $h$ is the four words at $\regs[\mathit{rs1}]$, the $64$-byte message $m$ the eight words at $\regs[\mathit{rs2}]$, and the instruction writes the $32$-byte result to the four words at $\regs[\mathit{rd}]$, a register it reads and does not write. The fourth register holds the byte counter, $t=\regs[\mathit{rs3}]$. Bit $0$ of \texttt{funct2} marks the final block: the finalization word $f_0$ is all ones when it is set and zero otherwise; the last-node flag $f_1$ is always zero. Every word is read before the result is written, so the result may overwrite the chaining value, $\mathit{rd}=\mathit{rs1}$, which is how a guest keeps one state across the blocks of a message, and each block is hashed where it lies. Bit $1$ of \texttt{funct2} makes the instruction a \emph{node}, the one-block hash of two digests, and requires bit $0$: the counter is $64$ whatever $\regs[\mathit{rs3}]$ holds, and the message's two halves are swapped when the low bit of $\regs[\mathit{rs3}]$ is set. A Merkle path is then one instruction a level, with the position in $\mathit{rs3}$, shifted right once a level: the message is the node below and its sibling, in memory in that order, and the bit puts them in the order the tree hashes them. Word $k$ of each of the three is the cell at its pointer $\oplus\,8k$, which is the pointer plus $8k$ when the chaining value and the result are aligned to $32$ bytes and the message to $64$, as the guest library ensures; an unaligned pointer permutes the words, deterministically, which is a guest bug rather than a soundness problem, and a pointer that is no word address traps like a misaligned load.

\paragraph{The extension-field multiplication.} Eight custom instructions multiply in the extension field $\E=\K[y]/(y^3+y+1)$, the field the proof's challenges live in. They are R-type, with opcode \texttt{custom-1} (\texttt{0x2b}).

They work on $128$ \emph{extension registers}, $\eregs[0]$ to $\eregs[127]$, written \texttt{f0} to \texttt{f127}. Each holds one element of $\E$, three words, its \emph{limbs} $c_0+c_1y+c_2y^2$. Each limb is an element of $\K$, read as above. As a run starts, $\eregs[0]$, $\eregs[1]$ and $\eregs[2]$ hold the constants $1$, $y$ and $y^2$, and the others hold $0$.

A register's number has seven bits: the five of its register field, then two of \texttt{funct7}, bits $0$ and $1$ for \texttt{fd}, $2$ and $3$ for \texttt{fs1}, $4$ and $5$ for \texttt{fs2}; bit $6$ of \texttt{funct7} is zero. Write $a=\eregs[\mathit{fs1}]$, $b=\eregs[\mathit{fs2}]$ and $c=\eregs[\mathit{fd}]$.
\begin{center}
\begin{tabular}{@{}cll@{}}
\hline
\texttt{funct3} & instruction & effect\\
\hline
$0$ & \texttt{extmul fd, fs1, fs2}  & $c = a\cdot b$\\
$1$ & \texttt{extmac fd, fs1, fs2}  & $c = c+a\cdot b$\\
$2$ & \texttt{extmulk fd, fs1, rs2} & $c = a\cdot \regs[\mathit{rs2}]$\\
$3$ & \texttt{extmack fd, fs1, rs2} & $c = c+a\cdot \regs[\mathit{rs2}]$\\
\hline
\end{tabular}
\end{center}
Bit $0$ of \texttt{funct3} adds the product to $c$. Bit $1$ makes the second operand an element of $\K$: the word in the integer register $\regs[\mathit{rs2}]$, whose number is the five-bit field alone. Bit $2$ gives each of the four a \emph{checked} form, \texttt{extmulz}, \texttt{extmacz}, \texttt{extmulkz} and \texttt{extmackz}: the instruction traps unless its result is zero. So \texttt{extmacz fd, fs1, f0} runs exactly when $\eregs[\mathit{fd}]=\eregs[\mathit{fs1}]$, and leaves $0$ in \texttt{fd}.

Every operand is read before $c$ is written, so \texttt{fd} may be \texttt{fs1} or \texttt{fs2}. For example, \texttt{extmul f5, f5, f5} squares $\eregs[5]$ in place.

Two more instructions, with opcode \texttt{custom-2} (\texttt{0x5b}), move an element between memory and an extension register. \texttt{eld fd, imm(rs1)} has a load's fields, and \texttt{esd fs2, imm(rs1)} a store's; the extension register's number is its five-bit field, then the two low bits of \texttt{funct3}, whose third bit is $0$ for \texttt{eld} and $1$ for \texttt{esd}. The element's limb $k$ is the word at $(\regs[\mathit{rs1}]+\mathrm{imm})\oplus 8k$, which is the word $8k$ bytes on when the element is on a $32$-byte boundary, as the guest library and the generated programs keep it; elsewhere the three words are permuted, deterministically. Each of the three must be an aligned word of RAM or the advice, or the instruction traps. \texttt{eld} never writes a constant: a destination below \texttt{f3} is undefined. A word $w$ also becomes an element as $1\cdot w$, by \texttt{extmulk fd, f0, rs2}.

The constants are never written: a destination below \texttt{f3} is undefined, and so is a base-field form whose \texttt{funct7} names a second operand past $\regs[31]$, like every other \texttt{custom-1} encoding.
