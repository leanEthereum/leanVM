\begin{abstract}
This document specifies the stateless hash-based signature leanVM aggregates: the
SPHINCS$^+$~\cite{SPHINCSPLUS} profile verified on Ethereum by NiceTry's
\texttt{SphincsVerifier\_v2}~\cite{NICETRYV2,NICETRYDOCS}. It is standard FORS under
a standard WOTS$^+$ hypertree, with Keccak-256 as the only hash and FIPS~205's
32-byte addresses~\cite{FIPS205}:
\begin{itemize}
  \item \textbf{Parameters:} $n=16$, $h=20$, $d=5$, $h'=4$, $a=9$, $k=19$, $w=16$, $\ell=32+3=35$.
  \item \textbf{Public key: 32 bytes} $(\seed,\pkroot)$, on chain two \texttt{bytes32}.
  \item \textbf{Signature: 6176 bytes.} No grinding anywhere: no randomizer search, no WOTS counter.
  \item \textbf{Verification:} 217 hash calls plus the chain steps, $267$ per layer on average and at most $510$; about $1550$ calls and $1600$ Keccak-f permutations in all.
  \item \textbf{Budget:} $2^{20}$ FORS instances, about $10^6$ signatures per key~\cite{NICETRYDOCS}.
\end{itemize}
The on-chain verifier is normative. \texttt{crates/sphincs} implements this document,
verifies NiceTry's reference vector, and reproduces it byte for byte from the same
seeds; \texttt{guests/lean\_ethereum.py} verifies the same signatures in the VM.
\end{abstract}

\section{Notation and hashing}
\label{sec:hashing}

Byte strings are written in memory order and $\concat$ is concatenation.
$\BE_r(z)$ is the $r$-byte big-endian encoding of an integer $z$. A 32-byte string
$D$ is also read as the integer $\mathrm{int}(D)=\sum_{i<32} D_i\,256^{31-i}$, and
$\mathrm{bits}(D,s,t)=\lfloor \mathrm{int}(D)/2^s\rfloor \bmod 2^t$: bit $b$ of
$\mathrm{int}(D)$ is bit $b\bmod 8$ of byte $31-\lfloor b/8\rfloor$. Every field of
a digest is read this way, least significant first.

$\K$ is Keccak-256 as the EVM computes it: the Keccak-f[1600] sponge with rate 136
bytes and padding $\texttt{0x01}\concat 0^*\concat\texttt{0x80}$ (not SHA3-256, whose
first padding byte is \texttt{0x06}). Values are $n=16$ bytes. A value $v$ enters a
tweakable hash as the 32-byte word $\slot(v)=v\concat 0^{16}$ (the value in the top half of a
\texttt{bytes32}), and $\trunc(D)$ keeps the first 16 bytes of a digest (the
verifier's \texttt{N\_MASK}).

\paragraph{Addresses.}
An address is FIPS~205's uncompressed 32-byte $\ADRS$, all fields big-endian:
\[
  \ADRS=\BE_4(\mathit{layer})\concat\BE_{12}(\mathit{tree})\concat\BE_4(\mathit{type})
  \concat\BE_4(w_1)\concat\BE_4(w_2)\concat\BE_4(w_3).
\]
\begin{center}
\begin{tabular}{@{}llll@{}}
\toprule
type & $w_1$ & $w_2$ & $w_3$\\
\midrule
0 \textsf{WOTS\_HASH} & key pair & chain $i$ & hash address\\
1 \textsf{WOTS\_PK} & key pair & 0 & 0\\
2 \textsf{TREE} & 0 & height & index\\
3 \textsf{FORS\_TREE} & key pair & height & index\\
4 \textsf{FORS\_ROOTS} & key pair & 0 & 0\\
5 \textsf{WOTS\_PRF} & key pair & chain $i$ & 0\\
6 \textsf{FORS\_PRF} & key pair & 0 & index\\
\bottomrule
\end{tabular}
\end{center}
Types 5 and 6 are the signer's own and never reach a verifier.

\paragraph{The hashes.} For values $v_1,\dots,v_m$,
\[
  \Th(\ADRS, v_1,\dots,v_m)=\trunc\!\left(\K\!\left(\slot(\seed)\concat\ADRS\concat\slot(v_1)\concat\cdots\concat\slot(v_m)\right)\right),
\]
96 bytes for one value ($F$), 128 for two ($H$), $64+32m$ for the FORS roots
($m=19$, 672 bytes) and a WOTS key ($m=35$, 1184 bytes). The message digest is
\[
  \Hmsg(R,M)=\K\!\left(\texttt{0xFF}^{32}\concat R\concat\seed\concat\pkroot\concat M\right),
\]
112 bytes, kept whole; $M$ is the 32-byte message (an ERC-4337 \texttt{userOpHash}).
No $\Th$ input is 112 bytes long.

\section{WOTS$^+$}
\label{sec:wots}

A WOTS key on layer $\lambda$ is named by its tree $t$ and key pair $j$; write
$A_{\lambda,t,j}(\mathit{type},w_2,w_3)$ for the address $(\lambda,t,\mathit{type},j,w_2,w_3)$.
Chain $i<\ell$ starts at the secret $s_i=\PRF(A_{\lambda,t,j}(5,i,0))$ and steps
\[
  c_i^{(0)}=s_i,\qquad c_i^{(p+1)}=\Th\!\left(A_{\lambda,t,j}(0,i,p),\,c_i^{(p)}\right),
\]
and the key is $\mathit{pk}=\Th(A_{\lambda,t,j}(1,0,0),c_0^{(15)},\dots,c_{34}^{(15)})$.

\paragraph{Digits.}
A node $N$ (16 bytes $N_0,\dots,N_{15}$) is signed directly. Its digits are
\begin{gather*}
  x_{2m}=\lfloor N_m/16\rfloor,\quad x_{2m+1}=N_m\bmod 16\quad(m<16),\qquad
  x_{32+j}=\lfloor\mathit{csum}/16^{2-j}\rfloor\bmod 16\quad(j<3),\\
  \mathit{csum}=\sum_{i<32}(15-x_i)=480-\sum_{i<32}x_i.
\end{gather*}
Both are read most significant first, which is FIPS~205's WOTS$^+$ encoding. Raising a message digit lowers
$\mathit{csum}$, whose base-16 value is monotone in each digit, so some checksum chain
would have to walk backward.

\paragraph{Signing and verifying.}
The signature is $\sigma_i=c_i^{(x_i)}$. The verifier recomputes $x$ from $N$ and
walks chain $i$ from position $x_i$ for $15-x_i$ steps, hash address $x_i+p$ at step
$p$, then compresses the tops into $\mathit{pk}$.

\section{The hypertree}
\label{sec:tree}

Each tree of layer $\lambda$ has $2^{h'}=16$ WOTS keys as leaves. Node $u$ at height
$z\geq1$ is $\Th((\lambda,t,2,0,z,u),\mathit{left},\mathit{right})$, and an
authentication path lists the siblings from the leaf up. Folding a leaf at index $j$:
at height $z-1$ the current node is the right child when bit $z-1$ of $j$ is set,
and the parent's index is $j\gg z$.

A hypertree leaf $\htidx<2^{20}$ names one key pair on every layer: layer $\lambda$
uses tree $t_\lambda=\htidx\gg4(\lambda+1)$ and key pair
$j_\lambda=(\htidx\gg4\lambda)\bmod16$. Layer 0 signs the FORS key, layer $\lambda>0$
signs the root of layer $\lambda-1$'s tree, and the single tree of layer 4 has the
public root $\pkroot$.

\section{FORS}
\label{sec:fors}

The FORS instance of $\htidx$ uses tree address $t_{\mathrm F}=\htidx\gg4$ and key
pair $j_{\mathrm F}=\htidx\bmod16$, and folds its 19 trees into one index space (FIPS~205
Algorithm 17): node $u$ at height $z$ of tree $i$ has $w_3=(i\ll(9-z))\,|\,u$. With
$B(z,w_3)=(0,t_{\mathrm F},3,j_{\mathrm F},z,w_3)$:
\[
  \text{leaf }u\text{ of tree }i=\Th\!\left(B(0,(i\ll 9)|u),\,\PRF((0,t_{\mathrm F},6,j_{\mathrm F},0,(i\ll9)|u))\right),
\]
nodes are $H$ under $B(z,\cdot)$, and the FORS key is
$\Th((0,t_{\mathrm F},4,j_{\mathrm F},0,0),\mathit{root}_0,\dots,\mathit{root}_{18})$.
A signature opens tree $i$ at index $u_i$: its secret and its nine-node path.

\section{The scheme}
\label{sec:scheme}

\paragraph{Keys.} The secret key is a 32-byte master secret $S$. It derives FIPS~205's
three 16-byte seeds in separate hash domains,
\[
  \skseed,\ \skprf,\ \seed=\trunc\!\left(\K(\mathit{tag}\concat S)\right),
\]
$\mathit{tag}$ being the ASCII strings \texttt{SPHINCS-v2 SK.seed},
\texttt{SPHINCS-v2 SK.prf} and \texttt{SPHINCS-v2 PK.seed} respectively,
with $\PRF(\ADRS)=\trunc(\K(\slot(\skseed)\concat\ADRS))$. The public key is
$(\seed,\pkroot)$, $\pkroot$ the root of the layer-4 tree. On chain both are
top-aligned words, and a word whose low 16 bytes are nonzero is rejected.\footnote{The
derivation of the seeds is the signer's own and no verifier sees it. NiceTry's reference
script takes the three seeds directly, and \texttt{sphincs::sign\_with\_seeds} does
the same to reproduce its vector.}

\paragraph{Signing $M$.}
\begin{enumerate}
  \item $R=\trunc(\K(\slot(\skprf)\concat M))$ and $D=\Hmsg(R,M)$.
  \item $u_i=\mathrm{bits}(D,9i,9)$ for $i<19$, and $\htidx=\mathrm{bits}(D,171,20)$.
  \item Open FORS instance $\htidx$ at $u_0,\dots,u_{18}$; let $N_0$ be its key.
  \item For $\lambda=0,\dots,4$: sign $N_\lambda$ with key pair $j_\lambda$ of tree
        $t_\lambda$ on layer $\lambda$, append that key's path, and let $N_{\lambda+1}$
        be the tree's root.
\end{enumerate}
Signing is deterministic and stateless.

\paragraph{Verifying.} Recompute $D$ from $R$, $M$ and the key; recover the FORS key
from the opened secrets and paths; for each layer recover the WOTS key from the chains
and fold it up the path. Accept if and only if the last node equals $\pkroot$. There is
no other check: every well-formed signature either reaches the root or does not.

\paragraph{Serialization.}
\begin{multline*}
  R\,(16)\concat 19\times\left[\text{secret}\,(16)\concat\text{9 path nodes}\,(144)\right]\\
  \concat 5\times\left[\text{35 chains}\,(560)\concat\text{4 path nodes}\,(64)\right]
  =6176\text{ bytes}.
\end{multline*}

\paragraph{Cost.} Outside the chains a verification makes $1+19\cdot10+1+5\cdot5=217$
hash calls: $\Hmsg$, the FORS leaves and nodes, the FORS key, and per layer
the key and four nodes. The chains add $\sum_i(15-x_i)$ per layer, 267 on average and
at most 510. Keccak-f calls: the FORS key takes 5, a WOTS key 9, every other
call 1.

\section{Security}
\label{sec:security}

This is SPHINCS$^+$ in its standard form, so the usual reduction applies: with
Keccak-256 modelled as a random oracle, a forgery either finds a second preimage or
collision among the tweakable-hash calls (all domain separated by $\seed$ and a
distinct address), or produces a FORS signature on an instance's unopened leaves.
The FORS term governs the budget. $\htidx$ is pseudo-random, and an instance used
$\gamma$ times is forged with probability about $(\gamma/512)^{19}$, which keeps a
margin near 128 bits while $\gamma\leq5$; around $2^{20}$ signatures the expected
maximum load is near that, so a key is budgeted at about $10^6$ signatures, counted
off chain~\cite{NICETRYDOCS}. $R$ is keyed by $\skprf$, so nobody else can search
messages for digests landing on revealed leaves.

This document proves nothing itself. The Lean development in \texttt{formal/sphincs}
concerns the previous leanVM variant (WOTS$^+$C and FORS$^+$C over the leanVM hash) and
does not cover this profile.

\section{Verification in leanVM}
\label{sec:vm}

The recursion guest replays the verifier with the VM's \texttt{SHA3} opcode, one
Keccak-f step over thirteen cells of 16 bytes. The compiler's \texttt{keccak} builtin
absorbs Keccak-256's 136-byte blocks. Lane 16 carries message data in every block but
the last, so a non-final block cancels the padding bit the opcode sets there. A
block that starts mid-cell (every odd one) takes each split cell apart into its two
64-bit lanes, proved in $\mathbb F_{2^{64}}$, and repacks them. Value words make half of every
multi-block input known zeros, which cost nothing.

The guest decomposes the last 24 bytes of $D$ into bits, and builds every address
field from them with one multiply-add a bit into its big-endian position. A WOTS digit
is hinted as $g^{x_i}$, range checked, and dispatched to the arm that walks
$15-x_i$ steps. The arms return $x_i$, and $\sum_{i<32}x_i\cdot 2^{8\lfloor i/2\rfloor+4(1-(i\bmod2))}$
must rebuild the cell holding $N$ exactly. The checksum digits satisfy the one exponent
identity $\prod_{i<32}g^{x_i}\cdot\prod_{j<3}(g^{x_{32+j}})^{16^{2-j}}=g^{480}$. The range
checks make each $x_{32+j}<16$, so the base-16 representation, and with it every
checksum digit, is unique.
