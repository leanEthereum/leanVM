# The executor on the guest: computed hints, the reference memory, the advised sizes, the headline

Scope: what `execute_complete` (`LeanVM/Prover/ExecuteComplete.lean`) still needs on the deployed guest beyond the mode walk (`exec-mode.md`) and the pops (`exec-spec.md`, M5), and the chain to the headline. Prototypes (built in a scratch tree, not committed): `LeanVM/Guest/Memory/HonestX.lean`, `LeanVM/Guest/Exact/Defs.lean`, `LeanVM/Guest/Exact/InverseCheck.lean`, each about 2 s and under 1 GB.

## Recommendations in one place

Computed hints: a tree predicate `Tree.Exact` (every hint on every path writes the executor's formula of what it reads), free by kernel check and validity for the functions whose hints are pinned inside their own body (44 sites), carried through the P forms for the rest (719 sites, all under `verify_sub` but for the batching's grind check under `aggregate_claims` and leanSPHINCS' digest bits under `main_loop3`), with the instance's own valuation supplying it where B1 already chooses the honest values. Reference memory: `honestX`, the honest writes then the heap hints' words read off B1's reader, B2C generalized from `honest` to any memory covering the honest writes. Advised sizes: `Tree.heapPops`, a pre-order list of the advised buffers' sizes, equal to the `heap_sizes` pushes family by family from the existing `daHeapSizes_bufs` and `childHints_heap`. Headline: one parameter (the advice generator) and one field in `Statement/`, nothing moved.

## 1. Computed hints

The executor needs, at each computed hint, the reference holding at the outputs the formula of the inputs (`HintOk`'s value part). Every input is a cell the mode walk proves written, and `Fine` makes the executor's word there the reference's, so the condition is one on the reference alone: outputs equal `F(inputs)`. On B1's tree the outputs are whatever the valuation chose (`Atom.Holds (.hint _) = True`), so what is needed is that the honest tree's valuation (and, for a heap destination, its reader) holds the computed words.

Survey of the core IR (`Pack/*/Core.lean`, static sites; a loop body counts once), 763 computed sites in 110 functions, beside 1698 witness and 1318 allocation sites:

| kind | sites | destination | functions |
| --- | --- | --- | --- |
| `windowsExp` | 580 | stack | `decode_query_windows` (18 specializations, 540), `grind_check` (20, 40) |
| `digitsExp` | 128 | 96 heap, 32 stack | `verify_tables` (96 heap), `column_selector` (30), `assert_small_g_power` (1) |
| `bits` | 35 | stack | `padding_weight` (30), `verify_sig_lean_sphincs` (3), `g_power_of_word` (1); `start` is always `0` |
| `bitsExp` | 8 | 5 heap, 3 stack | `log2_ceil_in_the_exponent` (2 heap), `verify_tables` (3 heap), `rs_eq_run`, `shared_selector_tables`, `verify_keccak` |
| `inverse` | 8 | stack | `verify_tables` (6), `verify_bus_gkr`, `da_row_shape` |
| `limbs` | 2 | stack | `verify_tables` (`split_limbs`) |
| `log2Ceil` | 2 | bits heap, result stack | `log2_ceil_in_the_exponent` (2) |

Every computed hint the guest reads is pinned by a check (the guest's rule), but by two kinds of argument. H1, pinned inside the function's own body with no memory: `inverse` by the `assertNe` right after it (all 8), `limbs` by `hi = (w + lo)·Y⁻¹; assert_in_k(lo, hi)`, `bits` by squaring each bit and rebuilding the word (`padding_weight`, `g_power_of_word`), the stack `bitsExp` by squaring and rebuilding the `g`-power from constants (`rs_eq_run`, `shared_selector_tables`, `verify_keccak`): 44 sites. H2, pinned only through memory tables or callees: the windows through `tabs[w]` and the rebuilt word, the digits through `g_squares`/`sel_g`/`shares` lookups, `log2Ceil` through `g_squares` and `assert_small_g_power`, the sphincs bits through the digest's rebuild in callees, the heap digits and bits of `verify_tables` through `block_selector(_tab)` and its tables: 719 sites. Some outputs are read by nothing: `log2_ceil`'s bits (only the `log2Ceil` hint reads them) and the low `κ` bits of `verify_tables`' offsets ("written but never read"); those are free once the reference memory holds the computed words (section 2).

Options weighed. A generic uniqueness argument (every valid tree has the computed words) is true for H1 and is cheap there, a local fact about one body. For H2 it needs, at each instance, the tables its pointers name to hold their patterns and its callees to be sound, which is an instance-level fact of the honest tree; carrying such facts down the tree is the same plumbing as exposure, with the soundness proofs to write besides. Re-choosing the hinted words is free only where nothing reads them, and those words are heap words, handled by the reference memory, not by the valuation. Exposure costs plumbing but no new mathematics: B1's completeness proofs already build the honest words (`winHintVal`, `qwVal_hint` in `B1/Bits/QueryWindowsHonest.lean`; `offBits`, `offDigits` in `B1/Tables/VtC/BSel.lean`; the honest valuations `vtQn`, `cpQn`).

Recommended: `Hint.Exact rd σ h` (prototype `Exact/Defs.lean`): each kind's outputs (`Dest.words rd σ`) equal `runHint`'s formula, written with the executor's own `bitWord`, `wordNat`, `g^n`, the `g`-power inputs below their bounds (`n < 2^nbits`, a start cell below `2^7`), so that `HintOk` follows by rewriting; witness hints and allocations exact by definition. `Tree.Exact P rd t`: every hint event on every path of every instance. Then:

- Free set. A kernel check per function (as `noWitness`, `NoWitness.lean`): its subtree's computed hints are all of functions with an H1 lemma, call-closed, so every valid tree of it is exact. The H1 lemmas are local: `Stmt.blockNextOk p q` (a block's atoms satisfying `p` each followed by a partner) decided per function, `walk_partnered` (a path has the partners), and the atom lemma. Prototyped for `inverse`: `inverse_exact`, `walk_partnered`, `inverse_exact_of_walk` (every `inverse` hint of every valid instance is exact, no hypothesis on the instance), and the three per-function kernel checks (`InverseCheck.lean`, 2 s, 0.7 GB; the same check over the whole program passes too but takes 17 GB, so per function it is). `limbs` needs one algebra lemma on `E` (`lo, hi ∈ K`, `w = lo + Y·hi` gives `lo = w.limb 0`); the `bits` and stack `bitsExp` families one lemma each from their templates' soundness direction (the bits rebuild the word or the exponent). 1221 of 1601 functions have no computed hint in their subtree at all.
- Exposure. The P forms carry the tree predicate `t.pops P rd = ps`; make it `t.pops P rd = ps ∧ t.Exact P rd` once, in `RelAtInP`, `RelAtInCP`, `KidsFromInP`, `CompleteAtP` and their composition lemmas (`relAtInP_of_walk`, `splice_of_body`, `kidsFromInP_of_kids'`), each taking one more hypothesis: the node's own hints exact under the valuation the proof builds, `trivial` by kernel check for a function without computed hints, and the `_nil` lemmas gaining the free set. Leaves supply their own: `QwEnv.Ok` gains a `.hint` case for `decode_query_windows`, and similarly `grind_check`, `column_selector`, `assert_small_g_power`, `log2_ceil_in_the_exponent` (its `log2Ceil` word from `meaningLog2CeilExp_pow`), `verify_tables` (from `vtQn`), `verify_sig_lean_sphincs` (from its digest template). Ancestors on the pops chain (`verify_sub`, `open_stacked`, `main_loop3/4`, `aggregate_claims`, `main`) change only through the generic lemmas. Ancestors off it, which take their callees through the `_nil` lemmas today, move to P forms: `level_positions` and its loop (117 specializations each, generated by `whir-queries`, so the generator emits it), `opening_round`, `bus_grind_check` (14), `check_opening_terminal`. At most 380 functions are involved: the 110 with computed hints and their 270 ancestors.
- Residuals. The mode walk's residuals (46 exponent bounds, 7 nonzero divisors in 23 functions) are facts of the instance's valuation too. Carry them in the same predicate: `Tree.Every Q` (every node satisfies `Q f σ rd`), `Q` the conjunction of exactness and the function's residuals, so one plumbing serves both.

One more piece is needed for computed and witness hints alike, and is not in any plan yet: the hint bridge. `HintOk` is stated at a pc and a frame; `Tree.Exact` and `pops` at core hint atoms on a path. Two halves. The map: per function, each ISA hint (its offset, its place in the list) is the compilation of a core hint atom of the body, its operands the certificate's cells of the atom's values (`cert f v`), its constants equal; generated and kernel-checked per pack (the mode walk's `Fun.hints` are already the executor's, `HintsOk`). The path: an instance whose frame passes that offset has the atom among its path's events. `ExecCore` cuts the code into segments but does not pair them with the core's arms; B2C's completeness walk does, since it runs each frame along the path's events (`walk σ body = .ret es vs`, `FrameHolds`) and decides each compiled branch from them. So the path half belongs there: file the path's hint atoms in its book (`locC` maps `.hint _` to `.none` today), check at each pc it passes that the ISA hints there are filed, and let `CplRun` state it of the run it builds; the cost is regenerating the `Cplw` certificates. `Inv`'s frame then carries, for its instance, the run's pcs so far in that frame. The witness streams need the bridge to get the cursor right (`StreamNext`: the executor's pops so far are the tree's pops before this atom, in pre-order), the allocations to get the bump pointer right. All of it lands in one hypothesis of `step_at` (`Mode/Step.lean`), `hhint`: each hint's `HintOk` once its inputs are written.

## 2. The reference memory

`Memory.honest` writes the frames (header, the certificate's cells: every named value, temporaries, plumbing) and the paths' memory equations. A store is a `.load` atom (the core does not tell a store from a load), so every word a `DEREF` writes is an equation; a stack hint's outputs are named values, so in frames. The only words the executor writes and the honest memory lacks are heap hint destinations no load reads: 783 heap-destination hint sites, 680 witness and 103 computed, the computed all into the function's own fresh `HeapBuf`.

The patch (prototype `Memory/HonestX.lean`): `honestX … X := image (honestWrites ++ X)`, `HonestX` adds to `Honest` that `X` names words of the memory, is consistent, and agrees with the honest writes (`xcross`). Take `X := readerWrites rd_L A`, `rd_L` the image of `main`'s layout (`imageOf L hdr`, the reader B1's tree is valid on and on which its pops and exactness hold) and `A` the heap hint destinations on the tree's paths. Then the executor's heap writes meet the reference: a witness word is the popped entry, which `pops` reads off `rd_L` (`Dest.words`); a computed word is `F(inputs)` by `Tree.Exact`, provided B1's layout holds it (true of `verify_tables`, whose memory holds `offBits`, `offDigits`; `log2_ceil`'s bits must be added to its own layout, a stronger hypothesis on the memory its proof already takes).

Consistency. Against the equations, free: both are `rd_L`'s words (`xcross_of_reader`, proved). Against the frames, a placement fact `Tree.HintsIn`, as `Tree.LoadsIn` for loads: every heap hint destination is in the tree's data, then a `HeapBuf` word is no frame word (`frameWrites_not_buf`) and a `frameAddr` run's word is an equation already. Local for the 490 sites writing into a `HeapBuf` the function allocates itself (the 103 computed among them): a kernel check of the pointer and the bound `off + len ≤ size` where the size is a constant, the size's value otherwise; the 293 others write through a parameter in six functions (`main_loop0`, `main_loop1`, `main_loop4`, `claim_list_digest`'s two loops, `claim_list_last`), into `main`'s buffers, and need one fact each from `main`'s honest data. Retemp: `honestAt_retemp` re-chooses the range checks' temporaries (the words at `x` and `k/x`) to agree with the fixed writes (`FixedW`), and a range check can read any word below its bound (bounds reach `g^63` and beyond), a heap hint's word included; so `X` joins `FixedW` (`DischargeHyps` gains `X`'s consistency, the same three facts as `HonestX`), and the re-chosen temporaries agree with it. Exactness, pops, `heapPops` and `HintsIn` survive retemp: a temporary is no hint's operand and paths read only uses (`walk1_congr`).

Where it plugs. `honest_of_mainX` (beside `honest_of_main`, `Guest/EndComplete.lean`): after `honestAt_retemp`, the tree `T'`, `X` as above, `HonestX` from `HintsIn` and `xcross_of_reader`. B2C reads the honest memory only through `Honest.read_C`, `read_hdr` and `valid_image` (`B2C/Frame.lean`, `FrameAll.lean`, `B2.lean`), and `CplRun` is generic in the memory. So: `Covers L` (every honest write at a word of the memory reads back from `L`; proved for `honest` and `honestX`, with `Covers.read_cell`, `read_hdr`, `read_C`, `read_eqn`, `valid`, `HonestX.publicBoundary`), and in `Frame.lean`/`FrameAll.lean` the memory `honest …` becomes a variable `L` with `hL : Covers … L`, each `h.read_C hI hmem` becoming `hL.read_C h hI hmem`; `B2Hyps.frame` quantifies over covering memories; `b2_complete`, `b2_count`, `jumpTables_honestC` follow for `L`. `b2_complete` on `honest` is the instance. The certificate modules do not change.

## 3. The advised sizes

The advice has 14 `allocAdvice` sites, each before its function's first call: `main` 7, `claim_list_digest` 1 (called twice), `da_verify` 2, `verify_sub` 1, `verify_tables` 3. The executor pops `heap_sizes` in pre-order of entries: `main`'s 7, the two claim lists' chains, DA's 2 (`da_verify` runs before the children loop), then 4 per child; this is `nodeHeapSizes ++` each child's `childHeap`, the order `honestPushes` has. The core has no `allocAdvice`: an advised buffer is an `alloc`/`allocDyn` atom whose ISA hint is preceded by the advice.

Plan. (a) Generated data `advSlots f`: for each function with advice, the destination value `v` of the core allocation each `allocAdvice` stands for, in hint order; a kernel check that the `allocAdvice`'s pointer is `cert f v` and the later allocation hint at that pointer is that atom's. (b) `Tree.heapPops P : Tree → List (Option ℕ)`: a node's entries for its slots (`some n` where its path allocates `v` with `n` cells, `none` where it does not), then its callees' in call order, phantoms none; `noAdvice`, as `noWitness`, gives `[]` for the 1595 functions without advice in their subtree. (c) The families: `main`'s 7 from its buffers `mSizes (hData …)` (a new lemma, the sizes `nodeHeapSizes` lists), `claim_list_digest`'s from `listChainCells`, `da_verify`'s from `daHeapSizes_bufs`, a child's 4 from `childHints_heap`; composed, `t.heapPops = (honestPushes …).filter heap_sizes` mapped back, carried in the same tree predicate as the pops. With `SameStreams` off `heap_sizes` (`MainCompleteP`), every stream the executor reads is then the tree's, entry for entry. (d) In `HintOk`: `StreamNext` from `Inv`'s cursor (the bridge counts an `allocAdvice` as a pop at its function's entry), and `AllocOk` from `Inv`'s bump pointer: the executor's `nextFree` at an instance's hints is the model's cursor, so the `k`-th reservation lands at `fp + fs f + Σ_{j<k} bufs[j]`, which `Tree.Placed` names; this rests on the compiler reserving a frame's buffers in the model's path order before any call (`fe4177e9f`, `89d39781b`), so `AllocInv` is a field of `Inv` proved per allocation hint kind. The bound `nextFree + n < maxCells` comes from `κ ≤ 28`.

## 4. The final assembly

The chain, each a theorem with what it rests on:

1. `mainComplete_budgetX` (`Budget/FinalX.lean`): `MainCompleteP` with the tree also `Every Q` on `rd_L` (exactness and the residuals), `HintsIn` and `heapPops = honestHeap s w`. From the families' P forms with the extended predicate. Open: the H2 exposures and the off-chain ancestors (section 1), the H1 lemmas, `HintsIn` for six functions, the `heapPops` families, the residuals' proofs from B1, `open_stacked`'s P form (`CRecHosP.lean`, in progress), and B1's completeness of the child claim list's monotone path (`child_mono = 1`, which the honest prover takes when a child's slots increase).
2. `honest_of_mainX` (section 2): `∃ rd T X, HonestX … ∧` the tree facts above `∧` the words and counts within the budget.
3. `refX_valid`: `ValidExecution guestProgram input ⟨κ, honestX …, n⟩` with `committedSize ≤ 2^30`, from `b2_complete`/`b2_count` on covering memories; so `κ ≤ 28`.
4. `guest_inv`: `InvRule guestProgram (honestX …) n C (refMem …) GInv` and `GInv (initSt …)`, `GInv` the mode walk's frame stack with the cursor and bump invariants. Rests on: `Inv` and `InvRule` themselves (`Mode/Inv.lean`, not written); every function the run enters passing the walk (51 fail today, among them `main`, `verify_sub`, `verify_tables`, `verify_keccak`, `verify_bus_gkr`, `da_verify`, `aggregate_claims`, `certify_placement`, `claim_list_digest`, the claim lists, 11 `open_stacked`, 2 `keccak_layer`); the four heavy functions whose walks pass but are not kernel-checked (`exponent_tables`, `__loop15`, `da_column_offsets`, `__loop17`); `__jump_tables`' prologue, straight-line `SET`s with no walk; the three facts the walk leaves to `Inv` (a tail call's header copy, a loop's exit, the termination facts of a table call's untaken arms); the hint bridge; each frame an instance of `T` (`FrameHolds`, `honest_kid`) carrying `Every Q`; `RefOk` from the reference step.
5. `execute_completeX`: `execute_complete` with two more conclusions, `t.logMemorySize ≤ κ` (an `Inv` field `s.mem.used ≤ 2^κ`, or `AllocOk` against `2^κ` instead of `maxCells`) and `t.opcodeCount = ` the reference's (the executor's run reads only written cells, equal to the reference's, so `run` takes the same steps on `t.memory`); then `t.committedSize ≤ 2^30`.
6. `guestExecution_complete`: for `NodeRelation`, `GuestLimits`, `ChildrenOk` and the budget, `execute guestProgram input (guestAdvice seed s w) = .ok t`, valid by `execute_sound`, within `2^30`. `guestAdvice` built from `Data.adviceMainFrame` and `Data.adviceHints` (the data the mode certificates are checked against, `ctx_hintsOk`), not by parsing `Data.adviceText`, so no parser proof.
7. `guest_execution_complete_on_honest_children : GuestExecutionComplete guestAdvice`: `DeployedLimits` to `GuestLimits` and the budget (`Budget/Fits.lean`), honest children to `ChildrenOk` (`acceptableChildren_of_honest`, `HonestChildren.lean`).
8. The headline, `guest_prover_rarely_refused` (`Statement/Corollaries.lean`): the composed prover (advice, executor, `leanVmHonestProver`) at `ρ ∈ [1, 4]` and `2^35` nonces makes no proof, or `verifierRefusingZero` rejects it, with probability at most `2^-100` in the RPM: field 7 and `HonestProofRarelyRefused`. The `aggregate_complete_of` form (`completenessError fuel + rpmError …`, any fuel up to `2^64`) follows likewise from `Rpm.completenessRpm`.

## 5. The statement change

The executor is in `Statement/` already; the advice is untrusted for soundness (`execute_sound` holds for every advice), so it need not be. Proposed: `Theorems` gains a third parameter, `guestAdvice : Digest → NodeStatement → NodeWitness → Advice`, named at use like the two programs (`LeanVM.theorems_hold : Theorems extractor decoder LeanVM.Guest.guestAdvice`), and one field. In `Statement/LeanVmGuestCompleteness.lean`:

```lean
/-- The guest program's run on a node: the executor on the statement's digest, with the advice
the generator makes from the statement and the witness. -/
def guestRun (advice : Digest → NodeStatement → NodeWitness → Prover.Exec.Advice)
    (statement : NodeStatement) (witness : NodeWitness) : Except (ℕ × Prover.Exec.Fault) (Execution guestProgram) :=
  Prover.Exec.execute guestProgram
    (PublicInput.ofDigest (statementDigest (deployedSeed guestProgram) statement))
    (advice (deployedSeed guestProgram) statement witness)

/-- The executor runs the guest program to completion on the advice, within `2^30` committed words,
on every node `GuestCompleteOnHonestChildren` admits. -/
def GuestExecutionComplete (advice : Digest → NodeStatement → NodeWitness → Prover.Exec.Advice) : Prop :=
  ∀ statement witness,
    NodeRelation (bytecodeWords guestProgram) (deployedSeed guestProgram) statement witness →
    DeployedLimits statement witness → (∀ child ∈ witness.children, HonestChild child) →
    ∃ execution, guestRun advice statement witness = .ok execution ∧
      ValidExecution guestProgram
        (PublicInput.ofDigest (statementDigest (deployedSeed guestProgram) statement)) execution ∧
      execution.committedSize ≤ 2 ^ 30
```

`GuestExecutionComplete` implies `GuestCompleteOnHonestChildren`, so that field moves to `Corollaries.lean` with the headline (field 8). Why a parameter and not a move: `Hints.honestStreams` closes over 26 modules outside `Statement/` (about 4300 lines without the guest's source, among them the leanXMSS, leanSPHINCS and LeanDA schemes' hint computations, the deferring verifier's replay, coverage, lemma files), and the compiler's hint table is 2.7 MB of data; moving them adds reading to the statement for objects whose correctness the theorem itself establishes. What a reader must check of the parameter is only that it is a genuine prover's: a computable function of the seed, the statement and the witness (not `noncomputable`; `lake exe guest-run` runs it against the Rust on real nodes in CI). The cost: the statement does not say which generator; `LeanVM.lean` does, as it does for the extractor.

Text for `statement.tex` (Section on the guest's completeness, after the theorems' list; and the "What is not proved" item on witness generation shortened to the executor's speed):

> \paragraph{The prover from the witness} (\lean{GuestExecutionComplete}). \lean{Theorems} takes a third parameter, the advice generator: a function from the seed, a statement and a witness to the executor's advice (the compiler's hints by pc, the size of \texttt{main}'s frame, the witness streams). \lean{LeanVM.lean} instantiates it with \lean{LeanVM.Guest.guestAdvice}, a computable definition that the CI runs against the Rust on real aggregations. The field states that on every node \lean{GuestCompleteOnHonestChildren} admits, the executor \lean{LeanVM.Prover.Exec.execute} run on the guest program, the statement's digest and that advice returns a valid execution of committed size at most $2^{30}$. Nothing about the advice is trusted: every execution the executor returns is valid whatever its advice (\lean{execute\_sound}); the field says that this advice makes it return one. With \lean{HonestProofRarelyRefused}, the prover that runs the generator, the executor and \lean{LeanVM.leanVmHonestProver} on a statement and a witness makes a proof the verifier accepts except with probability $2^{-100}$ in the RPM (\lean{Corollaries}). \lean{GuestCompleteOnHonestChildren} follows and is a corollary.
