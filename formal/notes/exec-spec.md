# An executable, proved spec of the guest's prover

Goal: from a node statement and witness alone, a Lean pipeline that runs and is proved: hints, guest execution, AIR witness, proof, accepted by the verifier. Headline: on every node meeting `NodeRelation`, within `DeployedLimits`, with honest children, the composed prover returns a proof the verifier accepts (up to proof-of-work fuel), the hints included.

## What exists

- Hints: `Guest/Hints.lean`'s `honestStreams` is computable and equals the Rust's streams on real nodes (`guest-diff`, CI), but no theorem mentions it.
- Execution to proof: `Statement/Prover/` (`witness?`, `prove`), proved (`witness?_spec`, `isSome_witness?_iff`, `LeanVM.Completeness`). It takes the execution as input.
- Guest completeness: `GuestCompleteOnHonestChildren` states `∃ t : Execution guestProgram`. Its proof chooses the memory noncomputably: B1 gives a call tree whose valuations hold the hinted values existentially, `honestAt_retemp` re-chooses the range checks' temporaries by `Classical.choose`, and `Memory.honest` is the image of that tree.
- Execution: nothing in Lean runs a program on its inputs. `Guest/Interp.lean` runs the core IR, unproved, without the ISA's memory layout.

The missing stage is `(statement, witness) ↦ Execution guestProgram`, computed and proved.

## Architecture

1. **The executor** (`Statement/Prover/Execute.lean`, `LeanVM.Prover.execute`): the ISA run of `crates/leanvm_core/src/cpu/execute.rs`, transcribed. Memory starts empty and is write-once. Each instruction fills its unknown cell: XOR and MUL forward, a MUL's single unknown operand by back-solving, a `DEREF` between two unwritten cells by linking them (a union-find whose class holds the value). The hints a pc carries run before its instruction: allocation (`next_free`), witness streams, computed advice (bits, digits, windows, limbs, `log2_ceil`, inverse). Its inputs are the program, the per-pc hint table, the streams and the public input. Its output is `Except Fault (Execution prog)`. One deliberate difference from the Rust: an instruction that reads an unwritten cell fails here. The Rust records the read and `prove` refuses the execution, so both accept the same runs.
2. **Generic soundness** (`lean_vm/LeanVM/Prover/Execute*.lean`): `execute … = .ok t → ValidExecution prog input t`, for every program, hint table and stream. Hints and allocation are untrusted. The proof:
   - memory only grows;
   - `executeWith` is monotone in its reader;
   - the final image (unwritten cells zero, one value per link class) extends every state the run passed through.
3. **The guest's prover**: `guestExecution seed s w` runs `execute guestProgram guestHints (honestStreams …) (publicInputOf …)`, and the existing `prove` follows. `guestHints` is the compiler's per-pc hint table, generated by `guest-export` like the rest of `Data/`.
4. **Completeness** (`execute` returns `.ok` on every node the headline admits) by a generic simulation. The executor succeeds whenever some reference valid execution satisfies three conditions:
   - (a) at every hint site it holds what the hint computes from it;
   - (b) every instruction finds its unknowns where the executor solves them;
   - (c) it allocates where the executor does.

   Instantiated with the honest memory of the existing proof, each condition needs work:
   - (a) B1's honest valuations must expose their hinted values as functions of the statement and witness. That means restating each family's completeness with concrete hints instead of an existential, and showing that the stream entries each subtree pops are `honestPushes`' (proved, not trusted).
   - (b) Modedness, from a per-function certificate checked by the kernel, like B2C's.
   - (c) The memory layouts must agree (below).

Why the ISA level and not the core IR:
- The prover takes the memory image, and `ValidExecution` is stated at the ISA level.
- The soundness theorem is independent of the program.
- The comparison with Rust is byte for byte on the memory and the cycle count.

A core-level executor (proving `Interp` against `Fn.Sem`) would still have to lay out memory and repeat B2C.

## Open decision: the memory layout

The proof's honest memory places each call subtree contiguously: frame, then its `HeapBuf`s, then its callees (`Memory/Alloc.lean`). The Rust allocates in execution order. On the deployed guest they differ in four places:

- 159 functions allocate a `HeapBuf` after a call.
- 298 dispatch sites have arms of different sizes. The Rust allocates the largest arm's frame, the model the taken arm's.
- A loop's final, untaken call is a phantom. The Rust gives it `tail` cells, the model its callee's whole frame.
- 201 of the 578 loop helpers call other functions. The Rust lays a loop out as its frames, then each iteration's callees, iteration 0 first. The model places them in reverse iteration order.

Moving the model to the Rust's order would touch about 10 infrastructure files and 70 to 100 B1 proofs. B1 states buffer positions as `bases (fp + fs f) sizes` and composes callees from after them: a buffer's address depending only on its own frame is what lets a proof fix it before its callees are known. A single-pass Rust cannot produce the model's loop order: iteration 0's callees would have to follow later iterations' subtrees.

Choice: the hybrid.

- **The Rust follows the model** for the other three:
  - A call reserves the callee's `HeapBuf`s with its frame. The sizes are constants, or computed from the parameters at entry; the later hint then finds its pointer written and does nothing.
  - A dispatch sizes its frame by the selected arm.
  - The untaken call gets its whole frame.
- **The late sizes are advice.** A buffer of `main`, `verify_sub`, `verify_tables`, `da_verify` or `claim_list_digest` sized only after a call (or reached only in a branch) is reserved before the first call by `AllocAdvice`, its size popped from the `heap_sizes` stream (an empty entry where the run allocates none, leaving the pointer unwritten as the model does), which the aggregator and `Hints.honestPushes` compute from the statement and witness; its own later hint then does nothing. The guest's bytecode is unchanged and never checks the sizes: a wrong one only fails the run.
- **The model follows the Rust for loops**: a loop's frames, then each iteration's callees in forward order. Done: a subtree is placed at a frame and a cursor (`Memory/Alloc.lean`), a loop's iterations from one on are `RelAtInC`, `CompleteAtL`.

The executor follows the hints whatever they are, so it changes with the Rust and stays its byte-for-byte mirror.

## Pops at tree level (M5)

A family's block-level pops (`FallPops`, `SplicePops`) reach the honest call tree through the placed completeness forms with pops, which name the entries the chosen tree pops on the reader in scope:

- `RelAtInP … ps`, `RelAtInCP … ps` (`B1/Main/RelAtInP.lean`) are `RelAtInT`, `RelAtInCT` with the predicate `t.pops coreProgram rd = ps`; `KidsFromInP … cs pss …` gives one entry list per call, `[]` for a skipped one.
- `relAtInP_of_walk`, `relAtInP_of_walk_loop` take the hypotheses of `relAtIn_of_walk`, `relAtIn_of_walk_loop`, the callees with their entries, and `splice rd σ es pss = ps`. `splice_of_body` gives that equation from the body's `SplicePops` (the template lemmas a family already proved) and a return that calls nothing.
- `CompleteAtP`, `CompleteAtDP`, `CompleteAtLP` (`B1/Main/CompleteP.lean`) take the entries as `Reader → List Pop`, since a heap hint's words are read through the memory; honest entries are usually constant. `kidsFromInP_of_kids'` composes the callees (`KidsP`), and `toCompleteAt`, `toD`, `toP`, `toL`, `toDP` drop the pops.
- Leaves come free. `noWitness g j` (`Memory/NoWitness.lean`) checks that function `j`, named `g`, has no witness hint in its subtree. It is decided per function by `decide +kernel`, with cost proportional to the subtree. The functions passing it are call-closed (`coreProgram_noWitIn`), so every valid tree of one pops `[]` on every memory (`pops_nil_of_noWitness`). `relAtInP_nil`, `completeAtP_nil`, `completeAtDP_nil` and `completeAtLP_nil` turn an existing proof into one popping `[]`. `RelAtInT.and_pops_nil` adds `∀ rd, t.pops coreProgram rd = []` to a tree predicate, so the `T` forms (`CompleteAtDT`, `CompleteAtDTB`, `KidsT`) carry it unchanged. 1153 of the 1601 functions have no witness hint in their subtree.
- Mute sets are not kept by hand: `noWitBlock j` checks a block of function `j`'s body (`NodeShapes`, `BatchPops`), `noWitS_of_callee` one callee (`DaPops`), each by `decide +kernel`, both landing in `noWitS` (`B1/Common/NoWitMute.lean`).
- A callee whose entries are its own buffers' words has a predicate of the memory: `CompleteAtDTBR` (`Budget/Bounded.lean`), from `completeAt_flatDTBR`, `completeAt_flatOutDTBR` and `flat_completeAtTBR` (a valuation property `Q rd`). `certify_placement_completeAtBR` and `verify_tables_completeAtTBWR'` expose the honest valuation and own buffers (`cpQn`, `vtQn`), from which `cp_honest_pops` and `vt_honest_pops` read their entries. `verify_sub_completeBTG` is generic in its three popping callees' predicates; `verify_sub_completeBT` (every predicate `True`) and `verify_sub_completeBTP` (their entries, given `open_stacked`'s) are its instances.
- To move a family over, rerun its placed proof with the `P` lemmas: swap `relAtIn_of_walk` for `relAtInP_of_walk`, build `KidsFromInP` where it built `KidsFromIn`, and discharge `hps` with `splice_of_body` and its pops lemmas. `B1/Opening/QueriesPlacedP.lean` does this for `walk_path` (`wp_relAtInP`, `WD.wpPops`), a level-0 iteration of `opening_queries` (`oqIter1_relAtInP`) and its loop (`oqLoop1_relAtInP`, its iterations' rows and children in order). `QD.rowPop_vals` states a row entry as the honest row's cells.

## Changes to `Statement/`

- `Prover/Execute.lean` (the executor) and the guest's hint table join the honest prover the completeness statements name. A reviewer checks only that the executor is a genuine one: its outputs are proved valid.
- `Theorems` gains the headline, `guestProverComplete`: the composed prover's proof is rejected with probability at most the existing bound, on every node `GuestCompleteOnHonestChildren` admits. That field can replace `guestCompleteOnHonestChildren`, whose existential it implies.

Each change is recorded in `statement.tex`.

## Milestones

- **M1, the approach.** The executor, its generic soundness, and `lake exe leanvm-execute`, compared byte for byte (memory, cycles) with the Rust on the prover differential's programs and the guest's `guest-diff` nodes, in CI. Report the executor's speed on a realistic node. One family on concrete hints: the computed-advice hints proved equal to what the B1 valuations hold.
- **M2, the guest end to end, run.** `guestHints` exported. `guestExecution`, then `prove`, then the Lean verifier, on Rust-exported nodes, in CI.
- **M3, the simulation theorem** and the modedness certificates.
- **M4, the layout** (the hybrid above): the Rust allocator and the three guest functions, then the model's loop placement.
- **M5 onwards.** B1 families on concrete hints, leaves first, up to `main`. Then the headline.

Each step is a green commit (`check-all.sh lean vectors`), and its cold-build cost goes in the commit message.

## Plan after the strategy review

An independent review (2026-11-14) kept the architecture: the executor, `execute_completeX`, the mode walk with `inv_rule`, the pops, `honestX` and the bridge's `compiles`/prefix checks all stay; a core-level evaluator would redo the heap analysis and lose the Rust mirror. The remaining work is regrouped:

1. Residuals by family: the challenge divisions in `open_stacked` from the honest-child hypotheses, the `walk_path` bounds from `WalkKnown`, the `sub` residuals from `LoadsIn` and `BufsOk`.
2. The walk closed: a rule or a small guest edit per remaining root failure; hand tables in the generators derived from the generated data.
3. The tree track as a theorem about the reference run (`RefTrace`): frame-to-instance map, pops cursor, bump pointer; `alignOk` per function for the 33 functions outside the prefix class and for calls. `inv_rule` is unchanged.
4. One tree-predicate pass (`Every Q`): computed-hint exactness, residuals, `HintsIn` and the `heap_sizes` slots together through the P forms, the locally pinned sites by kernel check, `level_positions` by its generator.
5. The remaining premises: termination from loop exits, `RefOk` from the reference step, the prologue, `X` kept by each step.
6. The final chain and the `Statement/` field, `guestAdvice` a parameter of `Theorems`.
