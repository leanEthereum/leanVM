# The core route

The guest's executability (on the honest hints every instruction finds its inputs written, `GuestExecutionComplete`) is proved from per-function facts about the zkDSL core IR and the compiled code, checked by the kernel, and generic theorems about the compilation proved once. Every compiled function is on the core route. Hand proofs cite core names (a value or statement by `val%`, `pos%`, a function by `fn%`), never bytecode offsets; what cites offsets is generated.

## Decomposition

Modedness is split by what each half needs to see.

* **Frame cells** (values, and the plumbing: header, callee frame pointers, jump targets, pooled constants, shared cells, range-check temporaries, hint cells) stay at the ISA: `CoreMode/Frame.lean`'s `frameOk`, one forward pass over the code as `Exec.exec` cuts it, a set of written frame offsets updated by the executor's own rules (`XOR`, `MUL` forward or back-solved by a divisor it knows nonzero, `KECCAK`, a `JUMP`'s cells, a `DEREF`'s pointer; a `DEREF` of mode `cell` stores when its frame side is written, loads when its heap side is known written or its offset is in the oracle `O`). It has no certificate of its own: its data is the function's interface (`FFun`), the oracle and stores from the pairing, and its residual divisors from its own walk.
* **Heap cells**, the only part that needs reasoning, are proved at the core: `CoreMode/HeapC.lean`'s `heapOkC`, one pass over the body over cells named by monomials of core values (`CCell`), each read's witnesses (`Wit`: an earlier event of its path, a precondition, a run, a residual) in a generated certificate (`HCert`). A call meets its callee's heap signature (`HSig`, `CoreMode/HeapCSig.lean`: points and runs over slots) and gains its guarantees; a loop helper's tail call meets its own preconditions, chained or covered. A function with no call and no loop may instead pass `heapOk` (`CoreMode/Heap.lean`), whose guarantees are cells its own loads witness (`postOk`).
* **The pairing** ties the two: `CoreMode/PairDefs.lean`'s `pairOk`, `Bridge.alignOk`'s in-order pass over code and body with the heap events consumed in order, each `DEREF` of a `load` at its certificate cells; it checks the oracle `O` (the offsets whose `DEREF` reads a cell the heap certificate proves written) and the stores `S` that the frame walk reads.
* **Residuals**: the statements on core names a heap certificate's witnesses use (`CRes`: `lt`, `sub`, `nz`), each of a family (below), a decidable check on the function's own code whose soundness at its honest instances is proved once per family from B1.
* **Signatures** are contracts: each function's `Fn.«k».csig : Mode.Sig` (`CoreMode/Sig/<pack>.lean`, tracked: the contracts' source, which `sigc.py` keeps as written) or one given in its rule file (`CONTRACTS`, below, written with `sigseed.py`'s literals), its frame cells checked against the frame layout and held by the route's checks to its heap signature (`CoreMode.ownOk`, `fitB`). A new function, or one whose frame layout changed, needs one in its rule file.

## The generic theorems

* `CoreMode/Spec.lean`, `FrameSpec`: what the stack invariant needs of one function, for any frame predicate `Q`; `Mode/InvRule.lean`'s `inv_rule_of_specs` builds `InvRule` from every function's, and `execute_complete_guest` follows.
* `CoreMode/CoreSound.lean`, `frameSpec_core`: a function whose core data its checks accept (`CoreOk`: `heapOkC` or `heapOk`, `pairOk`, `frameOk` with its windows' `FrameAcc`, the signature's `ownOk`, `retVOk`, `shapeOk`, `jumpCallOk`, `jtdOk`) meets `FrameSpec` at the core route's frame predicate `CoreAt` (the frame's honest valuation, its cells written as the passes say), wherever its frames have honest valuations. `CoreMode/CoreLoopC.lean`, `frameSpec_loopC`: the same for a loop helper (`LoopOkC`). Both share their step and call lemmas (`CoreFacts.lean`, `CoreJump.lean`: `heapRd_pair`, `fall_wrk`, `call_split`, `entry_fitB`, `post_wrk`, `resume_wrk`).
* `CoreMode/HeapCSound.lean`, `heapOkC_sound` (its parts `HeapCRun`, `HeapCInv`, `HeapCStmt`): every read of a path is written by the events before it, the guarantees written at return; `HeapCTree.lean` lifts it over an honest call tree. `PairSound.lean`, `FrameSound.lean`: the pairing's and the frame walk's passes give their facts at each offset they reach.
* Long functions are checked in windows from named states: `HeapCWin*` (the heap pass), `LoopWin` and `RouteWin` (a long body's other passes, chained by `Wins`), `PairRun` and `PairSlice` (the pairing: `pairOk_of_chainS`), `FrameWin` and `FrameSlice` (the frame walk: `chainFS_wins`). A window over a slice reads the code chunks it covers (`Bridge.slice`), not the code before it.
* `CoreMode/Assemble.lean`, `CoreFacts.of`, `assemble`: the generated certificates (`EndExec.CertE`, written one line each by `core_cert%`, `CoreMode/CertLit.lean`) closed into the end theorem's `ModeCerts`, with their termination facts and residuals.
* `EndExecCore.lean`, `coreHonAll_X`: on the tracks' invariant each frame of a function is an honest instance, its valuation the core route's; `EndExecCoreRes.lean`, `resFam_inst`: each family's residuals hold there. `EndExecFinal.lean` wires them into `ExecGaps` (`execGaps`).

## Module names

The `CoreMode/` modules are named by what they check and a suffix for the variant: `C` the check with calls (`HeapC`, `CoreLoopC`, `LoopBC`, `PairLoopC`; `PairC`, `PairJumpC` over its written cells, `WrittenC`), `L` a loop helper (`DataLC`, `GenWL`), `W` or `Win` in windows (`GenW`, `HeapCWin`, `FrameWin`, `RouteWin`, `LoopWin`), `Slice` windows over code slices (`FrameSlice`, `PairSlice`), and, for the heap check's windows, `F` a function body's and `M` a `match`'s (`HeapCWinF`, `HeapCWinM`). The generated glue is by what it holds: `GlueA` the advice, `GlueC` the code, `GlueE` the entries, `GlueG` the program's constants, `GlueP` the powers of `g`. A family's definitions are `Fam/*Defs.lean`, its facts carried down from the callers `Fam/*Q.lean` (`CsQ`, `ExpQv`, `TermQ`), and its proofs `Fam/Res*.lean`.

## Each function's own files

What the route knows of one guest function alone lives in that function's own files, read generically; the generators and the shared Lean files name no function.

* `scripts/core-mode/fn/<f>.py`, one per source function `f` (its specializations and loops, `fnrules.src`), merged by `scripts/core-mode/fnrules.py`: its inference features (`FEATURES`), its exponent and dimension facts (`EXP_FACTS`, `DIM_FACTS`, `EXP_VALS`, by parameter name where a parameter is meant), its stream-cursor loops (`ST_LOOPS`), its contracts given by hand (`CONTRACTS`, which `sigc.py` takes before a kept one), its own window sizes where the shared ones of `scripts/windows.py` would make a module too large (`FRAME_WIN`, `CORE_WIN`, `PAIR_WIN`), and hooks for its own families (`fam`, `ghost`, `sub`, `exp_bound`); `OWN` lists its own hand files beside its B1 modules, its `CoreMode/Fn/<f>/` implied: what a change to that function alone may change by hand, the checklist of an edit to it and the reference of a locality review. `fnreg.py` checks every list (`own_files`): each entry matches a file, no file is on two lists, and each `CoreMode/Fn/<f>/` has its rule file. A file about a callee as its caller sees it (a budget module counting a callee by its tree's shape, a family carried down from a caller, a dispatch's B1 module) is on the list of the function whose proof it is, so an edit to the other function can still reach it.
* `LeanVM/Guest/CoreMode/Fn/<f>/Data.lean`, `Fam.lean`, `Sound.lean` (namespace `CoreMode.Own.<f>`): lists by kind (`expFacts`, `dimFacts`, `expVals`, `stLoops`, `nzs`, `stCallers`, `mlLoops`, `cmLoops`, `glCallers`, `fams`, `gwFams`) and each entry's soundness (`<kind>_ok`, of the kind's predicate in `EndExecCoreFn.lean`: `ExpOk`, `StLoopOk`, `OwnOk`, …). `scripts/core-mode/fnreg.py` concatenates them into the registries (`Gen/FnData.lean`, `Gen/FnFams.lean`, read through `CoreMode/FnReg.lean`) and their soundness (`Gen/FnSound.lean`); the shared checks (`CoreRes.lean`, `CoreResG.lean`'s `resFamG`, `Nzs.lean`, `Fam/SelDefs.lean`, `Fam/TermDefs.lean`) and theorems (`EndExecCoreResAll.lean`, `EndExecCore.lean`, `NzsOk.lean`) read only the registries.
* The function's meaning, its B1 module (`Guest/B1/…`): a template equation `Fn.body (fn% «f») = …`, or a proof by the `vc` tactic (`Guest/VcTactic.lean`), or one from its reference function (`Guest/Ref`).
* For a callee whose loops enter its callers' completeness budget, its words interface: `B1/Tables/VtWords.lean` (`verify_tables`) and `B1/Gkr/VbgWords.lean` (`verify_bus_gkr`), proved by `VtWordsC.lean`, `VbgWordsC.lean`, instantiated at the deployed sizes in `Count/Fn/<f>.lean`. Its callers name only the interface.

## Names

A core value or top-level statement is cited by name: `val% «f» "name"`, `pos% «f» "name"`, and `valf% «f» "name"` across the specializations `f__L…` (`Guest/ValRef.lean`): the zkDSL variable the value is first bound to, as `guest-core --names` lists them. `scripts/val-names/gen.py` (the `core` step) writes the numerals of the names cited, `Guest/Data/ValNames/<f>.lean` (generated); a name the core IR no longer has fails there, naming the proofs that cite it. `scripts/val-names/rewrite.py [--write] FILE…` rewrites the numerals it can name for certain; `scripts/val-names/fnmap.tsv` (tracked) says which function a file or declaration is about where its source names none.

## The families

`resFamG` (`CoreMode/CoreResG.lean`) takes a residual of one of them, each function's own listed in its own files (`FnReg.fams`, `FnReg.gwFams`). `resFam` (`CoreMode/CoreRes.lean`), read off the function's own code: `rc` (a value range checked against a constant on every returning path), `sel` (a top-level selector's arms), `exp` (an exponent an entry run bounds), `addr` (addresses dereferenced and bits' powers), `rcv` and `rcn` (range checked against another value), `under` (beneath branch conditions), `neg`. Beside it: `resQ` (the instance's exponent and dimension facts), `split` (`g`-powers split from hinted bits, `splitRes`, `EndExecCoreSplit.lean`), `rcPts` (a cell at a range-checked index among the points it can be), `rcTab` (a range-checked table read's order). Each function's own, in `CoreMode/Fn/<f>/Fam.lean`: `column_selector`'s strided table (`csSub`), `vtStC` and `vtPerm` (`verify_tables`, `EndExecCoreVt.lean`), `cpPerm` (`certify_placement`), `vsExp` (`verify_sub`), `layQC` (`keccak_layer`), `daPadGap` and `daVerifyGap` (`da_pad`, `da_verify`, `EndExecCoreDa.lean`), `vkQC` (`verify_keccak`, `EndExecCoreVk.lean`), `glQC` (`gkr_layer`'s reads past its cursors, carried down from `verify_bus_gkr` through its several callers, `callersM`). The ghost families: `ml` (`child_claim_list_mono_last`'s reads in its caller's table, `EndExecCoreMono.lean`), `cm` (a frame loop's reads in its caller's table), `st` (a loop's reads past its cursor in its caller's proof stream, `EndExecCoreSt.lean`) and `verify_tables`' exponents (`vtExp`); and the claim lists' linked callers (`EndExecCoreLink.lean`). Their mathematics on the reference is in `CoreMode/Fam/` (the definitions `*Defs`, the facts carried down the honest tree from the callers, `RefAll.lean`'s `insts_all`, and the proofs `Res*`, stated over core names).

## The regeneration

`regen-guest.sh`'s `core-mode` step writes each function's data, by pack (`scripts/core-mode/`, each generator with `--check`, all through `scripts/genfiles.py`): its own registries (`fnreg.py`: `Gen/Fn*`), the claim list's linked callees (`anylink.py`), its signature and entry (`sigc.py`: `CoreMode/Sig/`, kept as written, `GlueE/`), its powers of `g` and glue to its global index (`pows.py`, `glue.py`), its heap certificate and its callees' heap signatures (`callc.py` for a body with calls, `loopcc.py` for a loop helper with `loopc.py`'s signature translation, `heap.py` for the rest: `Gen/<pack>/Data*`, long ones in windows `GenW/`, `GenWL/`), its pairing's oracle and stores (`pair.py`: `Gen/<pack>/Pair`, a long function's windows `Gen/<pack>/<fn>/W*`), its frame walk (`frame_gen.py`: `CoreMode/Pack/<pack>/Frame*`, one `frame_fn%` a function, `CoreMode/FrameLit.lean`), its core data and route checks (`core.py`: `Gen/<pack>/Core`, `Route`), and its certificate with its facts (`certs.py`: `Gen/<pack>/Cert`, `Gen/Certs*`). The `bridge` step (`scripts/bridge-cert/`) writes the hint bridge's checks per function (`Bridge/Align`, `AllocChk` with `alloc_chk%`, `PairChk`, `WitChk`, `JumpCells`, `ProgAl`); the `res` step the callers' facts carried down (`monocall.py`, `carry.py`, `termcall.py`). `python3 -I scripts/core-mode/route.py` prints how many functions each check takes; a function no check takes is reported there and fails `core.py`. `scripts/check-fresh` runs these generators on a copy of the tree without the files they write, which they must write again.

## What a guest edit touches

A one-function edit changes that function's core IR, so its generated data above; a changed signature regenerates its callers' heap certificates (data only). The bytecode offsets move for every function laid out after it, so their generated data that cites offsets (the bundles, frame walks, pairings, bridge checks) is regenerated too, with no hand proof involved. The hand files an edit can touch are the edited functions' own: their B1 modules, their rule files (`scripts/core-mode/fn/<f>.py`, `CoreMode/Fn/<f>/`), their contracts in `CoreMode/Sig/` when their frame layout changed, a callee's words interface and its `Count/Fn/<f>.lean` when its loops change, and their budget modules, the proofs about a function's body that count its callees (`main`'s `Budget/{Main,MainCount,MainExact,Instrs,Closed*,Final*,Deployed*,End,L5Count,MvCount}` and `Count/Instances`, `verify_sub`'s `Budget/VsCount` and `Count/{VsBound,VsWords,VsWB}`), all on their rule files' `OWN` lists (above). A rule file and its function's Lean data name core values and statements as the proofs do, never by number: `fnrules.val('f', 'name')`, `valf`, `pos` in Python (resolved through `Data/ValNames/`, which `val-names/gen.py` also writes for the rule files' citations) and `val%`, `valf%`, `pos%` in Lean; a table both sides hold (`EXP_FACTS`, `ST_LOOPS`, the families' constants) is written once, in the Lean data, and read by the rule file with `fnrules.lean_def`, so a renumbering changes neither. That covers renumbering only. A positional name (an expansion path, `@k`, `~k`) can shift when an edit inserts a statement or a binding before it: the citing proof then fails to elaborate or the kernel rejects it, at that site, so the cost is a diagnostic, never soundness. An inlined helper (`fs_perm`, `squeeze`, `fs_load`, …) has no core function of its own: its body is in every function that inlines it, and their proofs cite values on its expansion paths (`…:helper.…`), so an edit to it is an edit to each of them and touches their own files. The count generators (`scripts/count/`) likewise read each function's roots, words and parts from its rule file. `regen-guest.sh`'s `changes` step lists the hand modules that read a changed function, and `val-names/gen.py` the proofs citing a name it no longer has.
