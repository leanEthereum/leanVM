# formal

What is proved is [`statement.tex`](statement.tex), the one document a reviewer reads; this file is for contributors and agents. Each project's root module and its modules' docstrings say how its proof goes.

## The Hotwire port

The link (`crates/verifier/src/link.rs`) replaced the bus and the table sumcheck. The proofs of the protocol before it (leanVM's knowledge soundness and completeness, the guest program's knowledge soundness and execution completeness, the batching's soundness, the cost-compiled extractor and decoder, the honest prover's correctness, the core route's and the guest's certificates) are archived at tag `formal-bus-archive` (commit `7d46dcfc3c`). `Statement.Theorems` holds every end statement, each proved again for Hotwire (with the Fiat-Shamir framework they rest on, `lean_vm/LeanVM/Protocol/{Compile,Rpm}/`, packed messages included); `notes/hotwire-port.md` maps each archived family to the package that proves it again. The trusted statement, the honest prover (`Statement/Prover/`), the guest's witness generation and the Rust helpers (on the stable prover) are Hotwire's, and the gate (`./check-all.sh lean vectors`) runs every check against this tree's Rust.

## The repository

- Seven Lake projects, each built in its own directory: `Statement` (the statement: definitions and end statements only), `fast_fields` (proved `@[csimp]` lemmas that compile CompPoly's `GF(2^64)` and its degree-two extensions on machine words; `Statement` requires it and `Statement.Field` imports it, so the statement's definitions compile with them), and the proofs, `common`, `lean_vm`, `lean_xmss`, `lean_sphincs` and `lean_da`; the root is no Lean project. `lake build` at the root (`check-all.sh`) is the full gate; `.github/workflows/lean.yml` runs the same checks, a job per project (`fast_fields`' in the statement's).
- Name a project `lean_*` (or a library `Lean*`) only for a deployed object (leanVM, leanXMSS, leanSPHINCS, LeanDA); infrastructure is named for what it is (`common`, `Statement`, `fast_fields`).
- This tree is leanVM's `formal/`: `lean_vm` is about the Rust in this repository (`../crates`), at the same commit: the Lean and the Rust are always in sync, so a change to the Rust lands with the formalization's in one PR, and CI (`lean-vm-formalization` in `../.github/workflows/lean.yml`) rebuilds the proofs and checks every transcription against the Rust on every change to `crates/`.
- A citation `crates/<crate>/...` of a prover crate (`lean_vm_core`, `pcs`, `primitives`, `keccak_gkr`, `parallel`) names that crate in either prover tree, `crates/stable_prover/` or `crates/experimental_prover/`, as in the root AGENTS.md; the scripts, which build against one tree, name it in full.
- Generated data (`Statement/Data/`, `lean_vm/LeanVM/Guest/Data/`, the guest's per-function core IR and its compiled functions' certificates `lean_vm/LeanVM/Guest/Pack/`, the certificates' kernel checks `lean_vm/LeanVM/Guest/Checked{,/}`, `Guest/VsAt.lean`, `Guest/CoreNamesMod.lean`, `lean_vm/tests/LeanVMTests/Spec/NodeVectors.lean`, `lean_vm/tests/LeanVMTests/Guest/{Programs,Manifest}.lean`, the fold rounds' table in `lean_vm/LeanVM/Protocol/ToArkLib/Whir/AffineCombinerDeployedTable.lean`, by `lean_vm/scripts/whir-fold-table`) is regenerated, not edited: by `lean_vm/scripts/guest-export` from leanVM's sources at the pin, by `lake exe guest-core` and by `lake exe guest-cert --k`. The guest's constants are `Guest/Data/Consts.lean`, apart from its functions' bodies (`Guest/Data/Source.lean`), so a module that reads only constants does not rebuild on a body edit. `lean_vm/scripts/regen-guest.sh` runs `guest-export`, `guest-core` (with the value names, the names' modulus and `vs-at`), `guest-changes` and `guest-cert --k` in order. What the generators write whole is not committed (`formal/.gitignore` lists it, and CI fails on a file it writes that is not ignored): run `regen-guest.sh` before building `Statement` or `lean_vm`, after a checkout or a pull that changes the guest (`check-all.sh` and CI run it first). The fold rounds' table and `Programs.lean` stay committed.
- No `sorry`, `axiom`, `admit`, `native_decide`, `implemented_by` or `unsafe`, and no local overrides of a lakefile's options (one exception: `lake-build.py --dev`, below); every warning is an error, deprecations included. The outer axiom footprint check permits any subset of Lean's three standard axioms.
- Builds are heavy: run them on a large machine, after `lake exe cache get`. Cap `lean` and compiled executables with `ulimit -v`, not `lake` (it reserves about 1 GB of address space per job). The scripts run on macOS too, which has neither that cap nor a systemd scope: `lake-build.py`'s memory budget is the only guard there.
- An edit rebuilds what imports it, directly or not (in the module system only when what it exports changes: a statement, an exposed body, a declaration added or removed, its imports; and only through `public import`s: a private `import` stops the rebuild, while a file outside the module system sees everything below it). Keep a slow module, such as kernel-checked certificates, importing only the functions it evaluates and their facts, in modules of their own, never the proofs that use the certificates; `tools/NeededImports.lean` lists a module's needless imports and the modules to split, and `tools/deps.py cone FILE` what an edit of `FILE` rebuilds (Tools, below).
- A proof that needs more than the default `maxHeartbeats` is slow for a reason: profile it (`python3 -I tools/profile.py FILE`, which names the costly steps and their usual fixes) before raising the budget, and raise it on that declaration alone (`set_option maxHeartbeats N in`), never on a file. Tactics that try every hypothesis (`tauto`, `contradiction`, `aesop`, `congr`, `decide` on a goal with a large context) run slow where the context holds a kernel check of large data: clear it first (`clear * - h`). A long chain of `++` over lists of constructors elaborates as one `binop%` tree, slowly: write a new one `List.flatten [a, b, …]`, unless its proofs read the `++` shape.
- Since Lean 4.35 `Fin.foldl`, `Fin.foldr`, `List.ofFn` and `Array.ofFn` are structural, so the elaborator (`isDefEq`, `whnf`, `rfl` after `rw`/`unfold`, `congr`, `decide`, `exact` against an expected type, linters reading a local's type) evaluates concrete Keccak-f, `GF(2^64)` products (CompPoly's `carryLessMul`), large `ofFn` literals and whole protocol runs (`runI`, `shapedI`) where it used to stop: a recursion-depth error or a `whnf` timeout. Never raise `maxRecDepth` or `maxHeartbeats` for it, and making those definitions irreducible only turns the error into a failed unification. Instead keep the elaborator off the heavy term: an algebraic lemma for what it would compute (a power of `g` by `pow_one`, not an evaluation), a concrete equation decided by the kernel and rewritten (`rw [show … by decide +kernel]`, `decide +kernel` for a closed goal), `congrArg f` or `Finset.sum_congr` instead of `congr`, `dsimp only [d]` to expose both sides before a `refine`, `have h := e; exact h` to elaborate `e` before matching it, `generalize` on a concrete heavy subterm, `with_reducible exact` on the alternatives of a `first`, and arguments given explicitly rather than unified.
- The Rust code (Rust verifier, prover, guests) is test evidence, not proof; a proof claim cites leanVM sources at a named commit.
- `lean_da` builds on Benedikt Wagner's work (his framework for erasure code commitments and its games, from `b-wagn/fv-pq-da`), ported and instantiated with LeanDA: credit him in its files and in every commit that touches it.

## Statement

- `Statement/` is the trusted statement: twenty-seven files, eighteen at the top and the verifier's pieces in `Statement/Verifier/` (`statement.tex`, the reviewer's document, lists them in reading order; keep it in step with every change to `Statement/`; of them, a reviewer checks the guest's witness generation, `LeanVmGuestProver.lean`, only as a genuine prover), the generated guest bytecode and the compiler's hints (`Statement/Data/`, their bodies not exposed, for build locality: the values are unchanged, and a module that evaluates them adds `import all Statement.Data.Bytecode` or `AdviceHints`, which `import all` their chunks; such a module evaluates the data by `decide`, `decide +kernel`, `unfold` or `by rfl`, never by `simp` or `rw` with the data's names, whose equation lemma it would export, and a term-mode `rfl` over the data fails), the honest prover the completeness statements name (`Statement/Prover/`, its executable `LeanVM.Prover.prove` and the executor that runs a program on its advice, `LeanVM.Prover.Exec.execute`, fifteen files, generic over the program: a reviewer checks only that it is a genuine prover; the executor's soundness and completeness are proved in `lean_vm/LeanVM/Prover/`), proved `@[csimp]` lemmas for speed only (`Statement/Fast/`, and `fast_fields/` for the fields) and the proofs of laws the definitions need (`Statement/Lemmas/`, such as the irreducibility of `E`'s modulus), neither part of what a reviewer reads. It imports only Mathlib, VCVio, CompPoly, `fast_fields` and its own files, and `import all` only of `Statement.Data` (CI checks it), and every change to it changes what is proved. No file beyond the twenty-seven without asking. Definitions and end statements only: a proof belongs to the proof projects, unless a definition needs it (a structure's law, a decidability instance).
- Keep the leanVM definitions a faithful transcription of the leanVM sources they cite (Rust and guest items by name, `doc/leanvm` sections), at the commit they name. Cite by name, never by line number: line numbers go stale with every edit to the file they point into.
- Only statements in the random-permutation model are end statements; the random-oracle model and the sponge's indifferentiability are proof steps, in the proof projects.
- Each proof project's root module is its end file: it checks each end theorem against its `Statement` proposition and pins its axioms.
- `lake build` in `Statement/` builds the twenty-seven files, `Data/`, `Fast/`, `Lemmas/` and `Prover/`; the data's modules are heavy, so build them as CI does, `python3 -I ../lake-build.py .`.

## lean_vm

- Speed comes from proved `@[csimp]` lemmas (`Statement/Fast/` and `fast_fields/`: a `@[csimp]` lemma acts where a definition is compiled, so the statement's own definitions must see them); lemmas about the statement's definitions are in `LeanVM/Facts/`.
- A word of `E` has two limbs (`E.limb : Fin 2 → K`), and a numeral index wraps: `x.limb 2` elaborates and reads limb `0`. Write limbs `0` and `1` only.
- `leanvm-prove` runs the prover recompiled with `E`'s arithmetic on machine words (`LeanVM/Prover/Fast/`: every prover and verifier definition that multiplies in `E` copied, `@[csimp]` by `rfl`). A recursive prover definition is copied by hand there, its text with `mulE` and proved equal by induction; when the prover gains one, the build of `LeanVM.Prover.Fast.Prover` names it.
- `lake build` builds every module under `LeanVM/` (the lakefile's globs), and `LeanVM.lean` pins the end theorems' axioms. `lake test` builds every module under `tests/LeanVMTests/`; a test too slow for the interpreter is a run of the compiled `test-runs` (`tests/LeanVMTests/Runs.lean`, run with `lake env .lake/build/bin/test-runs` after `lake build test-runs`), as the gate does. Use `lake build <Module>` to check one module, not `lake env lean`.
- Lake has no job limit, so a cold parallel `lake build` can exceed a 16 GB machine. `python3 -I ../lake-build.py . LeanVM LeanVMTests` runs one `lake build` whose modules, the statement package's included, it admits by their recorded memory, the cores busy (CI uses it; `lake-build.tsv` holds the heavy modules, `--seed` rewrites it). A module must stay under 7.5 GB (the gate's cap), a hand-written one well under that. `lake-build.tsv` is tracked: after deleting or renaming heavy modules, prune their rows (or `--seed` it from a full build), so that `lake-build.py` and `tools/deps.py` read current modules.
- `lake-build.py --dev` is for development only: it builds into `.lake/build-dev` with the kernel skipped (`debug.skipKernelTC`) on `LeanVM` (its dependencies, `Statement` among them, are built as usual), several times faster. Elaboration still checks ordinary proofs; a false `decide +kernel` passes, and `#print axioms` does not show it. Never use it for CI, a gate, a push or a claim: those run the build above, kernel included.
- Outside CI, `lake-build.py` turns on Lake's local artifact cache (`LAKE_ARTIFACT_CACHE`, `LAKE_RESTORE_ARTIFACTS`): clones and branches on one machine share build products, keyed by the trace's hash (options included, so a `--dev` product never satisfies the real build). The cache sits in the toolchain's directory, or in `LAKE_CACHE_DIR`, and is never evicted: delete it to reclaim space.
- `Statement/Verifier/` is the readable reference of the verifier, a file per file of `crates/verifier/src` (`Lib.lean` the verifier itself, `Sumcheck.lean` the sumcheck rounds of `transcript.rs`), and `Statement/LeanVmVerifier.lean` its constants (the WHIR parameters, `securityBits`, `grindingBits`, `maxStackedClaims`), which a Rust test (`whir_query_table.rs`) reads from that path: they stay there, as written. Differential tests compare it with the Rust verifier, `scripts/fuzz-verifier.py` on `tests/fixtures/verifier` (Commands, below; its mutation positions come from the Lean verifier's own traced run, `leanvm-verify --events`), and pin values of the verifier at its pins (`tests/LeanVMTests/Spec/Layout.lean`, `Protocol/Link.lean`, `Protocol/RingSwitchVector.lean`, `Protocol/Transcript.lean`, `Protocol/Verifier/Helpers.lean`, `Compiled.lean`). A protocol change in the Rust verifier fails CI until `Statement/Verifier/` and the proofs follow. The fixtures are not committed: `scripts/export-verifier-fixtures-rust.sh` writes them from this tree's Rust prover before the differential tests (Commands, below).

## Changing the spec

Every spec change reaches the guest, and a change to the guest's bytecode rebuilds what reads it: the generated data, the modules that evaluate the bytecode, and the proofs about the changed functions. Every kind of change follows one loop, from `formal/lean_vm` unless said otherwise; the recipes below say what each kind adds.

1. **Rust first.** Change the crates (the Rust verifier, the prover and the guest `guests/lean_ethereum.py`, as the root AGENTS.md's "Three verifiers" says) and make their tests pass.
2. **Transcribe** into `Statement/` what the change touched, citing symbols, not line numbers, and keep `statement.tex` in step.
3. **Regenerate**: `scripts/regen-guest.sh --jobs N` writes everything derived from the guest, in order, by the step names `--from` takes: `export`, the core IR (`core`: `guest-core`), `changes`, the certificates of the compiled functions against it (`cert`: `guest-cert --k`, B2's, `Guest/Sound.lean`). A failed step names what to fix; `--from STEP` resumes there. `--check` writes nothing and compares every generator's output with the tree byte for byte. The `changes` step (`scripts/guest-changes`, against the core IR the export replaced) prints each function whose body changed, was added or was removed, by stable name, with the hand-written modules that state its body or name it.
4. **Adapt the kept proofs** (`Guest/Binding.lean`, the executor's `Prover/Execute*.lean`, the wire's `Wire/`) and the pinned values the tests name (`tests/LeanVMTests/Spec/Layout.lean`, `Protocol/Link.lean`, `Protocol/RingSwitchVector.lean`, `Protocol/Verifier/Helpers.lean`, `Compiled.lean`), kernel skipped: `python3 -I ../lake-build.py . LeanVM LeanVMTests --dev --keep-going` until it is green; `--keep-going` lists every failure in one run. `python3 -I ../tools/deps.py cone FILE` says what an edit rebuilds.
5. **Gate**: `./check-all.sh lean vectors` from `formal/` (the real build, kernel included, then the axioms and the Rust comparisons).

**A guest change** (a function's body, a helper added or removed, a loop bound) is the loop as it stands: transcribe nothing unless a constant the statement mirrors changed. A changed body fails the proofs that state it by the core IR's statement and value numbers (`verify_sub`'s templates, the core route's rule files; `notes/hotwire-port.md`, What must change together): the `changes` step lists them, and they are rewritten from the new core IR. A function the core route no longer takes breaks `CoreMode.offSigs = []`'s `rfl` in `LeanVM.lean`. The decoder's size bound, `guestWitnessDecoderSizeBound` (`Statement/LeanVmGuest.lean`), is a statement constant, the decoder compiled for Hotwire's guest and a slack below one leanXMSS signature's encoding (`decoderProgram_size_le`, pinned in `lean_vm/LeanVM.lean`); a guest change that grows the decoder past it is a statement change, and so is one that shrinks it by more than that slack (as for the extractor's bound, `leanVmKnowledgeExtractorSizeBound`). A change to the guest's memory per item (a child, a claim of a child's list, a raw signature, a blob row) counts the memory budget's coefficients again (`NodeWitness.memoryBudget`, `Statement/LeanVmGuestCompleteness.lean`, at least `lean_vm`'s `Coefs.checker`, which `scripts/count` writes): `cargo test --release -p aggregation --lib guest_memory_within_its_budget -- --ignored --nocapture` checks them against the guest, with `memory_budget` in `crates/aggregation/src/tests.rs` its copy.

**A verifier change** (a check, a transcript message, its order) is `verifyExecution`'s phase in `Statement/Verifier/` (the file named for the Rust's). Update the pinned values the tests name (`tests/LeanVMTests/Spec/Layout.lean`, `Protocol/Link.lean`, `Protocol/RingSwitchVector.lean`, `Protocol/Verifier/Helpers.lean`, `Compiled.lean`), and run the differential tests (Commands, below).

**A protocol parameter** (grinding bits, `queryTable`, folds, stack bounds) is one definition in `Statement/LeanVmVerifier.lean`; the proofs state the rows it enters as expressions in it (`Whir/Params/Check.lean`). A WHIR parameter starts in `crates/experimental_prover/pcs/src/whir_config.rs` (the security search; the stable prover reads the verifier's table) and `crates/verifier/src/whir.rs` (the query table both verifiers carry, which `print_whir_query_table`, in `crates/experimental_prover/lean_vm_core/tests/verifiers/whir_query_table.rs`, prints), and a change to WHIR's folding regenerates the fold rounds' table: `cargo run --release --manifest-path scripts/whir-fold-table/Cargo.toml -- LeanVM/Protocol/ToArkLib/Whir/AffineCombinerDeployedTable.lean`.

**An ISA change** is `Statement/LeanIsa.lean`; **a scheme change** is `Statement/LeanXmss.lean`, `LeanSphincs.lean` or `LeanDa.lean` with its proof project (`lean_xmss`, `lean_sphincs`, `lean_da`); **a wire change** is `LeanVM/Wire/Encoding.lean`, compared with the Rust by `scripts/wire-diff.py`. Each reaches the guest through its bytecode, and the loop above follows.

## Commands

Run from the project's directory. `./check-all.sh lean` and `./check-all.sh vectors` at the root are the gate, and CI runs the same checks; read `check-all.sh` for every step.

```sh
# any project
lake exe cache get
scripts/regen-guest.sh --jobs 24                  # Statement, lean_vm: from lean_vm, the files derived from the guest, which are not committed
python3 -I ../lake-build.py .                     # lean_vm: python3 -I ../lake-build.py . LeanVM LeanVMTests
python3 -I ../lake-build.py . LeanVM --dev        # lean_vm, kernel skipped, never a gate

# lean_vm, against this repository's Rust
lake test && lake exe node-vectors
python3 -I scripts/fuzz-verifier.py tests/fixtures/verifier --jobs 4     # after lake build leanvm-verify and cargo build of scripts/rust-verifier-cli
python3 -I scripts/wire-diff.py tests/fixtures/verifier --jobs 8         # after lake build wire-diff and cargo build of scripts/wire-diff
scripts/export-prover-traces-rust.sh /tmp/p && lake exe leanvm-execute /tmp/p/*/                 # the executor against the Rust interpreter
LEANVM_GUEST_DIFF=/tmp/g LEANVM_GUEST_EXEC=/tmp/e cargo test --release --manifest-path scripts/guest-export/Cargo.toml --lib guest_diff -- --ignored && lake exe guest-run --rust /tmp/e [--prove] /tmp/g/*.txt   # the guest from statement and witness, in Lean
cargo run --release --manifest-path scripts/executor-faults/Cargo.toml -- /tmp/f && lake exe leanvm-execute /tmp/f/*/   # the executor's faults against both Rust trees
scripts/export-prover-traces-rust.sh /tmp/p && python3 -I scripts/prover-diff.py /tmp/p --mutations 40 --jobs 4 --identical --expected tests/fixtures/verifier
scripts/export-verifier-fixtures-rust.sh tests/fixtures/verifier          # the fixtures, not committed: before the differential tests above
scripts/regen-guest.sh --jobs 24 [--check] [--from STEP]                 # every file derived from the guest, after a change to it
python3 -I ../lake-build.py . LeanVM LeanVMTests --dev --keep-going      # every proof a change breaks, in one run
scripts/guest-export/target/release/guest-export . [--check]             # the guest's data, after a change to the guest
cargo run --release --manifest-path scripts/whir-fold-table/Cargo.toml -- LeanVM/Protocol/ToArkLib/Whir/AffineCombinerDeployedTable.lean [--check]   # the fold rounds' certificate, after a change to whir_config.rs
LEANVM_GUEST_DIFF=/tmp/g cargo test --release --manifest-path scripts/guest-export/Cargo.toml --lib guest_diff -- --ignored && lake exe guest-diff /tmp/g/*.txt

# lean_sphincs: the crates' known answers on the compiled statement
lake exe signature-kat ../../crates ../../crates/lean_sphincs/tests/lean_sphincs/known_answer.hex
```

## Tools

- `python3 -I tools/deps.py cone FILE`: what an edit of `FILE`'s interface rebuilds, its CPU time, longest chain and families, by Lake's rule for private imports; `deps.py slow`, `deps.py path`.
- `python3 -I tools/firewall-canary.py`: checks that rule against Lake (the gate runs it); the plan that rests on it is `notes/per-function-cone.md`.
- `python3 -I tools/profile.py FILE`: where a slow file's time goes, by declaration and step; its docstring lists the usual fixes.
- `lake env lean --run ../tools/NeededImports.lean MODULE`: the imports `MODULE` does not need, and the modules to split.
- `lake env lean --run ../tools/Unused.lean ROOT... --prefix P`: declarations under `P` that no root uses; read before deleting.
- `python3 -I tools/escape-scan.py DIR...`: fails on a proof escape outside comments (the gate runs it).
- `python3 -I tools/statement-imports.py`: fails on an import of `Statement/` or `fast_fields/` beyond what each may import, read with `lean --deps-json` (the gate runs it).
- `bash tools/test-axiom-footprint.sh`: tests the axiom footprint check on small compiled modules.
- `python3 -I tools/docnames.py`: names `statement.tex` and the docs cite that no Lean file has.
