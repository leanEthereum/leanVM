# formal

What is proved is [`statement.tex`](statement.tex), the one document a reviewer reads; this file is for contributors and agents. Each project's root module and its modules' docstrings say how its proof goes.

## The repository

- Six Lake projects, each built in its own directory: `Statement` (the statement: definitions and end statements only), and the proofs, `common`, `lean_vm`, `lean_xmss`, `lean_sphincs` and `lean_da`; the root is no Lean project. `lake build` at the root (`check-all.sh`) is the full gate; `.github/workflows/lean.yml` runs the same checks, a job per project.
- Name a project `lean_*` (or a library `Lean*`) only for a deployed object (leanVM, leanXMSS, leanSPHINCS, LeanDA); infrastructure is named for what it is (`common`, `Statement`).
- This tree is leanVM's `formal/`: `lean_vm` is about the Rust in this repository (`../crates`), and `leanvm-rev` names the commit its citations and generated data's headers were last checked against; bump it when the formalization follows a change to the Rust.
- Generated data (`Statement/Data/`, `lean_vm/LeanVM/Guest/Data/`, `lean_vm/LeanVM/Cost/Decoder/GuestTables.lean`, the decoder tables' chunks (`lean_vm/LeanVM/Cost/DecoderSize/`, `lean_vm/LeanVM/Cost/DecoderTablesFirewall.lean`), `lean_vm/tests/LeanVMTests/Spec/NodeVectors.lean`, `lean_vm/tests/LeanVMTests/Guest/{Programs,Manifest}.lean`, the fold rounds' table in `lean_vm/LeanVM/Protocol/ToArkLib/Whir/AffineCombinerDeployedTable.lean`, by `lean_vm/scripts/whir-fold-table`) is regenerated, not edited: by `lean_vm/scripts/guest-export` from leanVM's sources at the pin, by `lake exe guest-core` / `lake exe guest-cert`, or, for the decoder's tables, by `lean_vm/scripts/decoder-tables` from the guest's generated data, and their chunks by `lean_vm/scripts/decoder-table-chunks`; so are the stacked opening's templates (`lean_vm/LeanVM/Guest/B1/Whir/{Data,HelperData,HelperFind}*.lean`, `HelperTables.lean`, `MatPlan.lean`, by `scripts/whir-data` and `scripts/whir-mat-plan`; the query walks and the walk certificates' checks (`Guest/WalkOq*`, `WalkLq*`, `WalkOs*`, `WalkWp*`), the opening's specializations' templates (`B1/Opening/WalkBody*`, `QueriesBody*`, `WalkFns.lean`, `QueriesPlacedE.lean`, `B1/Bits/QueryWindowsData.lean`, `QueryWindowsBody*.lean`) and the regions marked generated in hand-written files (`QueriesFns.lean`'s cases, the specializations' lists), by `scripts/whir-queries/all.py`, in the stable names of `Guest/CoreRef.lean`; the walks' obligations, `lean_vm/LeanVM/Guest/WalkKnownAll.lean`, by `scripts/walk-known-all`; where `verify_sub`'s obligations sit in its body, `lean_vm/LeanVM/Guest/VsAt.lean`, by `scripts/vs-at`). `lean_vm/scripts/regen-guest.sh` runs every guest generator in order.
- No `sorry`, `axiom`, `admit`, `native_decide`, `implemented_by` or `unsafe`, and no local overrides of a lakefile's options (one exception: `lake-build.py --dev`, below); every warning is an error, deprecations included. The axiom footprint of every end theorem is Lean's three.
- Builds are heavy: run them on a large machine, after `lake exe cache get`. Cap `lean` and compiled executables with `ulimit -v`, not `lake` (it reserves about 1 GB of address space per job).
- An edit rebuilds what imports it, directly or not (in the module system only when what it exports changes: a statement, an exposed body, a declaration added or removed, its imports; and only through `public import`s: a private `import` stops the rebuild, while a file outside the module system sees everything below it). Keep a slow module, such as kernel-checked certificates, importing only the functions it evaluates and their facts, in modules of their own, never the proofs that use the certificates; `tools/NeededImports.lean` lists a module's needless imports and the modules to split, and `tools/deps.py cone FILE` what an edit of `FILE` rebuilds (Tools, below). Guard such a split with a check in the build, as `lean_vm/LeanVM/Guest/B2C/CertFirewall.lean` does.
- A proof that needs more than the default `maxHeartbeats` is slow for a reason: profile it (`python3 -I tools/profile.py FILE`, which names the costly steps and their usual fixes) before raising the budget, and raise it on that declaration alone (`set_option maxHeartbeats N in`), never on a file. Tactics that try every hypothesis (`tauto`, `contradiction`, `aesop`, `congr`, `decide` on a goal with a large context) run slow where the context holds a kernel check of large data: clear it first (`clear * - h`). A long chain of `++` over lists of constructors elaborates as one `binop%` tree, slowly (half a minute for `lean_vm/LeanVM/Guest/B1/Gkr/Layer.lean`'s `lyBody`): write a new one `List.flatten [a, b, …]`, unless its proofs read the `++` shape (`holdsList_append`).
- Since Lean 4.35 `Fin.foldl`, `Fin.foldr`, `List.ofFn` and `Array.ofFn` are structural, so the elaborator (`isDefEq`, `whnf`, `rfl` after `rw`/`unfold`, `congr`, `decide`, `exact` against an expected type, linters reading a local's type) evaluates concrete Keccak-f, `GF(2^64)` products (CompPoly's `carryLessMul`), large `ofFn` literals and whole protocol runs (`runI`, `shapedI`) where it used to stop: a recursion-depth error or a `whnf` timeout. Never raise `maxRecDepth` or `maxHeartbeats` for it, and making those definitions irreducible only turns the error into a failed unification. Instead keep the elaborator off the heavy term: an algebraic lemma for what it would compute (`addressOfIndex 1 = g` is `pow_one`, not an evaluation), a concrete equation decided by the kernel and rewritten (`rw [show channelSep MemPush.toRaw = g by decide +kernel]`, `decide +kernel` for a closed goal), `congrArg f` or `Finset.sum_congr` instead of `congr`, `dsimp only [d]` to expose both sides before a `refine`, `have h := e; exact h` to elaborate `e` before matching it, `generalize` on a concrete heavy subterm, `with_reducible exact` on the alternatives of a `first`, and arguments given explicitly rather than unified.
- The Rust code (Rust verifier, prover, guests) is test evidence, not proof; a proof claim cites leanVM sources at a named commit.
- `lean_da` is Benedikt Wagner's work (framework, theorems and proofs, from `b-wagn/fv-pq-da`), ported and instantiated with LeanDA: credit him in its files and in every commit that touches it.

## Statement

- `Statement/` is the trusted statement: seventeen files (`statement.tex`, the reviewer's document, lists them in reading order; keep it in step with every change to `Statement/`), the generated guest bytecode (`Statement/Data/`), the honest prover the completeness statements name (`Statement/Prover/`, its executable `LeanVM.Prover.prove` and the executor that runs a program on its advice, `LeanVM.Prover.Exec.execute`, fifteen files: a reviewer checks only that it is a genuine prover, its correctness proved in `lean_vm/LeanVM/Prover/`), and proved `@[csimp]` lemmas for speed only (`Statement/Fast/`, not part of what a reviewer reads). It imports only Mathlib, VCVio, CompPoly and its own files (CI checks it), and every change to it changes what is proved. No file beyond the seventeen without asking. Definitions and end statements only: a proof belongs to the proof projects, unless a definition needs it (a structure's law, a decidability instance).
- Keep the leanVM definitions a faithful transcription of the leanVM sources they cite (`*.rs:N`, `doc/leanvm` sections), at the commit they name.
- Only statements in the random-permutation model are end statements; the random-oracle model and the sponge's indifferentiability are proof steps, in the proof projects.
- Each proof project's root module is its end file: it checks each end theorem against its `Statement` proposition and pins its axioms.
- `lake build` in `Statement/` builds the seventeen files, `Data/`, `Fast/` and `Prover/`; the data's modules are heavy, so build them as CI does, `python3 -I ../lake-build.py .`.

## lean_vm

- Speed comes from proved `@[csimp]` lemmas (`Statement/Fast/`: a `@[csimp]` lemma acts where a definition is compiled, so the statement's own definitions must see them); lemmas about the statement's definitions are in `LeanVM/Facts/`.
- A word of `E` has two limbs (`E.limb : Fin 2 → K`), and a numeral index wraps: `x.limb 2` elaborates and reads limb `0`. Write limbs `0` and `1` only.
- `leanvm-prove` runs the prover recompiled with `E`'s arithmetic on machine words (`LeanVM/Prover/Fast/`: every prover and verifier definition that multiplies in `E` copied, `@[csimp]` by `rfl`). A recursive prover definition is copied by hand there, its text with `mulE` and proved equal by induction; when the prover gains one, the build of `LeanVM.Prover.Fast.Prover` names it.
- `lake build` builds every module under `LeanVM/` (the lakefile's globs), and `LeanVM.lean` pins the end theorems' axioms. `lake test` builds every module under `tests/LeanVMTests/`; a test too slow for the interpreter is a run of the compiled `test-runs` (`tests/LeanVMTests/Runs.lean`, run with `lake env .lake/build/bin/test-runs` after `lake build test-runs`), as the gate does. Use `lake build <Module>` to check one module, not `lake env lean`.
- Lake has no job limit, so a cold parallel `lake build` can exceed a 16 GB machine. `python3 -I ../lake-build.py . LeanVM LeanVMTests` runs one `lake build` whose modules, the statement package's included, it admits by their recorded memory, the cores busy (CI uses it; `lake-build.tsv` holds the heavy modules, `--seed` rewrites it). Keep a new module under about 3.5 GB.
- `lake-build.py --dev` is for development only: it builds into `.lake/build-dev` with the kernel skipped (`debug.skipKernelTC`) on `LeanVM` (its dependencies, `Statement` among them, are built as usual), several times faster. Elaboration still checks ordinary proofs, and the kernel still checks the modules that tie a guest function's body or the core data to a template (`stmtsEqb`, `tbStmtsEqb`, or a `decide +kernel` in a module that reads the core IR), so a stale template fails as in the real build; any other false `decide +kernel` passes (`--dev-kernel all` checks those too, and the `kernel_lit` and `win_lit` values, slower; `none` checks nothing), and `#print axioms` does not show it. Never use it for CI, a gate, a push or a claim: those run the build above, kernel included.
- `Statement/LeanVmVerifier.lean` is the readable reference of the verifier. Differential tests compare it with the Rust verifier, `scripts/fuzz-verifier.py` on `tests/fixtures/verifier` (Commands, below; its mutation positions come from the Lean verifier's own traced run, `leanvm-verify --events`), and pin values of the verifier at its pins (`tests/LeanVMTests/Protocol/Verifier/Helpers.lean`, `Compiled.lean`). A protocol change in the Rust verifier fails CI until `Statement/LeanVmVerifier.lean` and the proofs follow; regenerate the fixtures (Commands, below).
- The guest's kernel-checked certificates (each function's in its pack, `Guest/Pack/*/{Bundle,Checked*,Cplw*,Shared*}`, over its own data and its view of its callees; the links to the whole program and what is not in the packs in `Guest/Checked`, `Guest/B2C/Shared`, `Guest/B2C/Cplw`; their data `Guest/Data/`) are written together by `lake exe guest-cert` (`--check` fails when one is stale), the mode walk's (`Guest/Pack/*/{ModeSig,Mode*}`: a long or costly function's in windows, `ModeD*` its data and the snapshots at its cuts, `ModeD*W*` one window each, `ModeL*` their chain; `ModeH` its hints against `Data/AdviceHints.lean`, the advice as data, which `guest-export` writes beside the text and `tests/LeanVMTests/Guest/AdviceData.lean` checks against the text's parse; firewalled by `Guest/Mode/Firewall.lean`) by `python3 -I scripts/mode-cert/gen.py [--check]`, the residuals by family (`Guest/Mode/ResData.lean`, read off those checks) by `python3 -I scripts/mode-cert/res.py [--check]` after it, the hint bridge's prefix checks (`Guest/Bridge/PrefixOk/*`: each function whose hints all run before its first jump, with its hints' cell map; firewalled by `Guest/Bridge/Firewall.lean`) by `python3 -I scripts/bridge-cert/gen.py [--check]`, and the completeness budget's static certificates by `python3 -I scripts/count/gen.py . all`. A certificate module imports only its bases, never B1's, the protocol's or the schemes' proofs (`Guest/B2C/CertFirewall.lean` fails the build otherwise), and a pack's checks no other function's data (`Guest/ViewFirewall.lean`); independent kernel checks that take minutes go in modules of their own.

## Changing the spec

Every spec change reaches the guest, and a change to the guest's bytecode rebuilds nearly all of `lean_vm` (every module reads the whole program). Every kind of change follows one loop, from `formal/lean_vm` unless said otherwise; the recipes below say what each kind adds.

1. **Rust first.** Change the crates (the Rust verifier, the prover and the guest `crates/rec_aggregation/guests/lean_ethereum.py`, as the root AGENTS.md's "Three verifiers" says) and make their tests pass; set `../leanvm-rev` to the commit.
2. **Transcribe** into `Statement/` what the change touched, citing symbols, not line numbers, and keep `statement.tex` in step.
3. **Regenerate**: `scripts/regen-guest.sh --jobs N` writes everything derived from the guest, in order: export, core IR (`guest-core`, then `core-names-modulus` and `vs-at`), `changes`, `verify_tables`' templates (`vt`), certificates, the mode walk's certificates (`mode`), the hint bridge's prefix checks (`bridge`), memory checks, the stacked opening's templates (`whir-data`, `whir-mat-plan`, `whir-queries`), count families, open_stacked's call tables (`whir-tables`), decoder tables. A failed step names what to fix; `--from STEP` resumes there. `--check` writes nothing and compares every generator's output with the tree byte for byte (the Python generators without a check mode of their own through `scripts/check-in-place`), so a hand edit to a generated file, or a generator that no longer reproduces it, fails at once. The `changes` step (`scripts/guest-changes`, against the core IR the export replaced) prints each function whose body changed, was added or was removed, by stable name, with the hand-written modules that state its body (directly or through a definition that reads it) or name it: the proofs to adapt.
4. **Templates.** A changed function's B1 module equates its body with a template (`Fn.body (fn% «name») = template`, by `decide +kernel`, which `--dev` still checks). `lake exe guest-core --show NAME` prints the new body; follow it in the template and its proof. `python3 -I ../lake-build.py . MODULE…` checks the modules `guest-changes` listed under `states its body` alone. An added function needs a B1 module of its own (its meaning, template and proof, as `B1/Sumcheck/Round4.lean` for `sumcheck_round4`) that its callers' proofs use; a removed one's modules go.
5. **Adapt the proofs, kernel skipped**: `python3 -I ../lake-build.py . LeanVM LeanVMTests --dev --keep-going` until it is green; `--keep-going` lists every failure in one run. A template that no longer matches its body fails here; a failed `decide +kernel` that reads no body (a budget) passes unless `--dev-kernel all`, and the gate catches it. `python3 -I ../tools/deps.py cone FILE` says what an edit rebuilds.
6. **Gate**: `./check-all.sh lean vectors` from `formal/` (the real build, kernel included, then the axioms and the Rust comparisons).

**A guest change** (a function's body, a helper added or removed, a loop bound) is the loop as it stands: transcribe nothing unless a constant the proofs mirror changed. Proofs name functions by stable name (`fn% «name»`, `fn_idx% «name»`, `name% «name»`, `Guest/CoreRef.lean`; a loop is `{caller}_loop{k}`), never by index or by the compiler's `__loop{id}`, so a renumbering changes no proof. A guest constant the proofs use (`levelOodGrind` and `queryGrind` in `Guest/B1/Whir/Template.lean`, the `lig*` sizes and caps in `Whir/Config.lean`) is `guest_const% NAME` (`Guest/GuestConst.lean`: the literal `guest-export` wrote as `Data.const_NAME`, the guest's source imported privately), never a hand copy, so the export alone carries a change to it. The guest's changed functions break mostly their own B1 proofs.

**A verifier change** (a check, a transcript message, its order) is `verifyExecution`'s phase in `Statement/LeanVmVerifier.lean`. The proofs about a phase rewrite with its normal form in `LeanVM/Protocol/Verifier/Phases.lean` (its messages and challenges, each run of pure steps between them collapsed into one `liftOption (xOf …)` or `require`, by `phase_nf`), so a change to a phase's checks or returned value is a change to its `xOf` there, and to the cost-compiled copies (`readSizesLite`, `commitStackPure`), whose `_eq` lemmas say where; the bus, the table sumcheck and the Keccak reduction are not in normal form yet. It breaks `LeanVM/Protocol/` (soundness `EndToEnd/Sound`, completeness `EndToEnd/Complete`, the verifier's facts `Verifier/`) and the B1 proofs that follow the phase. Also regenerate the fixtures (`scripts/export-verifier-fixtures-rust.sh tests/fixtures/verifier`) and update the pinned values the tests name (`tests/LeanVMTests/Protocol/Verifier/Helpers.lean`, `Compiled.lean`).

**A protocol parameter** (grinding bits, `queryTable`, folds, stack bounds) is one definition in `Statement/LeanVmVerifier.lean`; the proofs state the rows it enters as expressions in it (`Whir/Params/Check.lean`). A WHIR parameter starts in `crates/pcs/src/whir_config.rs` and `crates/verifier/src/whir.rs` (`print_whir_query_table` prints the query table both verifiers carry), and a change to WHIR's folding regenerates the fold rounds' table: `cargo run --release --manifest-path scripts/whir-fold-table/Cargo.toml -- LeanVM/Protocol/ToArkLib/Whir/AffineCombinerDeployedTable.lean`.

**An ISA change** is `Statement/LeanIsa.lean`; **a scheme change** is `Statement/LeanXmss.lean`, `LeanSphincs.lean` or `LeanDa.lean` with its proof project (`lean_xmss`, `lean_sphincs`, `lean_da`); **a wire change** is `LeanVM/Wire/Encoding.lean`, compared with the Rust by `scripts/wire-diff.py`. Each reaches the guest through its bytecode, and the loop above follows.

## Commands

Run from the project's directory. `./check-all.sh lean` and `./check-all.sh vectors` at the root are the gate, and CI runs the same checks; read `check-all.sh` for every step.

```sh
# any project
lake exe cache get
python3 -I ../lake-build.py .                     # lean_vm: python3 -I ../lake-build.py . LeanVM LeanVMTests
python3 -I ../lake-build.py . LeanVM --dev        # lean_vm, kernel skipped, never a gate

# lean_vm, against this repository's Rust
lake test && lake exe node-vectors
python3 -I scripts/fuzz-verifier.py tests/fixtures/verifier --jobs 4     # after lake build leanvm-verify and cargo build of scripts/rust-verifier-cli
python3 -I scripts/wire-diff.py tests/fixtures/verifier --jobs 8         # after lake build wire-diff and cargo build of scripts/wire-diff
scripts/export-prover-traces-rust.sh /tmp/p && lake exe leanvm-execute /tmp/p/*/                 # the executor against the Rust interpreter
LEANVM_GUEST_DIFF=/tmp/g LEANVM_GUEST_EXEC=/tmp/e cargo test --release --manifest-path scripts/guest-export/Cargo.toml --lib guest_diff -- --ignored && lake exe guest-run --rust /tmp/e [--prove] /tmp/g/*.txt   # the guest from statement and witness, in Lean
scripts/export-prover-traces-rust.sh /tmp/p && python3 -I scripts/prover-diff.py /tmp/p --mutations 40 --jobs 4 --identical --expected tests/fixtures/verifier
scripts/export-verifier-fixtures-rust.sh tests/fixtures/verifier          # after a protocol change
scripts/regen-guest.sh --jobs 24 [--check] [--from STEP]                 # every file derived from the guest, after a change to it
python3 -I ../lake-build.py . LeanVM LeanVMTests --dev --keep-going      # every proof a change breaks, in one run
scripts/guest-export/target/release/guest-export . [--check]             # the guest's data, after a change to the guest or leanvm-rev
cargo run --release --manifest-path scripts/whir-fold-table/Cargo.toml -- LeanVM/Protocol/ToArkLib/Whir/AffineCombinerDeployedTable.lean [--check]   # the fold rounds' certificate, after a change to whir_config.rs
scripts/renumber-chain dump OUT; scripts/renumber-chain apply BEFORE AFTER   # the cost bounds' names, after a change to the cost-compiled chain moves its indices
python3 -I scripts/extractor-cost/cost.py scripts/extractor-cost/params.csv  # the knowledge extractor's cost model, per shape (not a proof)
LEANVM_GUEST_DIFF=/tmp/g cargo test --release --manifest-path scripts/guest-export/Cargo.toml --lib guest_diff -- --ignored && lake exe guest-diff /tmp/g/*.txt

# lean_sphincs: the crates' known answers on the compiled statement
lake exe signature-kat ../../crates/signatures/tests/signatures/ethlib ../../crates/signatures/src/lean_sphincs/known_answer.hex
```

## Tools

- `python3 -I tools/deps.py cone FILE`: what an edit of `FILE`'s interface rebuilds, its CPU time, longest chain and families, by Lake's rule for private imports; `deps.py slow`, `deps.py path`.
- `python3 -I tools/firewall-canary.py`: checks that rule against Lake (the gate runs it); the plan that rests on it is `notes/per-function-cone.md`.
- `python3 -I tools/profile.py FILE`: where a slow file's time goes, by declaration and step; its docstring lists the usual fixes.
- `lake env lean --run ../tools/NeededImports.lean MODULE`: the imports `MODULE` does not need, and the modules to split.
- `lake env lean --run ../tools/Unused.lean ROOT... --prefix P`: declarations under `P` that no root uses; read before deleting.
- `python3 -I tools/escape-scan.py DIR...`: fails on a proof escape outside comments (the gate runs it).
- `python3 -I tools/docnames.py`: names `statement.tex` and the docs cite that no Lean file has.
