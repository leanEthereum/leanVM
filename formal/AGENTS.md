# formal

What is proved is [`statement.tex`](statement.tex), the one document a reviewer reads; this file is for contributors and agents. Each project's root module and its modules' docstrings say how its proof goes.

## The repository

- Six Lake projects, each built in its own directory: `Statement` (the statement: definitions and end statements only), and the proofs, `common`, `lean_vm`, `lean_xmss`, `lean_sphincs` and `lean_da`; the root is no Lean project. `lake build` at the root (`check-all.sh`) is the full gate; `.github/workflows/lean.yml` runs the same checks, a job per project.
- Name a project `lean_*` (or a library `Lean*`) only for a deployed object (leanVM, leanXMSS, leanSPHINCS, LeanDA); infrastructure is named for what it is (`common`, `Statement`).
- This tree is leanVM's `formal/`: `lean_vm` is about the Rust in this repository (`../crates`), at the same commit: the Lean and the Rust are always in sync, so a change to the Rust lands with the formalization's in one PR, and CI (`lean-vm-formalization` in `../.github/workflows/lean.yml`) rebuilds the proofs and checks every transcription against the Rust on every change to `crates/`.
- A citation `crates/<crate>/...` of a prover crate (`lean_vm_core`, `pcs`, `primitives`, `keccak_gkr`, `parallel`) names that crate in either prover tree, `crates/stable_prover/` or `crates/experimental_prover/`, as in the root AGENTS.md; the scripts, which build against one tree, name it in full.
- Generated data (`Statement/Data/`, `lean_vm/LeanVM/Guest/Data/`, `lean_vm/LeanVM/Cost/Decoder/GuestTables.lean`, the decoder tables' chunks and packed layout (`lean_vm/LeanVM/Cost/DecoderSize/`, `lean_vm/LeanVM/Cost/DecoderTablesFirewall.lean`, `lean_vm/LeanVM/Cost/Decoder/GuestLanes.lean`), `lean_vm/tests/LeanVMTests/Spec/NodeVectors.lean`, `lean_vm/tests/LeanVMTests/Guest/{Programs,Manifest}.lean`, the fold rounds' table in `lean_vm/LeanVM/Protocol/ToArkLib/Whir/AffineCombinerDeployedTable.lean`, by `lean_vm/scripts/whir-fold-table`) is regenerated, not edited: by `lean_vm/scripts/guest-export` from leanVM's sources at the pin, by `lake exe guest-core` / `lake exe guest-cert`, or, for the decoder's tables, by `lean_vm/scripts/decoder-tables` from the guest's generated data, and their chunks by `lean_vm/scripts/decoder-table-chunks`; so are the stacked opening's templates (`lean_vm/LeanVM/Guest/B1/Whir/{Data,HelperData,HelperFind}*.lean`, `HelperTables.lean`, `MatPlan.lean`, by `scripts/whir-data` and `scripts/whir-mat-plan`; the query walks and the walk certificates' checks (`Guest/WalkOq*`, `WalkLq*`, `WalkOs*`), the opening's specializations' templates (`B1/Opening/QueriesBody*`, `QueriesPlacedE.lean`, `B1/Bits/QueryWindowsData.lean`, `QueryWindowsBody*.lean`) and the regions marked generated in hand-written files (`QueriesFns.lean`'s cases, the specializations' lists), by `scripts/whir-queries/all.py`, in the stable names of `Guest/CoreRef.lean`; the walks' obligations, `lean_vm/LeanVM/Guest/WalkKnownAll.lean`, by `scripts/walk-known-all`; where `verify_sub`'s obligations sit in its body, `lean_vm/LeanVM/Guest/VsAt.lean`, by `scripts/vs-at`; the numerals of the value names the proofs cite, `lean_vm/LeanVM/Guest/Data/ValNames/`, by `scripts/val-names/gen.py`). The guest's constants are `Guest/Data/Consts.lean`, apart from its functions' bodies (`Guest/Data/Source.lean`), so a module that reads only constants does not rebuild on a body edit. `lean_vm/scripts/regen-guest.sh` runs every guest generator in order. What the generators write whole is not committed (`formal/.gitignore` lists it, and CI fails on a file it writes that is not ignored): run `regen-guest.sh` before building `Statement` or `lean_vm`, after a checkout or a pull that changes the guest (`check-all.sh` and CI run it first). The fold rounds' table, `Programs.lean` and the generated regions of hand-written files stay committed, and so do the generators' inputs: the core route's contracts (`lean_vm/LeanVM/Guest/CoreMode/Sig/`, which `sigc.py` keeps as written), each function's rule files (`lean_vm/scripts/core-mode/fn/`, `lean_vm/LeanVM/Guest/CoreMode/Fn/`) and `lean_vm/scripts/val-names/fnmap.tsv`.
- No `sorry`, `axiom`, `admit`, `native_decide`, `implemented_by` or `unsafe`, and no local overrides of a lakefile's options (one exception: `lake-build.py --dev`, below); every warning is an error, deprecations included. The axiom footprint of every end theorem is Lean's three.
- Builds are heavy: run them on a large machine, after `lake exe cache get`. Cap `lean` and compiled executables with `ulimit -v`, not `lake` (it reserves about 1 GB of address space per job). The scripts run on macOS too, which has neither that cap nor a systemd scope: `lake-build.py`'s memory budget is the only guard there.
- An edit rebuilds what imports it, directly or not (in the module system only when what it exports changes: a statement, an exposed body, a declaration added or removed, its imports; and only through `public import`s: a private `import` stops the rebuild, while a file outside the module system sees everything below it). Keep a slow module, such as kernel-checked certificates, importing only the functions it evaluates and their facts, in modules of their own, never the proofs that use the certificates; `tools/NeededImports.lean` lists a module's needless imports and the modules to split, and `tools/deps.py cone FILE` what an edit of `FILE` rebuilds (Tools, below). Guard such a split with a check in the build, as `lean_vm/LeanVM/Guest/B2C/CertFirewall.lean` does.
- A proof that needs more than the default `maxHeartbeats` is slow for a reason: profile it (`python3 -I tools/profile.py FILE`, which names the costly steps and their usual fixes) before raising the budget, and raise it on that declaration alone (`set_option maxHeartbeats N in`), never on a file. Tactics that try every hypothesis (`tauto`, `contradiction`, `aesop`, `congr`, `decide` on a goal with a large context) run slow where the context holds a kernel check of large data: clear it first (`clear * - h`). A long chain of `++` over lists of constructors (such as `lean_vm/LeanVM/Guest/B1/VerifySub/Template.lean`'s `vsReadsT`) elaborates as one `binop%` tree, slowly: write a new one `List.flatten [a, b, …]`, unless its proofs read the `++` shape (`holdsList_append`).
- Since Lean 4.35 `Fin.foldl`, `Fin.foldr`, `List.ofFn` and `Array.ofFn` are structural, so the elaborator (`isDefEq`, `whnf`, `rfl` after `rw`/`unfold`, `congr`, `decide`, `exact` against an expected type, linters reading a local's type) evaluates concrete Keccak-f, `GF(2^64)` products (CompPoly's `carryLessMul`), large `ofFn` literals and whole protocol runs (`runI`, `shapedI`) where it used to stop: a recursion-depth error or a `whnf` timeout. Never raise `maxRecDepth` or `maxHeartbeats` for it, and making those definitions irreducible only turns the error into a failed unification. Instead keep the elaborator off the heavy term: an algebraic lemma for what it would compute (`addressOfIndex 1 = g` is `pow_one`, not an evaluation), a concrete equation decided by the kernel and rewritten (`rw [show channelSep MemPush.toRaw = g by decide +kernel]`, `decide +kernel` for a closed goal), `congrArg f` or `Finset.sum_congr` instead of `congr`, `dsimp only [d]` to expose both sides before a `refine`, `have h := e; exact h` to elaborate `e` before matching it, `generalize` on a concrete heavy subterm, `with_reducible exact` on the alternatives of a `first`, and arguments given explicitly rather than unified.
- The Rust code (Rust verifier, prover, guests) is test evidence, not proof; a proof claim cites leanVM sources at a named commit.
- `lean_da` builds on Benedikt Wagner's work (his framework for erasure code commitments and its games, from `b-wagn/fv-pq-da`), ported and instantiated with LeanDA: credit him in its files and in every commit that touches it.

## Statement

- `Statement/` is the trusted statement: eighteen files (`statement.tex`, the reviewer's document, lists them in reading order; keep it in step with every change to `Statement/`; of them, a reviewer checks the guest's witness generation, `LeanVmGuestProver.lean`, only as a genuine prover, its completeness proved in `lean_vm/LeanVM/Guest/EndExecFinal.lean`, through `ProverGuest.lean`, which equates it with the proofs' `Guest/Hints.lean`), the generated guest bytecode and the compiler's hints (`Statement/Data/`, their bodies not exposed, for build locality: the values are unchanged, and a module that evaluates them adds `import all Statement.Data.Bytecode` or `AdviceHints`, which `import all` their chunks; such a module evaluates the data by `decide`, `decide +kernel`, `unfold` or `by rfl`, never by `simp` or `rw` with the data's names, whose equation lemma it would export, and a term-mode `rfl` over the data fails), the honest prover the completeness statements name (`Statement/Prover/`, its executable `LeanVM.Prover.prove` and the executor that runs a program on its advice, `LeanVM.Prover.Exec.execute`, fifteen files, generic over the program: a reviewer checks only that it is a genuine prover, its correctness proved in `lean_vm/LeanVM/Prover/`), proved `@[csimp]` lemmas for speed only (`Statement/Fast/`) and the proofs of laws the definitions need (`Statement/Lemmas/`, such as the irreducibility of `E`'s modulus), neither part of what a reviewer reads. It imports only Mathlib, VCVio, CompPoly and its own files, and `import all` only of `Statement.Data` (CI checks it), and every change to it changes what is proved. No file beyond the eighteen without asking. Definitions and end statements only: a proof belongs to the proof projects, unless a definition needs it (a structure's law, a decidability instance).
- Keep the leanVM definitions a faithful transcription of the leanVM sources they cite (Rust and guest items by name, `doc/leanvm` sections), at the commit they name. Cite by name, never by line number: line numbers go stale with every edit to the file they point into.
- Only statements in the random-permutation model are end statements; the random-oracle model and the sponge's indifferentiability are proof steps, in the proof projects.
- Each proof project's root module is its end file: it checks each end theorem against its `Statement` proposition and pins its axioms.
- `lake build` in `Statement/` builds the eighteen files, `Data/`, `Fast/`, `Lemmas/` and `Prover/`; the data's modules are heavy, so build them as CI does, `python3 -I ../lake-build.py .`.

## lean_vm

- Speed comes from proved `@[csimp]` lemmas (`Statement/Fast/`: a `@[csimp]` lemma acts where a definition is compiled, so the statement's own definitions must see them); lemmas about the statement's definitions are in `LeanVM/Facts/`.
- A word of `E` has two limbs (`E.limb : Fin 2 → K`), and a numeral index wraps: `x.limb 2` elaborates and reads limb `0`. Write limbs `0` and `1` only.
- `leanvm-prove` runs the prover recompiled with `E`'s arithmetic on machine words (`LeanVM/Prover/Fast/`: every prover and verifier definition that multiplies in `E` copied, `@[csimp]` by `rfl`). A recursive prover definition is copied by hand there, its text with `mulE` and proved equal by induction; when the prover gains one, the build of `LeanVM.Prover.Fast.Prover` names it.
- `lake build` builds every module under `LeanVM/` (the lakefile's globs), and `LeanVM.lean` pins the end theorems' axioms. `lake test` builds every module under `tests/LeanVMTests/`; a test too slow for the interpreter is a run of the compiled `test-runs` (`tests/LeanVMTests/Runs.lean`, run with `lake env .lake/build/bin/test-runs` after `lake build test-runs`), as the gate does. Use `lake build <Module>` to check one module, not `lake env lean`.
- Lake has no job limit, so a cold parallel `lake build` can exceed a 16 GB machine. `python3 -I ../lake-build.py . LeanVM LeanVMTests` runs one `lake build` whose modules, the statement package's included, it admits by their recorded memory, the cores busy (CI uses it; `lake-build.tsv` holds the heavy modules, `--seed` rewrites it). A module must stay under 7.5 GB (the gate's cap); the generators size their windows to about 6.5 GB (`lean_vm/scripts/windows.py`, with a function's own sizes in its rule file by stable name), and a hand-written module should stay well under that. `lake-build.tsv` is tracked: after deleting or renaming heavy modules, prune their rows (or `--seed` it from a full build), so that `lake-build.py` and `tools/deps.py` read current modules.
- `lake-build.py --dev` is for development only: it builds into `.lake/build-dev` with the kernel skipped (`debug.skipKernelTC`) on `LeanVM` (its dependencies, `Statement` among them, are built as usual), several times faster. Elaboration still checks ordinary proofs, and the kernel still checks the modules that tie a guest function's body or the core data to a template (`stmtsEqb`, `tbStmtsEqb`, or a `decide +kernel` in a module that reads the core IR), so a stale template fails as in the real build, and every module that uses the `vc` tactic; any other false `decide +kernel` passes (`--dev-kernel all` checks those too, and the `kernel_lit` and `win_lit` values, slower; `none` checks nothing), and `#print axioms` does not show it. Never use it for CI, a gate, a push or a claim: those run the build above, kernel included.
- Outside CI, `lake-build.py` turns on Lake's local artifact cache (`LAKE_ARTIFACT_CACHE`, `LAKE_RESTORE_ARTIFACTS`): clones and branches on one machine share build products, keyed by the trace's hash (options included, so a `--dev` product never satisfies the real build). The cache sits in the toolchain's directory, or in `LAKE_CACHE_DIR`, and is never evicted: delete it to reclaim space.
- `Statement/LeanVmVerifier.lean` is the readable reference of the verifier. Differential tests compare it with the Rust verifier, `scripts/fuzz-verifier.py` on `tests/fixtures/verifier` (Commands, below; its mutation positions come from the Lean verifier's own traced run, `leanvm-verify --events`), and pin values of the verifier at its pins (`tests/LeanVMTests/Protocol/Verifier/Helpers.lean`, `Compiled.lean`). A protocol change in the Rust verifier fails CI until `Statement/LeanVmVerifier.lean` and the proofs follow. The fixtures are not committed: `scripts/export-verifier-fixtures-rust.sh` writes them from this tree's Rust prover before the differential tests (Commands, below).
- The guest's kernel-checked certificates (each function's in its pack, `Guest/Pack/*/{Bundle,Checked*,Cplw*,Shared*}`, over its own data and its view of its callees; the links to the whole program and what is not in the packs in `Guest/Checked`, `Guest/B2C/Shared`, `Guest/B2C/Cplw`; their data `Guest/Data/`) are written together by `lake exe guest-cert` (`--check` fails when one is stale); the core route's per-function data and checks (`formal/notes/core-mode.md`: signatures `Guest/CoreMode/Sig/*` and glue `Guest/CoreMode/Glue*/*`, heap certificates, pairings and route data `Guest/CoreMode/Gen/*`, `Guest/CoreMode/GenW*/*`, frame walks `Guest/CoreMode/Pack/*/Frame*`, certificates `Guest/CoreMode/Gen/*/Cert`; the registries of each function's own routing facts and families, `Guest/CoreMode/Gen/Fn*`, from its own files `Guest/CoreMode/Fn/<f>/` by `fnreg.py`, beside which sit the proofs of its own facts and families, which no shared module imports (a shared module reads them through the registries); a contract given by hand in the function's rule file, `scripts/core-mode/fn/<f>.py`'s `CONTRACTS`, with `sigseed.py`'s literals) by the generators of `scripts/core-mode/` in the `core-mode` step (each with `--check`, `frame_gen.py` through `scripts/check-in-place`; `scripts/check-fresh` runs them on a copy of the tree without the files they write, which they must write again, each through the shared `scripts/genfiles.py`), the hint bridge's checks (`Guest/Bridge/{Align,AlignCtx,ProgAl,JumpCells,PairChk,WitChk,AllocChk}/*`) by `python3 -I scripts/bridge-cert/<check>.py [--check]`, and the completeness budget's static certificates by `python3 -I scripts/count/gen.py . all`. The program's certificates (`Guest/B2C/Cplw`, `Guest/B2C/Shared`, `Guest/Checked`, `Guest/Memory/GuestCnt`) import only their bases (`B2C.Cpl`, `B2C.ShareStatic`, `CheckWinC`, `Memory.Family`), never B1's, the protocol's or the schemes' proofs (`Guest/B2C/CertFirewall.lean` fails the build otherwise; the core route's generated certificates are not guarded by it, and reach B1's definitions through `CoreMode/CoreRes.lean`), and a pack's checks no other function's data (`Guest/ViewFirewall.lean`); independent kernel checks that take minutes go in modules of their own.

## Changing the spec

Every spec change reaches the guest, and a change to the guest's bytecode rebuilds what reads it: the generated per-function data and checks, which cite absolute positions, the modules that evaluate the bytecode, and the proofs about the changed functions. Every kind of change follows one loop, from `formal/lean_vm` unless said otherwise; the recipes below say what each kind adds.

1. **Rust first.** Change the crates (the Rust verifier, the prover and the guest `guests/lean_ethereum.py`, as the root AGENTS.md's "Three verifiers" says) and make their tests pass.
2. **Transcribe** into `Statement/` what the change touched, citing symbols, not line numbers, and keep `statement.tex` in step.
3. **Regenerate**: `scripts/regen-guest.sh --jobs N` writes everything derived from the guest, in order, by the step names `--from` takes: `export`, the core IR (`core`: `guest-core`, then `core-names-modulus`, `vs-at` and the value names the proofs cite, `val-names/gen.py`), `changes`, `verify_tables`' templates (`vt`), the certificates (`cert`), the hint bridge's checks (`bridge`), the core route's data and checks (`core-mode`), the memory checks (`memory`), the callers' facts carried down (`res`), the stacked opening's templates (`whir`: `whir-data`, `whir-mat-plan`, `walk-known-all`, `whir-queries`), the count families (`count`), open_stacked's call tables (`tables`: `whir-tables.lean`), the decoder tables (`decoder`). A failed step names what to fix; `--from STEP` resumes there. `--check` writes nothing and compares every generator's output with the tree byte for byte (the Python generators without a check mode of their own through `scripts/check-in-place`), so a hand edit to a generated file, or a generator that no longer reproduces it, fails at once. The `changes` step (`scripts/guest-changes`, against the core IR the export replaced) prints each function whose body changed, was added or was removed, by stable name, with the hand-written modules that state its body (directly or through a definition that reads it) or name it: the proofs to adapt.
4. **Templates.** A changed function's B1 module equates its body with a template (`Fn.body (fn% «name») = template`, by `decide +kernel`, which `--dev` still checks), proves its meaning from the condition the `vc` tactic computes from the body (`LeanVM/Guest/VcTactic.lean`; `--dev` keeps the kernel on such modules), or proves it from its reference function (`Guest/Ref`, as `verify_merkle_cap` in `B1/Merkle/CapRef.lean`). `lake exe guest-core --show NAME` prints the new body; follow it in the template and its proof, or in the rules and rewriting after `vc`. A function proved from its reference function has no template: its links (`Linked`, by `decide +kernel`) fail instead; the fix is in the reference function where the source changed, in the check (`Ref/Link.lean`) where the lowering changed what it observes, and in the meaning proof where the meaning changed. `python3 -I ../lake-build.py . MODULE…` checks the modules `guest-changes` listed under `states its body` alone. An added function needs a B1 module of its own (its meaning and proof, as `B1/Sumcheck/Round4.lean` for `sumcheck_round4`, by `vc`) that its callers' proofs use; a removed one's modules go.
5. **Adapt the proofs, kernel skipped**: `python3 -I ../lake-build.py . LeanVM LeanVMTests --dev --keep-going` until it is green; `--keep-going` lists every failure in one run. A template that no longer matches its body fails here; a failed `decide +kernel` that reads no body (a budget) passes unless `--dev-kernel all`, and the gate catches it. `python3 -I ../tools/deps.py cone FILE` says what an edit rebuilds.
6. **Gate**: `./check-all.sh lean vectors` from `formal/` (the real build, kernel included, then the axioms and the Rust comparisons), and `python3 -I scripts/check-fresh` from `lean_vm` after a regeneration (the core route's, the bridge's and `res`' generators write their files again from none). `regen-guest.sh --check` includes `val-names/gen.py --check`: a value name the proofs cite that the core IR no longer has fails there.

**A guest change** (a function's body, a helper added or removed, a loop bound) is the loop as it stands: transcribe nothing unless a constant the proofs mirror changed. Proofs name functions by stable name (`fn% «name»`, `fn_idx% «name»`, `name% «name»`, `Guest/CoreRef.lean`; a loop is `{caller}_loop{k}`), never by index or by the compiler's name for a loop (`__loop{k}_{caller}`), so a renumbering changes no proof (a renumbering only: a positional name, an expansion path, `@k` or `~k`, can shift when an edit inserts code before it, which costs a diagnostic, never soundness, as the kernel still checks the citing proof; and an edit to an inlined helper is an edit to every function that inlines it, `notes/core-mode.md`). A core value or a top-level statement is named likewise, `val% «f» "name"` and `pos% «f» "name"` (`Guest/ValRef.lean`: the zkDSL variable the value is first bound to, `g_squares`, `acc@2`, a temporary `acc~1`, else its expansion path, as `guest-core --names` lists them; `valf% «f» "name"` across the specializations `f__L…`; `pos%` also by the statement's first value's source name, or `ret` for the final `ret`; `span% «f» "a" "b"`, the number of statements from `a`'s to `b`'s, a slice's length), never `.n 62094` or `drop 1358`; `python3 -I scripts/val-names/rewrite.py [--write] FILE…` rewrites the literals it can name for certain and flags the rest; a file or declaration whose function its source does not name, and a list whose positions are a body's (`align vtPre verify_tables`), is a person's decision in `scripts/val-names/fnmap.tsv`. A guest constant the proofs use (`levelOodGrind` and `queryGrind` in `Guest/B1/Whir/Template.lean`, the `lig*` sizes and caps in `Whir/Config.lean`) is `guest_const% NAME` (`Guest/GuestConst.lean`: the literal `guest-export` wrote as `Data.const_NAME`, the guest's source imported privately), never a hand copy, so the export alone carries a change to it; likewise a size one function's proofs define and another's restate is `lit% c` (`Guest/LitRef.lean`: the literal the definition `c` evaluates to, as `main`'s proofs read `exponent_tables`' `B1.expTabN`), and a rule file reads such a definition with `fnrules.lean_def_at`. The guest's changed functions break mostly their own B1 proofs; on the core route an edit touches only the edited functions' own hand files (their rule files, their contracts when their frame layout changed, a callee's words interface when its loops change, and their budget modules: the proofs about a function's body that count its callees, such as `main`'s `Budget/MainCount`, `Instrs`, `Final` or `verify_sub`'s `Budget/VsCount`; each function's rule file lists its own files in `OWN`, `notes/core-mode.md`), and the few shared files and generators that name a function (`notes/core-mode.md`'s exceptions: the root `main`, a caller's budget modules that name its callees, the claim lists' links and cells, `CarryDefs`' carried parameters, the whole-program checks' ranges, the inlined helpers).

A guest change reaches the trusted statement in one number, and `lean_vm`'s guest decoder prices in a few more, each checked by the build:
- **The decoder's size bound**, `guestWitnessDecoderSizeBound` (`Statement/LeanVmGuest.lean`): the compiled decoder's size plus a slack of `430`. The decoder holds the guest's frame-cell table, packed four cells to a number, the functions grouped by decreasing number of cells and each group's row as long as its longest function's, and the guest's other per-function tables; so a function added or removed, or a longest function in a group that grows, changes the size. `Cost/DecoderSpec.lean`'s `decoderProgram_size_le` fails when the size passes the bound (`LeanVMTests/Cost/DecoderSize.lean` evaluates it). The fix is a statement change, asked for first: the new bound is the measured size, the right side of `decoderProgram_size_le_measured` (`Cost/DecoderSize.lean`) evaluated, plus `430`, written in `LeanVmGuest.lean` and in `statement.tex`'s decoder size paragraph (its sizes too).
- **The guest decoder's prices**, `Cost/Prices.lean`: `guestDecoderWitnessPriceAt` and `guestDecoderFrameLookupCountAt` (the witness read at counts at most `M`: the frames the decoder looks up, `verify_sig_lean_sphincs`' and its `sp_wots`', `main_loop2`'s iteration on its arguments, the children's cursors), `guestDecoderPreconditionPrice`, and `guestDecoderPrice` at the program's `ℓ = 19` (its bytecode below `2^19` words). A change to a frame the decoder reads, to an argument count, or to the bytecode's size past `2^19` fails `Cost/Bounds/Guest/Budget.lean`: `topConst_eq_at` (by `ring` after unfolding; the new constants are the failing goal's normal form, written in `Prices.lean`), then `guestDecoderPrice_le_budget`, which must still hold below the statement's `guestWitnessDecoderBudget` (a statement change, asked for first, when it does not).

**A verifier change** (a check, a transcript message, its order) is `verifyExecution`'s phase in `Statement/LeanVmVerifier.lean`. The proofs about a phase rewrite with its normal form in `LeanVM/Protocol/Verifier/Phases.lean` (its messages and challenges, each run of pure steps between them collapsed into one `liftOption (xOf …)` or `require`, by `phase_nf`), so a change to a phase's checks or returned value is a change to its `xOf` there, and to the cost-compiled copies (`readSizesLite`, `commitStackPure`), whose `_eq` lemmas say where; the bus, the table sumcheck and the Keccak reduction are not in normal form yet. It breaks `LeanVM/Protocol/` (soundness `EndToEnd/Sound`, completeness `EndToEnd/Complete`, the verifier's facts `Verifier/`) and the B1 proofs that follow the phase. Also update the pinned values the tests name (`tests/LeanVMTests/Protocol/Verifier/Helpers.lean`, `Compiled.lean`).

**A protocol parameter** (grinding bits, `queryTable`, folds, stack bounds) is one definition in `Statement/LeanVmVerifier.lean`; the proofs state the rows it enters as expressions in it (`Whir/Params/Check.lean`). A WHIR parameter starts in `crates/experimental_prover/pcs/src/whir_config.rs` (the security search; the stable prover reads the verifier's table) and `crates/verifier/src/whir.rs` (the query table both verifiers carry, which `print_whir_query_table`, in `crates/experimental_prover/lean_vm_core/tests/verifiers/whir_query_table.rs`, prints), and a change to WHIR's folding regenerates the fold rounds' table: `cargo run --release --manifest-path scripts/whir-fold-table/Cargo.toml -- LeanVM/Protocol/ToArkLib/Whir/AffineCombinerDeployedTable.lean`.

**An ISA change** is `Statement/LeanIsa.lean`; **a scheme change** is `Statement/LeanXmss.lean`, `LeanSphincs.lean` or `LeanDa.lean` with its proof project (`lean_xmss`, `lean_sphincs`, `lean_da`); **a wire change** is `LeanVM/Wire/Encoding.lean`, compared with the Rust by `scripts/wire-diff.py`. Each reaches the guest through its bytecode, and the loop above follows.

## Commands

Run from the project's directory. `./check-all.sh lean` and `./check-all.sh vectors` at the root are the gate, and CI runs the same checks; read `check-all.sh` for every step.


## Tools

- `python3 -I tools/deps.py cone FILE`: what an edit of `FILE`'s interface rebuilds, its CPU time, longest chain and families, by Lake's rule for private imports; `deps.py slow`, `deps.py path`.
- `python3 -I tools/firewall-canary.py`: checks that rule against Lake (the gate runs it); the plan that rests on it is `notes/per-function-cone.md`.
- `python3 -I tools/profile.py FILE`: where a slow file's time goes, by declaration and step; its docstring lists the usual fixes.
- `lake env lean --run ../tools/NeededImports.lean MODULE`: the imports `MODULE` does not need, and the modules to split.
- `lake env lean --run ../tools/Unused.lean ROOT... --prefix P`: declarations under `P` that no root uses; read before deleting.
- `python3 -I tools/escape-scan.py DIR...`: fails on a proof escape outside comments (the gate runs it).
- `python3 -I tools/docnames.py`: names `statement.tex` and the docs cite that no Lean file has.
