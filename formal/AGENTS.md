# formal

What is proved is [`statement.tex`](statement.tex), the one document a reviewer reads; this file is for contributors and agents. Each project's root module and its modules' docstrings say how its proof goes.

## The repository

- Six Lake projects, each built in its own directory: `Statement` (the statement: definitions and end statements only), and the proofs, `common`, `lean_vm`, `lean_xmss`, `lean_sphincs` and `lean_da`; the root is no Lean project. `lake build` at the root (`check-all.sh`) is the full gate; `.github/workflows/lean.yml` runs the same checks, a job per project.
- Name a project `lean_*` (or a library `Lean*`) only for a deployed object (leanVM, leanXMSS, leanSPHINCS, LeanDA); infrastructure is named for what it is (`common`, `Statement`).
- This tree is leanVM's `formal/`: `lean_vm` is about the Rust in this repository (`../crates`), at the same commit: the Lean and the Rust are always in sync, so a change to the Rust lands with the formalization's in one PR, and CI (`lean-vm-formalization` in `../.github/workflows/lean.yml`) rebuilds the proofs and checks every transcription against the Rust on every change to `crates/`.
- A citation `crates/<crate>/...` of a prover crate (`lean_vm_core`, `pcs`, `primitives`, `keccak_gkr`, `parallel`) names that crate in either prover tree, `crates/stable_prover/` or `crates/experimental_prover/`, as in the root AGENTS.md; the scripts, which build against one tree, name it in full.
- Generated data (`Statement/Data/`, `lean_vm/LeanVM/Guest/Data/`, `lean_vm/LeanVM/Guest/Deployed/Data.lean`, `lean_vm/LeanVM/Cost/Decoder/{GuestTables,GuestPlaces}.lean`, the decoder tables' chunks (`lean_vm/LeanVM/Cost/DecoderSize/`, `lean_vm/LeanVM/Cost/DecoderTablesFirewall.lean`), `lean_vm/tests/LeanVMTests/Spec/NodeVectors.lean`, `lean_vm/tests/LeanVMTests/Guest/{Programs,Manifest}.lean`, the fold rounds' table in `lean_vm/LeanVM/Protocol/ToArkLib/Whir/AffineCombinerDeployedTable.lean`, by `lean_vm/scripts/whir-fold-table`) is regenerated, not edited: by `lean_vm/scripts/guest-export` from leanVM's sources at the pin, by `lake exe guest-core`, the back end's tables by `lake exe guest-tables`, or, for the decoder's tables, by `lean_vm/scripts/decoder-tables` from the guest's generated data and the back end's places, and their chunks by `lean_vm/scripts/decoder-table-chunks`; so are the stacked opening's templates (`lean_vm/LeanVM/Guest/B1/Whir/{Data,HelperData,HelperFind}*.lean`, `HelperTables.lean`, `MatPlan.lean`, by `scripts/whir-data` and `scripts/whir-mat-plan`; the opening's specializations' templates (`B1/Opening/WalkBody*`, `QueriesBody*`, `WalkFns.lean`, `QueriesPlacedE.lean`, `B1/Bits/QueryWindowsData.lean`, `QueryWindowsBody*.lean`) and the regions marked generated in hand-written files (`QueriesFns.lean`'s cases, the specializations' lists), by `scripts/whir-queries/all.py`, in the stable names of `Guest/CoreRef.lean`); so is the compiled guest the Rust prover loads, `guests/lean_ethereum.compiled`, by `lean_vm/scripts/guest-artifact`; so are the back end's soundness obligations' guest tables and evaluation runs (`lean_vm/LeanVM/Guest/Backend/Sound/Obl/GuestXTab.lean`, `Obl/Eval/`, and the declarations `xTab` of `Obl/GuestX.lean`, `guestXIdx` and `vsIdx` of `Obl/GuestTab.lean`), by `lake exe guest-oblgen`, which fails on a function the hand-written facts name by stable name and the guest no longer has. `lean_vm/scripts/regen-guest.sh` runs every guest generator in order, the compiled guest first, which `guest-export` then reads as the statement's program. What the generators write whole is not committed (`formal/.gitignore` lists it, and CI fails on a file it writes that is not ignored): run `regen-guest.sh` before building `Statement` or `lean_vm`, after a checkout or a pull that changes the guest (`check-all.sh` and CI run it first). The fold rounds' table, `Programs.lean` and the generated regions of hand-written files stay committed.
- No `sorry`, `axiom`, `admit`, `native_decide`, `implemented_by` or `unsafe`, and no local overrides of a lakefile's options (one exception: `lake-build.py --dev`, below); every warning is an error, deprecations included. The axiom footprint of every end theorem is Lean's three.
- Builds are heavy: run them on a large machine, after `lake exe cache get`. Cap `lean` and compiled executables with `ulimit -v`, not `lake` (it reserves about 1 GB of address space per job).
- An edit rebuilds what imports it, directly or not (in the module system only when what it exports changes: a statement, an exposed body, a declaration added or removed, its imports; and only through `public import`s: a private `import` stops the rebuild, while a file outside the module system sees everything below it). Keep a slow module, such as a kernel check of generated data, importing only the functions it evaluates and their facts, in modules of their own, never the proofs that use the check; `tools/NeededImports.lean` lists a module's needless imports and the modules to split, and `tools/deps.py cone FILE` what an edit of `FILE` rebuilds (Tools, below). Guard such a split with a check in the build, as `lean_vm/LeanVM/Guest/Fast/Firewall.lean` does.
- A proof that needs more than the default `maxHeartbeats` is slow for a reason: profile it (`python3 -I tools/profile.py FILE`, which names the costly steps and their usual fixes) before raising the budget, and raise it on that declaration alone (`set_option maxHeartbeats N in`), never on a file. Tactics that try every hypothesis (`tauto`, `contradiction`, `aesop`, `congr`, `decide` on a goal with a large context) run slow where the context holds a kernel check of large data: clear it first (`clear * - h`). A long chain of `++` over lists of constructors elaborates as one `binop%` tree, slowly (half a minute for `lean_vm/LeanVM/Guest/B1/Gkr/Layer.lean`'s `lyBody`): write a new one `List.flatten [a, b, …]`, unless its proofs read the `++` shape (`holdsList_append`).
- Since Lean 4.35 `Fin.foldl`, `Fin.foldr`, `List.ofFn` and `Array.ofFn` are structural, so the elaborator (`isDefEq`, `whnf`, `rfl` after `rw`/`unfold`, `congr`, `decide`, `exact` against an expected type, linters reading a local's type) evaluates concrete Keccak-f, `GF(2^64)` products (CompPoly's `carryLessMul`), large `ofFn` literals and whole protocol runs (`runI`, `shapedI`) where it used to stop: a recursion-depth error or a `whnf` timeout. Never raise `maxRecDepth` or `maxHeartbeats` for it, and making those definitions irreducible only turns the error into a failed unification. Instead keep the elaborator off the heavy term: an algebraic lemma for what it would compute (`addressOfIndex 1 = g` is `pow_one`, not an evaluation), a concrete equation decided by the kernel and rewritten (`rw [show channelSep MemPush.toRaw = g by decide +kernel]`, `decide +kernel` for a closed goal), `congrArg f` or `Finset.sum_congr` instead of `congr`, `dsimp only [d]` to expose both sides before a `refine`, `have h := e; exact h` to elaborate `e` before matching it, `generalize` on a concrete heavy subterm, `with_reducible exact` on the alternatives of a `first`, and arguments given explicitly rather than unified.
- The Rust code (Rust verifier, prover, guests) is test evidence, not proof; a proof claim cites leanVM sources at a named commit.
- `lean_da` is Benedikt Wagner's work (framework, theorems and proofs, from `b-wagn/fv-pq-da`), ported and instantiated with LeanDA: credit him in its files and in every commit that touches it.

## Statement

- `Statement/` is the trusted statement: seventeen files (`statement.tex`, the reviewer's document, lists them in reading order; keep it in step with every change to `Statement/`), the generated guest bytecode (`Statement/Data/`), the honest prover the completeness statements name (`Statement/Prover/`, its executable `LeanVM.Prover.prove`, fourteen files: a reviewer checks only that it is a genuine prover, its correctness proved in `lean_vm/LeanVM/Prover/`), and proved `@[csimp]` lemmas for speed only (`Statement/Fast/`, not part of what a reviewer reads). It imports only Mathlib, VCVio, CompPoly and its own files (CI checks it), and every change to it changes what is proved. No file beyond the seventeen without asking. Definitions and end statements only: a proof belongs to the proof projects, unless a definition needs it (a structure's law, a decidability instance).
- Keep the leanVM definitions a faithful transcription of the leanVM sources they cite (Rust and guest items by name, `doc/leanvm` sections), at the commit they name. Cite by name, never by line number: line numbers go stale with every edit to the file they point into.
- Only statements in the random-permutation model are end statements; the random-oracle model and the sponge's indifferentiability are proof steps, in the proof projects.
- Each proof project's root module is its end file: it checks each end theorem against its `Statement` proposition and pins its axioms.
- `lake build` in `Statement/` builds the seventeen files, `Data/`, `Fast/` and `Prover/`; the data's modules are heavy, so build them as CI does, `python3 -I ../lake-build.py .`.

## lean_vm

- Speed comes from proved `@[csimp]` lemmas (`Statement/Fast/`: a `@[csimp]` lemma acts where a definition is compiled, so the statement's own definitions must see them); lemmas about the statement's definitions are in `LeanVM/Facts/`.
- A word of `E` has two limbs (`E.limb : Fin 2 → K`), and a numeral index wraps: `x.limb 2` elaborates and reads limb `0`. Write limbs `0` and `1` only.
- `leanvm-prove` runs the prover recompiled with `E`'s arithmetic on machine words (`LeanVM/Prover/Fast/`: every prover and verifier definition that multiplies in `E` copied, `@[csimp]` by `rfl`). A recursive prover definition is copied by hand there, its text with `mulE` and proved equal by induction; when the prover gains one, the build of `LeanVM.Prover.Fast.Prover` names it.
- `lake build` builds every module under `LeanVM/` (the lakefile's globs), and `LeanVM.lean` pins the end theorems' axioms. `lake test` builds every module under `tests/LeanVMTests/`; a test too slow for the interpreter is a run of the compiled `test-runs` (`tests/LeanVMTests/Runs.lean`, run with `lake env .lake/build/bin/test-runs` after `lake build test-runs`), as the gate does. Use `lake build <Module>` to check one module, not `lake env lean`.
- Lake has no job limit, so a cold parallel `lake build` can exceed a 16 GB machine. `python3 -I ../lake-build.py . LeanVM LeanVMTests` runs one `lake build` whose modules, the statement package's included, it admits by their recorded memory, the cores busy (CI uses it; `lake-build.tsv` holds the heavy modules, `--seed` rewrites it). Keep a new module under about 3.5 GB.
- `lake-build.py --dev` is for development only: it builds into `.lake/build-dev` with the kernel skipped (`debug.skipKernelTC`) on `LeanVM` (its dependencies, `Statement` among them, are built as usual), several times faster. Elaboration still checks ordinary proofs, and the kernel still checks the modules that tie a guest function's body or the core data to a template (`stmtsEqb`, `tbStmtsEqb`, or a `decide +kernel` in a module that reads the core IR), so a stale template fails as in the real build; any other false `decide +kernel` passes (`--dev-kernel all` checks those too, and the `kernel_lit` and `win_lit` values, slower; `none` checks nothing), and `#print axioms` does not show it. Never use it for CI, a gate, a push or a claim: those run the build above, kernel included.
- `Statement/LeanVmVerifier.lean` is the readable reference of the verifier. Differential tests compare it with the Rust verifier, `scripts/fuzz-verifier.py` on `tests/fixtures/verifier` (Commands, below; its mutation positions come from the Lean verifier's own traced run, `leanvm-verify --events`), and pin values of the verifier at its pins (`tests/LeanVMTests/Protocol/Verifier/Helpers.lean`, `Compiled.lean`). A protocol change in the Rust verifier fails CI until `Statement/LeanVmVerifier.lean` and the proofs follow. The fixtures are not committed: `scripts/export-verifier-fixtures-rust.sh` writes them from this tree's Rust prover before the differential tests (Commands, below).
- The compiler's back end in Lean (`LeanVM/Guest/Backend/`) compiles the guest the Rust prover proves, and the end theorems are proved through it (`Backend/Guest/End.lean`, `Backend/Guest/Cpl/`): `Backend.compile` is `Expand` then placement, emission and assembly, and `lake exe guest-backend check` compares what it compiles of the guest with `Statement/Data/`, instruction for instruction. `lake exe guest-artifact` writes the compiled guest, with its Fiat-Shamir IV and the source line of every instruction, to `guests/lean_ethereum.compiled`, which `crates/aggregation` loads; the guest's placeholders depend on its size, so `scripts/guest-artifact` iterates the source's export (`guest-export --source K`) and the compilation to the fixed point. The lines are debug data from a pass of their own, `Backend/Lines.lean` (the traced expansion records each statement's line, and a walk that calls placement's own steps gives each placed statement the line of its event), so placement and emission, and what is proved of them, carry none; `Lines.compileLines` fails when its walk places a program otherwise than `Backend.compile`. The Rust compiler is a differential test of it (`aggregation`'s `the_artefact_is_the_rust_compilers_guest`, source lines included). `Backend/ExpandTrace.lean` is generated from `Guest/Expand.lean` by `scripts/expand-trace` (`--check` fails when it is stale), so an edit to `Expand.lean` regenerates it. `scripts/backend-diff` runs every check, the comparison with the Rust compiler included. `Backend/Sound/` proves the back end's own passes sound against `Statement/LeanIsa.lean` and the located core semantics (`Backend/Sound.lean` lists the theorems and pins their axioms), on every trace (`lake exe guest-backend coverage` says what it covers of the guest), and an edit to `Place.lean`, `Emit.lean` or `Assemble.lean` must keep both `Backend.Sound` building and `guest-backend check` passing. `Backend/Guest/` is the guest as the back end's input, `coreProgram`'s functions with their traces (`World.lean` states the guest's theorem); its data, `Traced.lean` and `Trace/`, is written by `lake exe guest-traced` (`--check` fails when it is stale, then compiles that input natively and compares it with `Statement/Data/`), so a change to the guest or to the trace regenerates it after `guest-core`. `Backend/Guest/Compiled.lean` proves `GuestCompiles` from the kernel's checks of the guest's compilation function by function, `Backend/Guest/Piece/` (a function too large for one piece checked in parts, its walk cut between top-level statements and between the arms of a `match`, its states at the cuts written out by `state_lit`, `Piece/C*.lean`), all written by `lake exe guest-pieces` after `guest-traced` (`--check` fails when one is stale, and evaluates every check natively first; `lake exe guest-pieces test` writes the same for a test program, `tests/LeanVMTests/Guest/BackendPieces.lean`); the piece modules are heavy, so build them through `lake-build.py`.
- The completeness budget's static certificates (counts and words over the core IR, `Memory/GuestWords*`, `Memory/GuestCnt*`, `Count/`) are written by `python3 -I scripts/count/gen.py . all`; independent kernel checks that take minutes go in modules of their own.

## Changing the spec

Every spec change reaches the guest, and a change to the guest's bytecode rebuilds nearly all of `lean_vm` (every module reads the whole program). Every kind of change follows one loop, from `formal/lean_vm` unless said otherwise; the recipes below say what each kind adds.

1. **Rust first.** Change the crates (the Rust verifier, the prover and the guest `guests/lean_ethereum.py`, as the root AGENTS.md's "Three verifiers" says) and make their tests pass.
2. **Transcribe** into `Statement/` what the change touched, citing symbols, not line numbers, and keep `statement.tex` in step.
3. **Regenerate**: `scripts/regen-guest.sh --jobs N` writes everything derived from the guest, in order: export, core IR (`guest-core`, then `core-names-modulus`), `changes`, `verify_tables`' templates (`vt`), the back end's tables (`guest-tables`, step `deployed`), memory checks, the stacked opening's templates (`whir-data`, `whir-mat-plan`, `whir-queries`), count families, open_stacked's call tables (`whir-tables`), decoder tables, the back end's obligations' tables and evaluation runs (`guest-oblgen`, step `backend`). A failed step names what to fix; `--from STEP` resumes there. `--check` writes nothing and compares every generator's output with the tree byte for byte (the Python generators without a check mode of their own through `scripts/check-in-place`), so a hand edit to a generated file, or a generator that no longer reproduces it, fails at once. The `changes` step (`scripts/guest-changes`, against the core IR the export replaced) prints each function whose body changed, was added or was removed, by stable name, with the hand-written modules that state its body (directly or through a definition that reads it) or name it: the proofs to adapt.
4. **Templates.** A changed function's B1 module equates its body with a template (`Fn.body (fn% «name») = template`, by `decide +kernel`, which `--dev` still checks). `lake exe guest-core --show NAME` prints the new body; follow it in the template and its proof. `python3 -I ../lake-build.py . MODULE…` checks the modules `guest-changes` listed under `states its body` alone. An added function needs a B1 module of its own (its meaning, template and proof, as `B1/Sumcheck/Round4.lean` for `sumcheck_round4`) that its callers' proofs use; a removed one's modules go.
5. **Adapt the proofs, kernel skipped**: `python3 -I ../lake-build.py . LeanVM LeanVMTests --dev --keep-going` until it is green; `--keep-going` lists every failure in one run. A template that no longer matches its body fails here; a failed `decide +kernel` that reads no body (a budget) passes unless `--dev-kernel all`, and the gate catches it. `python3 -I ../tools/deps.py cone FILE` says what an edit rebuilds.
6. **Gate**: `./check-all.sh lean vectors` from `formal/` (the real build, kernel included, then the axioms and the Rust comparisons).

**A guest change** (a function's body, a helper added or removed, a loop bound) is the loop as it stands: transcribe nothing unless a constant the proofs mirror changed. Proofs name functions by stable name (`fn% «name»`, `fn_idx% «name»`, `name% «name»`, `Guest/CoreRef.lean`; a loop is `{caller}_loop{k}`), never by index or by the compiler's `__loop{id}`, so a renumbering changes no proof. A guest constant the proofs use (`levelOodGrind` and `queryGrind` in `Guest/B1/Whir/Template.lean`, the `lig*` sizes and caps in `Whir/Config.lean`) is `guest_const% NAME` (`Guest/GuestConst.lean`: the literal `guest-export` wrote as `Data.const_NAME`, the guest's source imported privately), never a hand copy, so the export alone carries a change to it. The guest's changed functions break mostly their own B1 proofs.

**A verifier change** (a check, a transcript message, its order) is `verifyExecution`'s phase in `Statement/LeanVmVerifier.lean`. The proofs about a phase rewrite with its normal form in `LeanVM/Protocol/Verifier/Phases.lean` (its messages and challenges, each run of pure steps between them collapsed into one `liftOption (xOf …)` or `require`, by `phase_nf`), so a change to a phase's checks or returned value is a change to its `xOf` there, and to the cost-compiled copies (`readSizesLite`, `commitStackPure`), whose `_eq` lemmas say where; the bus, the table sumcheck and the Keccak reduction are not in normal form yet. It breaks `LeanVM/Protocol/` (soundness `EndToEnd/Sound`, completeness `EndToEnd/Complete`, the verifier's facts `Verifier/`) and the B1 proofs that follow the phase. Also update the pinned values the tests name (`tests/LeanVMTests/Protocol/Verifier/Helpers.lean`, `Compiled.lean`).

**A protocol parameter** (grinding bits, `queryTable`, folds, stack bounds) is one definition in `Statement/LeanVmVerifier.lean`; the proofs state the rows it enters as expressions in it (`Whir/Params/Check.lean`). A WHIR parameter starts in `crates/experimental_prover/pcs/src/whir_config.rs` (the security search; the stable prover reads the verifier's table) and `crates/verifier/src/whir.rs` (the query table both verifiers carry, which `print_whir_query_table`, in `crates/experimental_prover/lean_vm_core/tests/verifiers/whir_query_table.rs`, prints), and a change to WHIR's folding regenerates the fold rounds' table: `cargo run --release --manifest-path scripts/whir-fold-table/Cargo.toml -- LeanVM/Protocol/ToArkLib/Whir/AffineCombinerDeployedTable.lean`.

**An ISA change** is `Statement/LeanIsa.lean`; **a scheme change** is `Statement/LeanXmss.lean`, `LeanSphincs.lean` or `LeanDa.lean` with its proof project (`lean_xmss`, `lean_sphincs`, `lean_da`); **a wire change** is `LeanVM/Wire/Encoding.lean`, compared with the Rust by `scripts/wire-diff.py`. Each reaches the guest through its bytecode, and the loop above follows.

## Commands

Run from the project's directory. `./check-all.sh lean` and `./check-all.sh vectors` at the root are the gate, and CI runs the same checks; read `check-all.sh` for every step.

```sh
# any project
lake exe cache get
scripts/regen-guest.sh --jobs 24                  # Statement, lean_vm: from lean_vm, the files derived from the guest, which are not committed
python3 -I ../lake-build.py .                     # lean_vm: python3 -I ../lake-build.py . LeanVM LeanVMTests
python3 -I ../lake-build.py . LeanVM --dev        # lean_vm, kernel skipped, never a gate

# lean_vm, against this repository's Rust
lake test && lake exe node-vectors
python3 -I scripts/fuzz-verifier.py tests/fixtures/verifier --jobs 4     # after lake build leanvm-verify and cargo build of scripts/rust-verifier-cli
python3 -I scripts/wire-diff.py tests/fixtures/verifier --jobs 8         # after lake build wire-diff and cargo build of scripts/wire-diff
scripts/export-prover-traces-rust.sh /tmp/p && python3 -I scripts/prover-diff.py /tmp/p --mutations 40 --jobs 4 --identical --expected tests/fixtures/verifier
scripts/export-verifier-fixtures-rust.sh tests/fixtures/verifier          # the fixtures, not committed: before the differential tests above
scripts/regen-guest.sh --jobs 24 [--check] [--from STEP]                 # every file derived from the guest, after a change to it
python3 -I ../lake-build.py . LeanVM LeanVMTests --dev --keep-going      # every proof a change breaks, in one run
scripts/guest-artifact [--check]                                         # the compiled guest the Rust prover loads (guests/lean_ethereum.compiled), at its fixed point
scripts/guest-export/target/release/guest-export . [--check]             # the guest's data, after scripts/guest-artifact
cargo run --release --manifest-path scripts/whir-fold-table/Cargo.toml -- LeanVM/Protocol/ToArkLib/Whir/AffineCombinerDeployedTable.lean [--check]   # the fold rounds' certificate, after a change to whir_config.rs
scripts/renumber-chain dump OUT; scripts/renumber-chain apply BEFORE AFTER   # the cost bounds' names, after a change to the cost-compiled chain moves its indices
LEANVM_GUEST_DIFF=/tmp/g cargo test --release --manifest-path scripts/guest-export/Cargo.toml --lib guest_diff -- --ignored && lake exe guest-diff /tmp/g/*.txt

scripts/backend-diff                                                     # the Lean back end against Statement/Data and the Rust compiler
lake exe guest-traced [--check]                                          # the guest's traced input to the back end (Backend/Guest/), after guest-core
lake exe guest-pieces [--check]; lake exe guest-pieces test [--check]     # the kernel's checks of the guest's compilation (Backend/Guest/Piece/, Compiled.lean), after guest-traced
lake exe guest-tables [--check]                                          # the back end's tables of the guest (Guest/Deployed/Data.lean), after guest-traced

# lean_sphincs: the crates' known answers on the compiled statement
lake exe signature-kat ../../crates ../../crates/lean_sphincs/tests/lean_sphincs/known_answer.hex
```

## Tools

- `python3 -I tools/deps.py cone FILE`: what an edit of `FILE`'s interface rebuilds, its CPU time, longest chain and families, by Lake's rule for private imports; `deps.py slow`, `deps.py path`.
- `python3 -I tools/firewall-canary.py`: checks that rule against Lake (the gate runs it); the plan that rests on it is `notes/per-function-cone.md`.
- `python3 -I tools/profile.py FILE`: where a slow file's time goes, by declaration and step; its docstring lists the usual fixes.
- `lake env lean --run ../tools/NeededImports.lean MODULE`: the imports `MODULE` does not need, and the modules to split.
- `lake env lean --run ../tools/Unused.lean ROOT... --prefix P`: declarations under `P` that no root uses; read before deleting.
- `python3 -I tools/escape-scan.py DIR...`: fails on a proof escape outside comments (the gate runs it).
- `python3 -I tools/docnames.py`: names `statement.tex` and the docs cite that no Lean file has.
