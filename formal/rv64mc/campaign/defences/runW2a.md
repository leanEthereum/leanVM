## Decisions

### D1. The shared representation: `Proof/Runtime/VecReprT.lean`, `BufT`, `RawVecT`, `VecT`.
- `BufT env m cap ptr size := cap.toNat = 0 ∨ (0x10000000 ≤ ptr.toNat ∧ env.Live m ptr (cap.toNat * size) ∧ ptr.toNat % 8 = 0)`: the buffer is none, or allocated before `m` (below `NEXT`) from the heap window's start, 8-aligned.
- `RawVecT env m a size := InWin env a 16 ∧ a.toNat % 8 = 0 ∧ BufT env m (getMem (rvCapAt a)) (getMem (rvPtrAt a)) size ∧ cap * size < 2^63`.
- `VecT env m a size := InWin env a 24 ∧ RawVecT env m a size ∧ len ≤ cap`.
- **Why**: what callers need to read and write a vector's elements and its header: the header's two (three) words in a window and aligned (the grow functions store into it), the buffer's bytes in a window (`BufT.inWin`: `cap * size = 0 ∨ InWin ptr (cap * size)`, from `Live` and `next ≤ heapEnd`), its doublewords aligned, and `Live` (so a callee's frame keeps it: `Frame.keeps_live`). `BufT.live` is exactly `GrowPre`'s and `FinishGrowPre`'s buffer disjunct, and `BufT`'s lower bound is exactly what `FinishGrowPreT` adds, so the chain discharges its callees' preconditions from it.
- **Where**: in `Proof/Runtime/`, not the suggested `Spec/Runtime/VecT.lean`, because it is stated with `MemsetT.InWin` (wave 1a's vocabulary, in `Proof/Runtime/MemsetT.lean`) and no `Spec/` module imports a `Proof/` one (`grep -rn "^import Rv64mc.Proof" Rv64mc/Spec` is empty); the total contracts' own definitions (`FinishGrowPreT`, `MemsetPreT`, `AllocSpecT`) live in `Proof/` too. The module is `VecReprT`, not `VecT`, because the definition `VecT` in a namespace `...VecT` trips the `dupNamespace` linter (observed).
- **Rejected**: (a) restating `InWin`'s body in `Spec/` (a second copy of the window vocabulary); (b) alignment to `T`'s alignment instead of 8 (`u16`, `u8` buffers would then not give callers 8-byte alignment for nothing, but every buffer comes from `alloc`, which returns multiples of 8, and the empty one is excluded by `cap = 0`); (c) putting the length and the elements' contents in the predicate (contents are function-specific; `VecAt` already exists for them).
- **Claims (non-vacuity)**: `bufT_of_alloc` (what `alloc` returns, of the size asked, is a `BufT`), `bufT_zero`, `RawVecT.of_empty` (an empty header in a window, aligned), `RawVecT.of_alloc` (a header naming a block `alloc` returned) are proved in the module, so the predicates hold of real states.

## Known risks

- **`BufT`'s 8-alignment**: true of every buffer from this bump allocator, but a contract stated over `T`'s alignment would be more portable. A vector whose buffer pointer is an interior pointer with nonzero capacity would violate it; I know of none.
- **`RawVecT` vs `Owned`**: the grow functions still need `GrowPre`'s `Owned` (below `NEXT` or at or above the stack top) besides `InWin`; a header inside a heap object allocated after the caller's `NEXT` snapshot is fine (`Owned` is checked against the current `NEXT`), but a header in the heap window above `NEXT` would satisfy `InWin` and fail `Owned` (impossible for a live object).
- `TryAllocRv64Pre`'s `align ≤ 8` (wave 0's) holds at `main`'s three sites (`x12 := 8`).
- `GrowAmortizedT.after` restates the partial `after`'s parameters (`nc`, `R`, the `hR*` equalities) over `Total`; the choice part depends on `rv_autoT` stopping at pc 42 on exactly eight paths (`iterate 8`), as the partial's does.
