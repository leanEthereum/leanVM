leanVM is knowledge sound and complete; its leanISA guest program, which aggregates signatures,
data-availability claims and other proofs, is sound and complete as an aggregation step; leanXMSS
and leanSPHINCS are strongly unforgeable; and LeanDA's commitments are position binding, and code

leanVM at commit \texttt{40f877dc} of its \texttt{main} branch, with pull request \#724 squash-merged
(\texttt{KECCAK} writes only the output cells its bytecode requests, one, two or all thirteen, and
the guest program writes each digest as one or two cells).

\section{The setting}

\paragraph{Hashing.} leanVM hashes with Keccak-256, the sponge over the permutation
Keccak-f[1600] (rate $136$ bytes, capacity $512$ bits, padding \texttt{0x01}\,\dots\,\texttt{0x80},
zero initial state, the first four lanes as digest). The statement writes a state as $25$ lanes of
$64$ bits throughout and defines Keccak-256 once, over any permutation (\lean{keccak256With});
the deployed Keccak-256 is this sponge over Keccak-f[1600]. leanVM's Fiat--Shamir transcript is a
duplex that calls Keccak-f[1600] directly, overwriting the first $16$ lanes of the state.

\paragraph{The random permutation model (RPM).} Keccak-f[1600] is modelled as a uniformly random
permutation $\pi$ of $\{0,1\}^{1600}$, sampled lazily (\lean{Common.lazyRandomPermutation},
\lean{Statement/RandomPermutation.lean}). The model's oracles are $\pi$ and $\pi^{-1}$ and
nothing else (\lean{Common.RandomPermutationOracles}). No hash is an oracle or a parameter of
the statement: every algorithm (verifier, prover, scheme, argument) is written over one
permutation and computes Keccak-256 as the sponge over it (\lean{keccak256With}), and its duplex
calls it; the model gives every party $\pi$ (\lean{Common.queryPermutation}), the deployed
instance Keccak-f[1600]. Each experiment is one game run against the lazily sampled permutation
(\lean{Common.runWithRandomPermutation}), the adversary's queries recorded where an extractor reads
them (\lean{Common.loggedOracles}). \emph{The assumption is that the
deployed Keccak-f[1600], a fixed permutation, behaves like a random one}, even to programs that
compute it: the \texttt{KECCAK} instruction a proved program executes computes the deployed
Keccak-f[1600], so in the model the transcript's permutation and a program's are independent,
while deployed they are the same function. The model thus excludes, by construction, programs that
evaluate their own proof's Fiat--Shamir duplex, the setting of the known attacks on Fiat--Shamir
for GKR-based systems (Khovratovich, Rothblum and Soukhanov, 2025). The adversary is classical,
and its code is fixed before $\pi$ is sampled (no advice that depends on the permutation). Every end statement with
an adversary is in this model; \lean{Statement/} contains no random oracle. Queries are counted in
one of two ways:
\begin{itemize}
\item for leanVM and its guest program (Sections~\ref{sec:zkvm} and~\ref{sec:guest}), $Q$ bounds
the adversary's own queries to $\pi$ and $\pi^{-1}$ on every path; the verifier's calls are bounded
in the proofs and enter the constants;
\item for the signature schemes (Section~\ref{sec:schemes}), $q$ bounds the adversary's own calls
of $\pi$ and $\pi^{-1}$ on every path; key generation, the signer and the final verification are
not charged;
\item for LeanDA (Section~\ref{sec:schemes}), $Q$ bounds every permutation call of the game on
every path, the scheme's own included; a Keccak-256 evaluation of $n$ bytes costs
$\lfloor n/136\rfloor + 1$ calls.
\end{itemize}
Adversaries may flip private coins, which no budget counts; the transcript records them, but the extractor's program reads only the permutation queries (\lean{permutationQueries}).

\paragraph{How the proofs reach the RPM.} Each proof is first carried out with independent random
oracles (Keccak-256 a random function on byte strings and, for leanVM and LeanDA, Keccak-f a random
function on states), then moved to the RPM by the project \lean{common}: the sponge over $\pi$ is
indifferentiable from a random oracle, so an experiment of $q$ permutation calls changes
probability by at most $q^2/2^{509}$, or $q^2/2^{508}$ with the duplex's direct calls
(\lean{Common.keccak256_transfer}, \lean{keccak256_transfer2}). The proofs reason with Keccak-256 as a call or parameter of its own, over
the same $\pi$; with that hash Keccak-256 over the permutation these forms are the statement's
algorithms and games, with the same distribution and the same permutation calls (the
\lean{WithHashBridge} files of each project, \lean{Common.PiOnly}). These are proof steps; their
costs are included in the bounds below.

\section{The zkVM: knowledge soundness and completeness}\label{sec:zkvm}

\paragraph{What a proof claims.} A proof claims that a program $\mathit{prog}$ (leanVM bytecode) runs to
completion on a public input $x$. A \emph{valid execution} of $\mathit{prog}$ on $x$ (\lean{ValidExecution},
\lean{Statement/LeanIsa.lean}) is a memory of $2^\kappa$ words, $2^{16} \le 2^\kappa \le 2^{32}$,
holding $x$ in words $0$ and $1$, together with a number of steps that run $\mathit{prog}$ on it from
$(\mathit{pc}, \mathit{fp}) = (1, 1)$ to the final state $(g^{N_{\mathit{prog}}-1}, 1)$, where $N_{\mathit{prog}}$ is the
bytecode's size: the last bytecode slot, in \texttt{main}'s frame. The machine halts when both
registers equal the final state's, checked before each step. This is exactly the state the
verifier's state bus checks for, so knowledge soundness needs no condition on the program.

\paragraph{The extractor.} Knowledge soundness is stated for the extractor a program of a cost
machine computes (\lean{LeanVM.extractorComputedBy}~$P$, \lean{Statement/CostMachine.lean}): the
program $P$, of size at most $14500$ (\lean{leanVmKnowledgeExtractorSizeBound}: the compiled
extractor's $14225$ and a slack of $275$, less than one leanXMSS signature's encoding), run on the encoded
statement, transcript and proof within a budget (\lean{leanVmKnowledgeExtractorBudget}: the most its
run may cost in the machine's price, so also the most steps it may execute,
$2^{81} + (N + 2^{30})(D + 2)^2(2^{15} + 2D)$ for $N$ permutation queries, $D = \log_2(N + 2) + 1$,
above the price \lean{lean_vm} proves of the compiled extractor at every shape; polylogarithmic per
query: about $2^{81}$ for $N \le 2^{50}$, the list decoder dominating, and $2^{157.08}$ at
$N = 2^{128}$, the transcript's index dominating), its output parsed as an execution; a run out of
budget outputs nothing, which counts as a break. The budget passes $2^{128}$ at about
$N = 2^{100}$, where the soundness bound is still $2^{-28}$, and its constant $2^{81}$ would pay for
a search of about $2^{70}$ Keccak-f[1600] evaluations: knowledge of a witness such a search finds
(of low entropy) is not what the statement certifies. The
statement takes $P$ as a parameter (\texttt{leanVmKnowledgeExtractor := P}) and constrains it only
by its size and budget: $P$ is a program (no classical choice), the size bound leaves the compiled
extractor no room for a useful table of witnesses, the budget is the one above, and the machine's
only runtime data is its input. The machine's prices are trusted to be honest: each step costs at
least $1$ and at least the words it writes (a \texttt{case} pays for the fields it binds, a
closure's application for its captured values); an operation on natural numbers costs the 64-bit
limbs it reads or writes, and a product, quotient, remainder or carry-less product the product of
its operands' limb counts (schoolbook), at least the limbs it writes, so one-limb operations, the
carry-less product included (PCLMULQDQ, PMULL), cost $1$, or $2$ when the result spills into a
second limb; a $\mathbb{F}_{2^{64}}$ product is compiled code (a carry-less product
and its reduction, $27$). In a program's size, a constructor's tag and a function index count one:
the machine reads them only by bounded lookups.

\texttt{lean\_vm} proves it for \lean{LeanVM.Cost.compiledKnowledgeExtractor}, the compiled form of
\lean{transcriptExtractor} (\lean{lean_vm/LeanVM/Protocol/Extraction/Extractor.lean}), and proves
that the program computes it within the budget. \lean{transcriptExtractor} is straight-line: it reads the proof and
the adversary's transcript and nothing else; it neither queries $\pi$, nor rewinds the adversary,
nor sees the verifier's queries. From the transcript's permutation queries (its coins left out,
\lean{permutationQueries}) it collects the Keccak-256 evaluations whose
whole padded sponge path appears as a chain of forward queries from the zero state
(\lean{keccakEvaluationsOfTranscript}). It reads the announced sizes and the stack's Merkle root off the proof,
inverts the Merkle tree through those evaluations to recover the committed word, lists the stacks
whose Reed--Solomon encoding agrees with the word on at least the Johnson threshold of columns (at
most $2^{12}$ of them, \lean{LeanVM.candidates_ncard_le}, \lean{lean_vm}), and returns a candidate's memory
image whose halting run is a valid execution, if one exists.

It is an algorithm: every definition it uses is computable and deterministic. It lists the
candidates lane by lane with the Guruswami--Sudan list decoder over $\mathbb{F}_{2^{64}}$
(CompPoly's Lee--O'Sullivan interpolation and Roth--Ruckenstein root finding, with Shoup's trace
splitting for the field roots), and it is proved to list every candidate. It runs each
candidate for at most as many steps as the announced tables have rows (\lean{stepCap}), which a
valid execution never exceeds (proved). Its running time, as the compiled program, is proved
within the budget above (\lean{LeanVM.Cost.Bounds.extractorC_cost}, \lean{lean_vm}): the compiled list decoder
interpolates by CompPoly's approximant basis (it lists the same candidates, proved), and
Roth--Ruckenstein's search dominates, with $O(\log^2 N)$ comparisons per lookup in the evaluations (sorted maps). It gives straight-line knowledge with a
concrete reduction cost for the collision clauses below.

\paragraph{The proof.} A proof (\lean{Proof}, \lean{Statement/LeanVmVerifier.lean}) is the Rust
verifier's: the scalar stream and the Merkle openings, grouped in phases, one phase per opened
commitment, each opening (\lean{Opening}) the position it opens, the leaf's words and the full path
of siblings, in the order the verifier samples the queries. The verifier opens a phase
(\lean{openPhase}, \texttt{Transcript::merkle}) in the Rust's order: it rejects unless every leaf is
the commitment's width and every path its height (the shape), then unless the phase's positions are
the queries it sampled, in order (the positions), then unless each path climbs to the committed
root.

\paragraph{Knowledge soundness} (\lean{LeanVM.KnowledgeSoundness}). In the experiment
(\lean{knowledgeSoundnessExperiment}), an adversary $\mathcal{A}$ with oracle access to $\pi$ and
$\pi^{-1}$ outputs a program $\mathit{prog}$, a public input $x$ and a proof, and the verifier
checks it with Keccak-256 the sponge over $\pi$ and Keccak-f the permutation $\pi$. For every
adversary making at most $Q \le 2^{128}$ queries to $\pi$ and $\pi^{-1}$ on every path,
\[
\boxed{\ \Pr\left[\begin{array}{l}\text{the verifier accepts } (\mathit{prog},x,\text{proof}) \text{ and the}\\
\text{extractor outputs no valid execution of } \mathit{prog} \text{ on } x\end{array}\right]
\le (Q+2^{14})\cdot 2^{-128} + 5\,(Q+2^{14})^2\cdot 2^{-256}\ }
\]
(\lean{LeanVM.knowledgeSoundness_holds}). The constant $2^{14}$ absorbs the verifier's $12006$
Keccak-256 evaluations and duplex permutations (as calls of $\pi$ up to $12006\cdot 2^{32}$, the IV
hashing a bytecode of up to $2^{32}$ instructions) and two further terms of at most $2^{-128}$ each:
the transfer to the RPM, which pays for those calls, and the verifier's own $12006/2^{256}$.

\paragraph{Completeness} (\lean{LeanVM.Completeness}). The statement names its honest prover,
\lean{LeanVM.leanVmHonestProver}: the executable \lean{LeanVM.Prover.prove}
(\lean{Statement/Prover/}), its Keccak-256 and Keccak-f[1600] calls answered here from $\pi$; with
the deployed Keccak it is \texttt{lake exe leanvm-prove}. It runs the execution once to obtain the
witness, then plays the honest moves against the verifier's own program. Its only search is the
proof-of-work nonce search within its fuel, and it sees hash answers only as the challenges the
verifier samples. On the test corpus ($17$ programs at $4$ rates) its proofs are byte-identical to
the Rust prover's, and both verifiers reject every mutation of them.

For every program $\mathit{prog}$, public input $x$ and valid execution of $\mathit{prog}$ on $x$ of committed size at
most $2^{28}$ cells, at every inverse rate $2^\rho$ with $1 \le \rho \le 4$, trying $2^{25}$ nonces
per proof of work,
\[
\boxed{\ \Pr[\text{the verifier rejects the honest proof}] \le 2^{-256}\ }
\]
(\lean{LeanVM.completeness_holds}, through \lean{prove_eq_honestComp} in \lean{lean_vm}: the prover is the
specification's honest prover at the execution's witness). Completeness is not perfect only
because the proof of work is bounded: for any fuel $f \le 2^{64}$ the rejection probability is at
most
\[
\delta(f) = Q_f\,(1-2^{-17})^{f} + (Q_f\cdot 2^{32})^2/2^{508}, \qquad
Q_f = 12008 + 48017\,(2^{27} + 2f + 2)
\]
(\lean{LeanVM.Rpm.completenessRpm}, \lean{lean_vm}). The \emph{committed size} (\lean{Execution.committedSize}) of an
execution is
$4\cdot 2^{\kappa} + 2^{\ell} + 15h_{\mathrm{xor}} + 15h_{\mathrm{mul}} + 8h_{\mathrm{set}} +
15h_{\mathrm{deref}} + 14h_{\mathrm{jump}} + 28k + 2^6 k$, where $2^\kappa$ is the memory size,
$2^\ell$ the bytecode size, $h_{op}$ the least power of two at least the number of executed
instructions of opcode $op$, and $k$ the same for \texttt{KECCAK}, at least $2^9$.

\paragraph{The proof on the wire.} The end statements are about the structured proof. On the wire
a proof travels as bytes, its one encoding (\lean{crates/fiat_shamir/src/wire.rs}), each phase's
paths pruned to their positions, their sizes, the distinct leaves and the siblings no other path
gives; the pruning idea and its first formalization, on leanerVM's \texttt{main} branch, are
Nicolas Schleicher's (\url{https://github.com/scaraven}). The encoding is a compression layer, outside
\lean{Statement/}: \lean{lean_vm} transcribes the encoding and the decoding
(\lean{lean_vm/LeanVM/Wire/Encoding.lean}) and proves, as theorems of its own pinned with the end
theorems, that it is lossless on honest proofs (the round trip, \lean{LeanVM.Wire.roundTrip}, with
\lean{LeanVM.Wire.proveWithHash_wireDecodable}: the honest prover's proofs decode from their
encoding) and the only encoding of its proof (bytes that decode to a proof are its encoding,
\lean{LeanVM.Wire.oneEncoding}). That the transcription is the Rust's
\texttt{from\_bytes} and \texttt{to\_bytes} is test evidence (the wire differential: honest wire
proofs, their mutations and the Rust test's vector).

\section{The signature schemes and LeanDA}\label{sec:schemes}

In the signature games $q$ counts the adversary's own calls of $\pi$ and $\pi^{-1}$; in LeanDA's games
$Q$ counts every permutation call of the game. Every bound holds for every $q$ or $Q$ (a bound above
one says nothing).

\subsection*{The signature schemes}

\paragraph{leanXMSS} (\lean{LeanXmss.RandomPermutationModel.LeanXmssStronglyUnforgeable},
\lean{Statement/LeanXmss.lean}): a single key is strongly unforgeable under chosen-message attack
(multi-key security is not stated: a guessing reduction would have to simulate the other keys' key
generation and signing as its own, charged, calls, so it does not give $k\cdot(q+\mathit{slack})\cdot2^{-127}$ for
$k$ keys; a direct multi-key bound, the public parameters acting as salts, is plausible but not proved).
The game samples the key's seed, generates the keys, and runs the adversary with $\pi$,
$\pi^{-1}$ and a signing oracle; the adversary picks each request's leaf index and wins
only if no index is requested twice (re-signing the same message at the same index, which the crate allows, is a loss too), and its forgery wins if it verifies and is not a pair the
oracle returned. For every $q$, an adversary that itself makes at most $q$ calls of $\pi$ and
$\pi^{-1}$ on every path, and at most $2^{32}$ signing requests (a hypothesis of the Lean statement that costs nothing: past $2^{32}$ requests some leaf index repeats, so the adversary that stops there wins at least as often),
forges with probability at most
\[
\boxed{\ (q + 2^{10})\cdot 2^{-127}\ }
\]
(\lean{XmssSecurity.leanXmss_rpm_security}, \lean{Common.SufCma.StronglyUnforgeable}). Key
generation, the signer's hashing, its grinding through up to $2^{32}$ randomizers per layer
included, and the final verification are not charged to $q$. The constant is the random-oracle
step's $530 = (2\cdot384 + 290 + 2)/2$ (the forgery's verification counted in each of the proof's two
lanes, the first lane's forgery probes, two seed guesses) and the transfer's one unit, rounded up.

\paragraph{leanSPHINCS} has the same game and the bound $(q + 2^{19})\cdot 2^{-127}$ for every $q$
(\lean{Sphincs.LeanSphincsStronglyUnforgeable}, \lean{Statement/LeanSphincs.lean}), for at most
$N = 1\,182\,000\,000$ signing requests (\lean{Sphincs.leanSphincsStronglyUnforgeable}, from
leanVM's own random-oracle theorem \lean{FORS.h26_layered}, $(q + 265072)/2^{127}$: key
generation's $264193$ hash calls and the verification's $879$); staying within $N$ signatures is the key holder's duty (the signer does not
count them). The scheme is SLH-DSA (FIPS 205) on Keccak-256 with WOTS$^+$C: every tree, chain and
secret hash is $\mathrm{Trunc}_{16}(H(\mathrm{PK.seed} \Vert \mathrm{ADRS} \Vert M))$ with FIPS 205's
32-byte address, FORS trees are hashed to their roots, and the digest is two counter-mode calls on
the 32-byte message unframed (only the randomizer's $\mathrm{PRF}_{\mathrm{msg}}$ hashes pure
SLH-DSA's framing $M'$), read as FIPS 205's Algorithm~19. Its secret key is the crate's, the
32-byte $\mathrm{SK.seed}$, from which $\mathrm{PK.seed}$ and $\mathrm{SK.prf}$ are hashed again at
each signature, and its signer is the
crate's, hash call for hash call (the top tree built once, for the root and the top path, each FORS
tree built once, the layers from the bottom up). In leanXMSS the secret key is the crate's too: the
key's seed $S_0$ and the public parameter $P$ key generation derived, from which the signer derives
the scheme seed $S = H(\mathit{tag} \Vert S_0)$ again at each signature. A leanSPHINCS signature
costs about $2^{19}$ permutations in expectation and about $2^{33.6}$ in the worst case ($2^{32}$
encoding counters on each of its three layers); none of it is charged to $q$, and the bound does not
grow with the number of signatures. Signed messages are 32 bytes: a longer payload needs an outer
hash, whose collisions are outside the bounds. Both schemes are stated through one game,
\lean{Common.SufCma.StronglyUnforgeable},
and share the shape of one tweakable hash (\texttt{hasher}, \texttt{truncate} of
\texttt{crates/signatures/src/lib.rs}), hash chain and path fold.

\subsection*{LeanDA}

LeanDA commits to a matrix of blobs so that clients can check random pieces of it. Its statements are
Benedikt Wagner's framework, theorems and proofs, ported and instantiated with LeanDA
(\lean{Statement/LeanDa.lean}). Everyone in the games (the adversary, the argument, the verifier)
queries $\pi$ and $\pi^{-1}$ alone and hashes with Keccak-256 over $\pi$.

\paragraph{The matrix.} The matrix has $r$ rows, $1 \le r \le 1024$, one blob each. A blob is a
payload of $2^{14}$ field elements, Reed--Solomon encoded to $2^{15}$
(\texttt{leanDaErasureCode r}). Each encoded row is cut into $128$ \emph{cells}, so the matrix has
$128\,r$ positions.

\paragraph{The commitment.} The committer hashes each row's $128$ cells into a Merkle tree, the
row's \emph{blob root} (\lean{blobRootWith}), and publishes the root of the Merkle tree over the
blob roots, the rows padded to a power of two with zero codewords (\lean{commitCells}). To
\emph{open} a position, it gives the cell and its path, in its blob's tree and then in the tree over
the blob roots; the opening verifies if they hash back to the root (\lean{verifyCellWith}).

\paragraph{The proof that the rows are codewords.} A Merkle root alone does not show that the rows
are codewords. So the committer also gives a proof, from some \emph{argument} (\lean{OracleArgument}: a
prover and a verifier that may query the oracles), that the cells satisfy LeanDA's relation
(\lean{relationWith}):
\begin{itemize}
\item the cells hash to the root, and
\item every row passes the \emph{membership test}: from the root, the duplex derives one
challenge $z$, which defines a codeword $L(x) = \prod_{j<14} (1 + z^{2^j}\,\widehat{W}_j(x))$ of the
dual code (\lean{dualCodewordAt}); every row must be orthogonal to $L$. A row that is not a codeword
passes with probability at most $(2^{14}-1)/2^{192} < 2^{-178}$: its inner product with $L$ is a
nonzero polynomial in $z$ of degree below $2^{14}$.
\end{itemize}

\paragraph{Completeness} (\lean{LeanDa.LeanDaPerfectlyComplete}). If the argument is perfectly
complete, every position of an honest commitment opens and verifies, with probability $1$, for
every permutation $\pi$ (\lean{LeanDa.leanDa_perfectlyComplete_rpm}).

\paragraph{Position binding} (\lean{LeanDa.LeanDaPositionBinding}). No adversary can open one
position to two different cells. For every argument, with $Q$ permutation calls, it succeeds with
probability at most
\[
\boxed{\ (Q+1)^2\cdot 2^{-256}\ }
\]
(\lean{LeanDa.leanDa_positionBinding_rpm}).

\paragraph{Code binding} (\lean{LeanDa.LeanDaCodeBinding}). Position binding is not enough for
sampling. A committer could commit to rows that are not codewords; each opening would still
verify, but the cells clients receive would not come from one matrix of codewords, whose blobs could then not
be reconstructed. Code binding says this cannot happen.

\emph{The game} (\lean{codeBindingGame}). The adversary outputs a root, a proof, and some opened
positions (each with a cell and an opening). It wins if
\begin{itemize}
\item the argument's verifier accepts the proof,
\item every opening verifies, and
\item no codeword agrees with all the opened cells (\lean{ErasureCode.Consistent}).
\end{itemize}

\emph{The assumption.} Code binding can only be as good as the argument, so the theorem assumes the
argument is \emph{knowledge sound}. That means there is an extractor that, reading only the proof
and the adversary's queries (\lean{StraightLineExtractor}; it does not rewind), finds cells satisfying the
relation whenever the verifier accepts. Precisely: in the game \lean{knowledgeSoundnessGame}, an adversary making
$q \le 2^{128}$ calls makes the verifier accept while the extracted cells fail the relation with
probability at most $(q + c)\cdot 2^{-k}$, for some constants $c$ and $k$.

\emph{The theorem.} Under this assumption, an adversary making $Q$ calls (any $Q$, verifications
included) wins the code-binding game with probability at most
\[
\boxed{\ (Q + c + 2^{22})\cdot 2^{-k} + (Q + 2^{22})\cdot 2^{-178} + (Q + 2^{22})^2\cdot 2^{-247}\ }
\]
(\lean{LeanDa.leanDa_codeBinding_rpm_bound}). At $Q = 2^{64}$ the last two terms are about
$2^{-114}$ and $2^{-119}$.

\emph{Why.} Run the extractor on the adversary; it returns cells $c^*$. One of three things holds.
\begin{enumerate}
\item $c^*$ fails the relation. Then the adversary breaks the argument's knowledge soundness:
the first term.
\item $c^*$ satisfies the relation but has a row that is not a codeword. Then it passed the
membership test by luck, $(2^{14}-1)/2^{192}$ per root: the second term.
\item $c^*$ is a codeword. Every opened cell hashes to the same root as $c^*$, so unless Keccak-256
has a collision, each opened cell is $c^*$'s cell, and the codeword $c^*$ agrees with all of them:
the adversary loses. Collisions and other bad hash events give the third term.
\end{enumerate}

\emph{What is open.} The assumption can be met: the argument whose proof is simply all the cells
is complete and knowledge sound, though its proof is as large as the matrix (an observation, not
formalized). The deployed argument is leanVM proving the relation inside the guest program. It cannot
meet the assumption in this model: its relation uses the real Keccak-f[1600], not $\pi$, so an
adversary computes a root with no query to $\pi$ and proves its opening honestly, and no
straight-line extractor finds a $\pi$-preimage of it. Code binding covers the arguments whose
relation is evaluated over $\pi$; for the deployed one it would need a model that ties the guest
program's Keccak to $\pi$ (Section~\ref{sec:notgive}, and the first item of the last section).

\section{The leanISA guest program (aggregation)}\label{sec:guest}

The guest program aggregates: from signatures, DA matrices and child proofs, it proves one statement
holding all their claims. This section defines what it proves and states what is proved about it.
Every definition named here is in \lean{Statement/}: what a node proves in
\lean{Statement/LeanVmGuest.lean} (with the statement and its digest), the batching program
in \lean{Statement/LeanVmGuestBatching.lean}, the completeness statements and the batching's
soundness in \lean{Statement/LeanVmGuestCompleteness.lean}, the decoder program's also in
\lean{Statement/LeanVmGuest.lean}, the composed statements in \lean{Statement/Corollaries.lean}; names
marked \lean{lean_vm} are the proofs'.

\subsection{The objects}

\paragraph{The guest program} $G$ (\lean{LeanVM.Guest.guestProgram}) is leanVM's compiled aggregation
program (\texttt{crates/rec\_aggregation/guests/lean\_ethereum.py} at \texttt{40f877dc}),
transcribed as generated data (\lean{Statement/Data/}). Its bytecode $B$ has $2^{19}$ instruction
slots of $16$ words of $\mathbb{F} = \mathrm{GF}(2^{64})$, so $2^{23}$ words
(\lean{bytecode_length}, in \lean{lean_vm}). Below, $H$ is Keccak-256 and
$\mathbb{E} = \mathbb{F}[y]/(y^3+y+1)$, the field of $2^{192}$ elements. Its \emph{deployed seed}
\[
iv_G = \mathrm{IV}(B) = H(\mathit{TAG} \,\|\, \bar B), \qquad \mathit{TAG} = \texttt{leanvm-v1}
\]
(\lean{deployedSeed}, \lean{fiatShamirIvWith}, \texttt{crates/verifier/src/layout.rs:68},
\texttt{bytecode.rs:46-53}), the hash of the proof system's $9$-byte version tag and the bytecode's
words as $8$-byte little-endian strings, is the Fiat--Shamir initial value prover and verifier
derive from the bytecode; a test run by the gate (\texttt{lake exe node-vectors}) checks it against
leanVM's \texttt{fs\_seed}.

\paragraph{A statement} $s$ (\lean{NodeStatement}) consists of
\begin{itemize}
\item a list $\Cx$ of leanXMSS claims and a list $\Cs$ of leanSPHINCS claims, each a pair $(pk, m)$
meaning ``$pk$ signed $m$'';
\item a \emph{DA digest} $\mathit{da}$ (\lean{NodeClaims.daDigest}): either $H(\rho \,\|\, z)$ of one
data-availability claim (\lean{DaClaim}, \lean{daClaimDigest}), a matrix root $\rho$
(\lean{daRoot}) and a membership challenge $z \in \mathbb{E}$ (\lean{membershipChallenge}, as its
three limbs and a zero word), or $32$ zero bytes without one (\lean{zeroDigest};
\texttt{verifier::da::digest}, \texttt{crates/verifier/src/da.rs:19-26}). The claim: some matrix of
$1$ to $1024$ encoded blobs with root $\rho$ has every row orthogonal to the dual codeword $L$ of $z$
(\lean{Da.MatrixWitness.Opens}), which the guest program builds from $z$. The outer verifier holds
$\rho$, derives $z$ from $\rho$ (Section~\ref{sec:schemes}) and checks $\mathit{da} = H(\rho \,\|\, z)$; that
this derivation makes the rows codewords is not proved (Section~\ref{sec:notgive});
\item a \emph{deferred claim} $c = (\zeta, v)$, $\zeta \in \mathbb{E}^{23}$, $v \in \mathbb{E}$, meaning
that the multilinear extension $\widehat{B}$ of the bytecode, as a function on $\{0,1\}^{23}$,
satisfies $\widehat{B}(\zeta) = v$ (\lean{DeferredClaim.HoldsWithShape}).
\end{itemize}

\paragraph{The statement's digest} under a seed $\sigma$ (\lean{statementDigest},
\texttt{aggregation/statement.rs:85-114}) is
\[
\mathrm{dig}_\sigma(s) = H\big(\sigma \,\|\, H(\enc(\Cx)) \,\|\, H(\enc(\Cs)) \,\|\, \mathit{da} \,\|\, \enc(c)\big),
\]
where $\enc(\Cx)$ concatenates, per claim, the key's bytes, a leanXMSS key's root ($16$ bytes)
then its parameter ($16$), and the message ($32$); $\enc(\Cs)$ likewise, a leanSPHINCS key's bytes
being $\mathrm{PK.seed}$ then $\mathrm{PK.root}$ (\lean{claimListDigest},
\texttt{aggregation/statement.rs:32-56}); and $\enc(c)$ is the $24$-byte encodings of
$z_1, \dots, z_{23}, v$,
padded with one zero element to an even number. The lists' lengths are bound by Keccak's padding;
the deferred claim's encoding carries no length, so deferred claims are told apart only at one
shape. The guest program's public input is this $32$-byte digest.

The seed $\sigma$ is the Fiat--Shamir IV with which $G$ verifies its children's proofs, meant to be
proofs of $G$ itself (the deferring verifier reads $G$'s bytecode only through its length, so it
accepts as well a proof of any program of that length: Section~\ref{sec:notgive}). $G$ cannot contain its own IV (a hash of its own bytecode), so it reads
$\sigma$ as input, and the digest binds it; the outer verifier computes the digest with
$\sigma = iv_G$.

\paragraph{A witness} $w$ (\lean{NodeWitness}) consists of
\begin{itemize}
\item a list of \emph{children}, each a statement $s_i$, a proof $p_i$, and a \emph{fresh} claim
$f_i = (\zeta_i, v_i)$ on the bytecode, the evaluation the child's proof leaves to be checked;
\item the \emph{raw signatures}, leanXMSS and leanSPHINCS, each with the claim it signs;
\item optionally, one LeanDA matrix the node checks directly, with the DA claim it opens;
\item the \emph{batching hints}: the round messages of one sumcheck, and a final value.
\end{itemize}

\subsection{What one node establishes}

$\mathrm{NodeRel}(B, \sigma, s, w)$ (\lean{NodeRelation}) is the conjunction of four conditions,
the witnesses holding the claims:
\begin{enumerate}
\item Every signature claim of $s$ is held (\lean{SignatureClaimsHeld}): every raw signature verifies
under its claim's key and message (Keccak-256 as the schemes' hash, at any leaf index), and every
claim of $s$ is a raw signature's claim or occurs in the corresponding list of some child's $s_i$.
\item The DA digest is accounted for (\lean{DaDigestHeld}): with a direct matrix,
$\mathit{da} = H(\rho \,\|\, z)$ of the claim it opens; without one, $\mathit{da}$ is zero or
some child's DA digest (the guest program's \texttt{da\_pick}, \texttt{lean\_ethereum.py:4643-4647}).
\item Every child is proven (\lean{ChildrenProven}): its deferred claim has the bytecode's shape,
and the \emph{deferring verifier} accepts its proof: $\mathrm{verifyDeferred}(B, \sigma,
\mathrm{dig}_\sigma(s_i), f_i, p_i) = \mathsf{true}$. The deferring verifier is the zkVM verifier
except that, instead of evaluating $\widehat{B}$ at the point it reaches, it outputs that evaluation
as the claim $f_i$. It runs on the real Keccak-256 and Keccak-f[1600], the ones the guest program
computes.
\item The deferred claim batches the children's (\lean{DeferredClaimBatched}). With no children, its
point is all-zero (its value is left to the outer verifier); otherwise $\mathrm{batch}\big(
(\mathrm{dig}_\sigma(s_i), f_i, c_i)_i, \text{hints}\big) = c$ (\lean{nodeBatchingProgram} run by
\lean{runBatching}; \lean{batch} in \lean{lean_vm}), with $c_i$ the deferred claim of $s_i$. The
batching is a Fiat--Shamir transcript on Keccak-f[1600], seeded from the hash of the label
\texttt{leanvm/recursion-aggregation/v1}: it absorbs the number of children, then each child's
digest and two claims; squeezes one challenge $\lambda \in \mathbb{E}$, whose powers batch the
claims (\lean{lambdaPowers}); and runs one degree-$2$ sumcheck reducing
$\sum_i (\lambda^{2i} v_i + \lambda^{2i+1} v'_i)$, with $v_i$
the value of $f_i$ and $v'_i$ that of $c_i$, to one claim on $\widehat{B}$ at a new point.
Either way $s$'s deferred claim has the bytecode's shape: its point has $23$ coordinates
(\lean{DeferredClaim.HasBytecodeShape}), the zero point's or the sumcheck's challenges.
\end{enumerate}
\lean{NodeRelation} does \emph{not} say that a child's claims are true, only that the deferring verifier,
run on the real Keccak, accepts its proof. Whether that makes them true is the soundness of leanVM
with Keccak instantiated, which is not proved (Section~\ref{sec:notgive}).

\paragraph{The outer verifier} (\texttt{EthereumProof::verify}, \texttt{aggregation/proof.rs:152-169})
additionally checks that the DA digest is that of its root with the root's membership
challenge, that the deferred claim holds ($\widehat{B}(\zeta) = v$), and the lists' form
(sorted, no repeats, fewer than $2^{16}$ signature claims). Of these, \lean{AggregateSound} below
assumes only that the deferred claim holds (\lean{DeferredClaim.HoldsWithShape}); no end statement
models the DA digest's derivation or the lists' form. Without the derivation, the DA condition says
nothing of the blob: \lean{MatrixWitness.Opens} accepts any challenge the digest binds, $z = 0$
included, whose dual codeword is all ones.

\subsection{Soundness}

The outer verifier accepts a proof that $G$ ran on the public input $x = \mathrm{dig}_{iv_G}(s)$.
What does that establish about $s$? The answer has three parts, each an end theorem.
\begin{enumerate}
\item \textbf{The zkVM is knowledge sound} (\lean{KnowledgeSoundness},
Section~\ref{sec:zkvm}). Except with probability
\[
\varepsilon(Q) = (Q+2^{14})\cdot 2^{-128} + 5\,(Q+2^{14})^2\cdot 2^{-256},
\]
the extractor returns a valid execution $t$ of $G$ on $x$. This is the only step with an oracle
and a probability.
\item \textbf{Every execution of $G$ proves a statement} (\lean{GuestKnowledgeSoundness}). From
every valid execution $t$ of $G$ on any public input $x$, the decoder program $D$ outputs, within
its budget, a seed $\sigma'$, a statement $s'$ and a witness $w'$ with
\[
\mathrm{dig}_{\sigma'}(s') = x \qquad\text{and}\qquad \mathrm{NodeRel}(B, \sigma', s', w').
\]
\item \textbf{The digest binds} (\lean{StatementDigestBinds}). Let $(\sigma, s)$ and $(\sigma_0, s_0)$
be seeds and statements whose deferred claims have the bytecode's shape. If
$\mathrm{dig}_\sigma(s) = \mathrm{dig}_{\sigma_0}(s_0)$, then $(\sigma, s) = (\sigma_0, s_0)$, or
Keccak-256 collides on one of three pairs of inputs (\lean{collisionCandidates}): those of the
outer hash, of $H(\enc(\Cx))$ and of $H(\enc(\Cs))$. The DA digest enters the outer input as it
is, so it needs no pair of its own.
\end{enumerate}
Steps 2 and 3 are facts about $G$'s code and the digest: no oracle, no probability, and Keccak is
the deployed function $G$ computes.

\paragraph{Chained.} Steps 1 and 2 compose: except with probability $\varepsilon(Q)$, an accepted
proof of $G$ on any $x$ yields an extracted execution on which $D$ outputs, within its budget, a
decoding $(\sigma', s', w')$ with $\mathrm{dig}_{\sigma'}(s') = x$ and
$\mathrm{NodeRel}(B, \sigma', s', w')$ (\lean{lean_vm} proves this for its
\lean{transcriptExtractor} and its memory decoder \lean{decode}: \lean{aggregate_knowledge}). Step 3
with $(\sigma_0, s_0) = (iv_G, s)$ then gives \lean{AggregateSound} (from the fields alone,
\lean{LeanVM.corollaries_of_theorems}, \lean{lean_vm}): except with probability $\varepsilon(Q)$, if
the verifier accepts a proof of $G$ on $\mathrm{dig}_{iv_G}(s)$, for any $s$ whose deferred claim
holds (\lean{DeferredClaim.HoldsWithShape}, as the outer verifier checks), the extracted execution $t$
\emph{explains} $s$
(\lean{ExplainsStatement}):
\begin{itemize}
\item $D$ decodes $t$ to $(iv_G, s, w')$ with $\mathrm{NodeRel}(B, iv_G, s, w')$, or
\item the decoded seed and statement, with $(iv_G, s)$, give a Keccak-256 collision among the
three pairs.
\end{itemize}
For one execution and \lean{lean_vm}'s decoder \lean{decode}, steps 2 and 3 together are
\lean{decode_binds} (\lean{lean_vm}).

Two Keccaks meet here. The verifier of step 1 runs on $\pi$: Keccak-256 is the sponge over $\pi$,
Keccak-f is $\pi$, and its transcript starts from the IV computed over $\pi$, while the digest's
seed $iv_G$ is the IV over the deployed Keccak. The digest, \lean{NodeRelation} (the children's proofs, the signatures, the
batching) and the collision use the deployed Keccak, which $G$ executes. The collision is therefore
not an event of small probability: it is a concrete pair of inputs, read off $t$ and $s$, on which
the deployed Keccak-256 collides.

\paragraph{Why a decoder.} \lean{GuestKnowledgeSoundness} could have said only that some
$(\sigma', s', w')$ exists (\lean{guest_sound} in \lean{lean_vm} proves that too). It says more: the
witness is computed \emph{from} the execution, by a program within a budget. That is what makes the
extracted execution knowledge of a witness. But a decoder given as a Lean function may use classical
choice, and one that simply chose some triple satisfying the conclusion would make
\lean{GuestKnowledgeSoundness} no stronger than the existential. The statement is only as strong as
its decoder, so the decoder is a parameter of the same kind as the extractor: a cost-machine program
$D$ (\lean{Statement/LeanVmGuest.lean}) of size at most \lean{guestWitnessDecoderSizeBound} (its
literals, the guest program's per-function tables, counted in full), run within
\lean{guestWitnessDecoderBudget} on the encoded program and execution
(\lean{encodeGuestWitnessDecoderInput}), whose output must be the encoding (\lean{encodeValue}) of a
decoding that explains the input; there is no parse, and the encoding is injective
(\lean{encodeValue_decoded_injective}, \lean{lean_vm}). A program chooses nothing. The statement
accepts any program that computes the witness from the execution within the budget, not only one
that reads it off the memory, just as it asks of the extractor program only that it compute a valid
execution within its budget. A program that output another statement of the same digest would
exhibit a Keccak-256 collision; what excludes it is that none is known.

\paragraph{The decoder's budget.} The budget (\lean{guestWitnessDecoderBudget}) is
$(\mathit{steps} + 1)(2^{21} + 2^{13}\lambda) + (70\kappa + 374)\cdot 2^\kappa + 2^{37}(\lambda + 16)$,
$\lambda = \log_2(\mathit{steps} + 1)$, above the closed-form price \lean{lean_vm} proves of the
compiled decoder (about $0.32$ to $1.09$ bits above it at the six points below): per step $2^{20.55}$ to $2^{20.98}$, against the budget's $2^{21}$ to $2^{21.3}$ (the replay
and the filing of the state in a sorted array, its share of one sort, growing as $\log$ of the
steps); the sorted table of the memory's addresses at the execution's $\kappa$; and
$2^{37}(\lambda + 16)$, about $2^{42}$ to $2^{43}$, for the witness read at the counts and the
cursors a valid execution bounds, with about $2^{25.28}$ frame lookups: $G$'s own asserts give at
most $16$ children, $65535$ claims of each scheme and $65535$ coverage slots (\lean{valid_counts});
each child's cursor is at most $8192$ words, as the stream of its proof is, which the deferring
verifier accepts on a valid execution (\lean{valid_cursor}, from
\lean{stream_le_of_verifyDeferred}); and the decoder clamps the DA matrix's row count at $1024$. The
budget is $2^{42.74}$ at $\kappa = 20$ and $2^{20}$ steps, $2^{45.32}$ at $\kappa = 24$ and
$2^{24}$, $2^{49.17}$ at $\kappa = 28$ and $2^{28}$, $2^{51.17}$ at $\kappa = 32$ and $2^{30}$,
$2^{72.26}$ at $\kappa = 32$ and $2^{51}$, and $2^{81.30}$ at $\kappa = 32$ and $2^{60}$ (the price
there: $2^{41.65}$, $2^{44.83}$, $2^{48.78}$, $2^{50.80}$, $2^{71.93}$, $2^{80.98}$). The constant
prices the witness at the bounds above, not at the run's, so with fewer children and claims, at
$\kappa \le 28$ and well below $2^{22}$ steps, the budget is several times the compiled decoder's
price. There is no cap on the steps in the budget. A valid execution of $G$ (\lean{ValidExecution})
has fewer than $2^{51}$ steps: the memory is fixed and every instruction reads a cell at
$\mathit{fp}\cdot o$ for an offset $o$ fixed by $\mathit{pc}$, so at each $\mathit{pc}$ at most
$2^\kappa$ values of $\mathit{fp}$ let a step succeed; the run is determined by
$(\mathit{pc}, \mathit{fp})$, and a repeated state would loop without halting
($2^\ell\cdot 2^\kappa$ states, $\ell = 19$, $\kappa \le 32$; argued, not a Lean theorem;
\lean{lean_vm} proves fewer than $2^{128}$, \lean{steps_lt_replayFuel}).

\paragraph{The decoder's size bound.} The bound (\lean{guestWitnessDecoderSizeBound}, $628800$)
limits any program; it is the compiled decoder's size at leanVM \texttt{40f877dc}, $628370$ (proved
at most that, measured exactly; the guest's frame-cell table is $587459$ of it), and a slack of
$430$: room for one leanXMSS signature's encoding ($309$) beside its code but not two, so no useful
table of witnesses (hard-coded signatures that would mask a bug of $G$ on finitely many statements)
fits there. It does not bound what a program written differently could hold: the frame-cell table
(cells below $2^{20}$) packs to about a third, three cells to a limb, and a program may compute its
tables from its input.

The proofs' decoder is \lean{LeanVM.Guest.End.decode}, defined in \lean{lean_vm}; a program
computing it within its size bound and budget gives \lean{GuestKnowledgeSoundness}
(\lean{guestKnowledge_of_decode}, \lean{lean_vm}). It replays the run:
\begin{itemize}
\item the seed and the statement from \texttt{main}'s frame, read through the sorted table of the
memory's $2^\kappa$ addresses;
\item each signature, matrix, child proof and batching hint from the frame of the function that
checked it: the run is stepped from its initial state through the program's and the memory's
tables, and each call is given the frame at which the run first entered its callee, its
precondition decided there.
\end{itemize}
It runs the machine (whose \texttt{KECCAK} instruction checks Keccak-f[1600]) and no verifier,
decides no proposition classically and picks no witness. The test
\lean{LeanVMTests.Guest.DecodeNoChoice} checks this by following every definition the decoder
unfolds to.

\paragraph{The batching on its own} (\lean{BatchingSound}). The batching of \lean{NodeRelation}'s fourth
condition is also proved sound as a verifier in its own right, in the RPM: Keccak-256 is the sponge
over $\pi$, Keccak-f is $\pi$, and it accepts when the sumcheck closes and the claim it outputs
holds of $\widehat{B}$ (\lean{runBatching} of \lean{boundedBatchingProgram}). Fix a bytecode $B$ of power-of-two
length and $M \le 2^{64}-1$. An adversary making $Q_A$ queries to $\pi$ and $\pi^{-1}$ outputs a
proof. The probability that the batching accepts it while its proof stream begins with fewer than
$M$ children of the bytecode's shape, one of whose claims (fresh or carried) is false
(\lean{SomeChildClaimFalse}), is at most
\[
\boxed{\ (Q_A + Q_V + 1)\cdot M\cdot 2^{-191} + 5\,(Q_A+Q_V)^2\cdot 2^{-256}\ }
\quad\text{for } Q_A \le 2^{128},\ Q_V \le 2^{96},
\]
where $Q_V$ (\lean{batchingQueryBound}) is the batching's own query bound for $M$ children (about
$2^{68}$ for $G$'s bytecode at $M = 2^{64}-1$; \lean{batch_sound_holds}, \lean{lean_vm}). The factor $M$ comes from
the single challenge $\lambda$. Weighted by the powers of $\lambda$, the gaps of the fewer than $2M$
claims (claimed minus true value) form a polynomial in $\lambda$ of degree below $2M$, nonzero when
a claim is false. It vanishes at fewer than $2M$ values of $\lambda$, against at most $2$ values for
a sumcheck round's challenge. For $G$'s $16$ children, $M = 17$.

\subsection{What the soundness theorems do not give}\label{sec:notgive}

They speak about one node. A claim the root holds through a child carries no knowledge by itself:
the deferring verifier reads the bytecode only through its length and takes the bytecode's value at
the child's point from the witness (the fresh claim $f_i$), which no end statement requires true, so
a proof of any program of $G$'s length, under the node's seed, makes a child of any statement. A
child's claims mean something only once its fresh claim is true. That needs the root's deferred
claim recomputed, as the outer verifier does (\lean{AggregateSound} assumes it), and the batching
sound inside the circuit at every level, so that a true batched claim makes the children's fresh and
carried claims true; and to conclude from an accepted root that every claim held at the leaves, one
would need, at each internal node, the soundness of the children's proofs \emph{as the guest
program verifies them}: with the real Keccak-256 and Keccak-f, not with $\pi$. That is the
Fiat--Shamir heuristic for an instantiated hash, and it is not proved. Likewise \lean{BatchingSound} is
the batching outside the circuit, with Keccak-f $= \pi$; it does not compose with the in-circuit
statements, whose \texttt{KECCAK} instruction computes the deployed Keccak-f[1600], so soundness
across recursion levels does not follow from it.

\subsection{Completeness}

\paragraph{The hypotheses,} on a statement $s$ and a witness $w$ with
$\mathrm{NodeRel}(B, iv_G, s, w)$, under the deployed seed:
\begin{enumerate}
\item \lean{DeployedLimits}, the limits the guest program enforces on the node: each declared list
is a sub-multiset of the raw signatures' claims and the children's lists (a claim declared $n$ times
is held $n$ times, each raw signature or child's entry used once); at most $16$ children; the
coverage table, one slot per raw signature and per entry of a child's lists
(\lean{coverageSlots}), shorter than $2^{16}$.
\item Every child carries an honest proof (\lean{HonestChild}): its fresh claim is true of the
bytecode (\lean{BytecodeClaim.Holds}); its proof is the one the named honest prover
\lean{LeanVM.leanVmHonestProver} makes with the deployed Keccak
($2^{25}$ nonces per proof of work) of an execution of $G$ of
committed size above $2^{21}$ (so of stack log $\lceil\log_2 \mathrm{size}\rceil \ge 22$, the floor
the guest program checks and leanVM's aggregator pads every aggregate to) on
$\mathrm{dig}_{iv_G}(s_i)$; and the verifier that also refuses
every zero challenge (\lean{verifierRefusingZero}, through
\lean{VerifierProgram.refusingZeroChallenge}, which fails on every zero challenge the verifier
program samples) accepts it with the deployed Keccak. The guest program divides by the fold and tail
challenges and by the batching coefficient $\lambda$ at the stacked opening; refusing every zero
challenge is slightly stronger, each challenge being zero with probability $2^{-192}$. An honest
proof is refused with probability at most $2^{-126}$ in the RPM (\lean{HonestProofRarelyRefused}
below).
\item The budget: a bound on the run's size, below.
\end{enumerate}
What the guest program checks of a child is in \lean{lean_vm} (\lean{AcceptableChild}): the
statement's deferring-verifier conditions; a stack log of at least $22$ announced (the guest program
has opening code for stack logs $22$ to $28$ only) and a proof stream of at most $8192$ field
elements; at each query step of its deferring verifier, the Merkle openings agreeing wherever they
share a node of the tree (an honest prover's openings, all from one tree, agree); and no zero
challenge in its deferring verifier. \lean{lean_vm} proves that honest children meet it
(\lean{guest_child_complete}, with \lean{freshClaim_unique}: the deferring verifier accepts a proof
with at most one true claim, so the child's fresh claim is the one its run evaluates).

\paragraph{Honest proofs are rarely refused} (\lean{HonestProofRarelyRefused}). For the same named
prover \lean{LeanVM.leanVmHonestProver}: in the RPM, with $2^{25}$ nonces per proof of work, it
makes no proof, or the verifier that also refuses every zero challenge (\lean{verifierRefusingZero})
rejects its proof, of any valid execution of committed size at most $2^{28}$, at $1 \le \rho \le 4$,
with probability at most $2^{-126}$. The guest program checks a child with the deployed Keccak, so
the bad events (a proof of work with no nonce within its fuel, a zero challenge) are bounded in the
RPM for the same prover and check, and their absence at the deployed Keccak is what
\lean{HonestChild} asks. Completeness thus holds level after level as far as the deployed Keccak
behaves like $\pi$ for these events; that step is the model's assumption, not a theorem. Not stated
either: that honest batching hints exist, that batching true claims gives a deferred claim that
holds, and that the outer verifier accepts an honest root (see the last section).

\section{What is not proved}

\begin{itemize}
\item The \texttt{KECCAK} instruction a program executes computes the real Keccak-f[1600], not
$\pi$: the RPM idealizes the proof system's hash, not the guest program's computation. It thus
excludes, by construction, programs that evaluate their own proof's Fiat--Shamir duplex
(Khovratovich, Rothblum and Soukhanov, 2025); the assumption is that Keccak-f[1600] behaves as a
random permutation even to programs that compute it. Statements
about the guest program's own execution use the deployed Keccak-256, under the assumption that no
one finds a Keccak-256 collision.
\item Soundness across recursion levels (Section~\ref{sec:notgive}); completeness across levels
holds only through \lean{HonestProofRarelyRefused}.
\item That the cost machine's prices are honest (Section~\ref{sec:zkvm}): trusted, as the
statement's model of computation (a one-limb operation, the carry-less product included, at one
unit: a few instructions of a 64-bit CPU).
\item Security against quantum adversaries (a quantum random-permutation model), for the
signature schemes and for leanVM's Fiat--Shamir: every statement is about classical adversaries.
\item LeanDA's code binding for an argument whose relation uses the deployed Keccak-f[1600] rather than $\pi$ (leanVM's in-circuit DA check), and the link from the guest
program's DA check (\lean{Da.MatrixWitness.Opens}) and the outer verifier's derivation of the challenge to
LeanDA's code binding.
\item That a parent can always form its witness from honest children (the batching hints exist),
that batching true claims gives a true deferred claim, and that the deployed outer verifier
(\texttt{EthereumProof::verify}) accepts an honest root.
\item Completeness for children whose proofs are not \lean{LeanVM.leanVmHonestProver}'s with the
deployed Keccak (the Rust prover's, say), or under another seed than the deployed one:
\lean{HonestChild} names the proof.
\item Which programs $P$ and $D$ are: the statement takes them as parameters within their size
bounds and budgets; the end theorem holds at \lean{lean_vm}'s compiled \lean{transcriptExtractor}
and \lean{LeanVM.Guest.End.decode} (\lean{LeanVM.Cost.compiledKnowledgeExtractor},
\lean{LeanVM.Cost.compiledGuestWitnessDecoder}).
\item That the extracted execution is the one the proof commits to: \lean{KnowledgeSoundness}
asks only for some valid execution of $\mathit{prog}$ on $x$, and \lean{AggregateSound} decodes that one.
\item That a valid execution of $G$ has fewer than $2^{51}$ steps (Section~\ref{sec:guest}): argued,
not a Lean theorem (\lean{lean_vm} proves fewer than $2^{128}$, \lean{steps_lt_replayFuel}); the
decoder's budget has no cap on the steps, and its constant prices the witness at the bounds a valid
execution's asserts and its children's accepted proofs give ($16$ children, each with $65535$
claims of each scheme and a cursor of $8192$ words), not at the run's.
\item That the size bounds exclude a table of witnesses for every program: literals count toward
size, and the bounds are tight only for programs written like the compiled ones (a decoder
written differently could pack the guest's frame-cell table about three times tighter, freeing
room for about $1270$ signatures' encodings, or compute it from its input, freeing room for about $1900$).
\item How $D$ computes the witness: the statement accepts any program that computes it from the
execution within its budget, not only one that reads it off the memory.
\item A tight extractor budget: it is $2^{81} + O(N\log^3 N)$, priced at the worst shape.
\item The Rust verifier, prover and guests. They are tested against the Lean specification: the
verifier differential fuzz; the wire differential (the Lean decoding against the Rust
\texttt{Proof::from\_bytes} on honest wire proofs and their mutations); the prover differential (the Lean prover's proofs byte-identical to the
Rust prover's, accepted by both verifiers, every mutation rejected by both), which does not yet
include an execution of the guest program; the guest-diff check on real aggregations; and the node
vectors.
\item Witness generation: the Lean prover takes the execution (memory and hints) as input, checks
it, and computes the committed columns from it, but nothing in Lean runs a program on its private
inputs; in the prover differential the executions come from leanVM's Rust interpreter.
\item The Lean prover's speed: compiled, it takes about $24$ times as long as the multithreaded
Rust prover on the test corpus ($2876$ s against $119$ s), and no complexity bound is proved.
\end{itemize}
