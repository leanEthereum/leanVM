# AGENTS.md

## What this is

A RISC-V (rv64im) virtual machine and the SNARK that proves its execution. Proofs are not zero knowledge. Every rv64im instruction is proven, plus custom ones: the BLAKE2s compression (`blake2s rs1, rs2`) and the multiplication in the extension field `E = GF(2^192)` (`extmul`, `extmac`, `extmulk`, `extmack` and their checked forms, each `fd, fs1, fs2` on the 128 extension registers `f0..f127`, a `k` form's second operand a word in an integer register). A program is a guest's ELF file (`programs/<name>/guest`, Rust built for `riscv64im-unknown-none-elf`, loaded by `rv::Guest::from_elf`) or a text assembled by hand with `leanvm_core::rv::asm`; a run is proven on an advice (a region of memory the prover fills), and its statement is the program's digest and the output (`a0..a3` at `exit`); there is no public input. One run is one proof: a run whose witness exceeds one commitment (`pcs::MAX_MU`) is refused up front with `ProveError::TooLong` (re-exported as `leanvm::ProveError::TooLong`), continuations being unimplemented.

- `doc/leanvm/` is the LaTeX project describing the machine ISA and the snark that proves it. Its root is `doc/leanvm/main.tex`; build it with `cd doc/leanvm && latexmk -pdf main.tex`, which writes to the gitignored `doc/leanvm/.build/`. Sections live in `doc/leanvm/body/`, numbered `01`..`08` plus the lettered annexes `a` (ring switching), `b` (the PCS), `c` (Flock), `d` (novel basis and additive NTT), and `e` (recursion), and every symbol is defined once in `doc/leanvm/preamble/macros.tex`. If latexmk fails oddly (a bibtex error, or a missing `main.log`) right after inputs are renamed or `refs.bib` is edited, remove `doc/leanvm/.build` and rerun; it has not reproduced on unchanged inputs. **Drafting one section:** each section file carries a `% !TeX root` comment pointing at its generated driver in `doc/leanvm/drafts/`, so the LaTeX build key (`F5`, or the extension's `cmd+alt+b`) compiles only that section, numbered as in the full document and with cross-references and citations resolved against `.build/main.aux`; in `main.tex` the same key builds everything. Run `doc/leanvm/make-drafts.sh` after adding, renaming or renumbering a section.
- The one hash function is BLAKE2s, in `primitives::hash`: scalar, streaming, and a lane-transposed batched form for the PCS Merkle tree. The VM's compression instruction is the generic gate-list circuit in `rv::semantics::hash` (`Class::Hash.circuit()`), proven like every other class; its witness is word arithmetic in `rv::semantics::hash` (exported as `rv::circuits::blake2s_witness`), pinned to the walk of the gate list by a test. `flock::hash` is the hand-optimized circuit of the same function with its own witness kernels, kept as flock's throughput benchmark and used by nothing else: it builds only for tests and flock's `bench` feature.

## Layout

The root `Cargo.toml` is workspace-only: the libraries are in `crates/`, the CLI in `bins/`, the guest SDK in `sdk/`, the programs' host crates in `programs/*/host`. Dependency order, leaves first:

| crate             | role                                                                   |
| ----------------- | ---------------------------------------------------------------------- |
| `parallel`        | thread pool (below)                                     |
| `primitives`      | field kernels (NEON/AVX), bit transposes, multilinear helpers, streaming stores |
| `bench`           | benchmark harness for the CLI and the `benches/` targets: the global allocator they install (`Counting` over `Jemalloc`, below), `Plan` (warmup, repeats, cooldown), `Timing`, the `--tracing` trace tree, Bencher Metric Format output (`Metric`, `bencher_json`); never linked by the prover |
| `leanvm_guest`    | `sdk/`, the guest SDK every program links: `read::<T>()` and `commit(&value)` (the only I/O a guest does), `Words`, `PublicValues`, `advice_words!`, the custom instructions (`precompile`), the `Blake2s`, `Template` and `hash_with` hashers, the extension field (`ext::Registers`: `mul`, `mul_add`, `mul_base`, `mul_add_base`, `mul_add_is_zero`, `mul_add_base_is_zero` and `load`, on extension registers named by const number, the constants `ONE`, `Y`, `Y2`), Keccak in software (`keccak`: the permutation `f1600`, `RATE`, `keccak256` over words), and `link.ld`, the memory map; off the VM `Blake2s`, `Template`, `hash_with`, `ext` (its `Registers` then holding the cells itself), `keccak`, `Words` and `PublicValues` remain, with `Run`, what a host hands its guest |
| `fiat_shamir`     | VM-native `FiatShamirState` + prover/verifier transcript, the proof body's encoding, and the verifier's arithmetic (`arith`: `Arith`, `Verifier`, native over `VerifierState`), which the native verifier and its rows share |
| `pcs`             | additive NTT over `K`, Merkle, ring switch, stacked WHIR; the stacked opening ring-switches all its claims as one family (`stack_open`: a challenge `gamma_rs` combines their slices before the map is drawn, each claim's scale inside the map, so the claims' points need not be related; `ring_switch::RingFamily` draws the family's challenges, and its `RingShare` gives the target and the weight in the map's Frobenius form; the opening's verifier is generic over `verifier::OpeningVerifier`, a `Verifier` that also reads roots, samples queries and opens Merkle rows) |
| `flock`           | batched R1CS over GF(2): zerocheck + lincheck; gate-list circuits over word ports (`circuit`), the u64 adder and multiplier in them (`gadgets`), the BLAKE2s circuit (`hash`) |
| `leanvm_core`     | the RISC-V machine (`rv`: decoder, class semantics and circuits, interpreter, assembler, ELF loader) and its arithmetization: tables, bus, constraints, `cpu::Prover::prove`, `cpu::Program::verify`; the recursion machine (`rec`) |
| `leanvm`          | the public API: re-exports of `leanvm_core`, the prover/verifier setup, and aggregation trees (`aggregate`) |

`crates/leanvm` is the public API and the only thing a user imports: every other crate is `publish = false`, and `leanvm` is re-exports of `leanvm_core` alone, so a user-facing type lives in the core under its public name and is re-exported there, never wrapped. The API is `Program` (`from_elf`, `new`, `measure`, `verify`), `Prover { rate }` and its `ProvenRun`, `Proof`, `Output`, and `aggregate` (`rec::tree`: `Tree`, `TreeShape`, `Leaf`, `LeafShape`, `TreeProof`, `CircuitStats`); each operation returns its own error (`ProveError`, `VerifyError`, `DecodeError`, `TreeError`), and both proofs' bytes start with one header (`envelope.rs`: magic, then version). What the core's integration tests, benches and the program hosts need beyond that (`Program::execute`, `verify_core`, `verify_to_raw`, `check_deferred`, `digest`, `fs_seed`, a `Proof`'s transcript `.0`, and the machine's and tables' types and constants re-exported at the core's root) is `#[doc(hidden)] pub`: callable across the workspace, absent from the documented API. The core's modules are private, so rustc flags whatever nothing reaches. The CLI is its own package, `bins/leanvm` (`leanvm-cli`, binary `leanvm`), run with `cargo leanvm <subcommand>` (a `.cargo/config.toml` alias for `run --release -p leanvm-cli --`): `fibonacci`, the benchmark, `guest <elf> --advice a,b,...`, and `aggregate`, an aggregation tree over copies of one leaf proof.

`programs/` holds the programs a guest runs, one folder each, and has no `Cargo.toml`. `programs/<name>/guest` is the guest, a standalone package and its own workspace, with its own `Cargo.lock`, toolchain file (a dated nightly with `rust-src`) and `.cargo/config.toml` (target `riscv64im-unknown-none-elf`, `build-std = ["core"]`, `-T../../../sdk/link.ld`, the release profile), so `cargo build --release` in that folder builds it; the eleven copies of the toolchain file and config are identical, so change them together. **A guest's I/O is its `main` and nowhere else**: `main` reads the advice (`read`, and `read_unchecked` for a library's `repr(C)` word types, whose layout the host writes with `as_words_unchecked`), calls its library's ordinary functions, and `commit`s the public values; the library knows nothing of the VM. `programs/<name>/host`, where a program has one, is its code off the VM, a member of the root workspace: it builds the guest's advice and the output the guest must give (a `leanvm_guest::Run`, the output being `PublicValues` over what `main` commits), exposes the guest's `ELF`, and holds the tests that pin the guest's library to its reference implementation and run the guest on the interpreter; it knows nothing of proving or reports, which are the CLI's (`bins/leanvm/src/workload.rs`). A host depends on its guest's library by path, so the root `Cargo.toml` names that guest in `exclude` (which takes no globs). The runtime every guest links is not a program but the VM's side of the contract with its guests, so it has a top-level folder of its own: `sdk/` (`leanvm_guest`: `_start`, `read`, `read_slice` and `read_unchecked`, which take values from the advice in place with no copy or decoding, `commit`, which streams words into a BLAKE2s whose digest is the run's four output words at exit, through a static block the instruction compresses in place (a word is a store and a pointer bump; the static is reached only by its address, never by a reference), `advice_words!` sizing a guest's advice region, BLAKE2s over the custom instruction as a streaming `Blake2s`, a `Template` rehashed in place (`Template::chain` for a hash chain) and `hash_with` (`hash_prefix_with` for a message ending inside its last word), a one-shot message written into the instruction's block, a panic that is `unimp`), whose `precompile` module is the only place a custom instruction is written (`.insn r`: `blake2s_compress`, public for a guest that wants the bare compression, the crate's own `blake2s_chain` loop under `Template::chain`, and `ext` and `ext_base`, under the safe `ext` module) and its `link.ld`, the memory map, which must match `rv::TEXT_BASE`, `rv::ADVICE_BASE` and `rv::RAM_BASE`. It is a root workspace member, built natively there, and what a guest author outside this repository would depend on. `programs/build.sh` builds every guest into one target directory and refreshes the checked-in ELF fixture `programs/<name>/<name>.elf` that the tests, the hosts and the CLI load. **Rerun `programs/build.sh` after touching a guest or the runtime**: nothing rebuilds the fixtures, so CI would keep testing the old ELF and say nothing. The toolchain files pin a dated nightly, so the same sources and lock files build the same fixtures byte for byte; moving to a newer nightly is a change of its own, made in all eleven toolchain files at once with every fixture rebuilt in the same commit, since a new compiler moves the cycle counts. CI does not diff them. The root `.cargo/config.toml` scopes `target-cpu=native` to `cfg(not(target_arch = "riscv64"))` because the guests inherit it. Atomics are why the target is `im` and not `imac`: the builtin target has no compare-and-swap, so a dependency needing one does not compile.

**The workload programs** `leanxmss`, `leansphincs`, `leanda`, `falcon`, `stateproof` and `shielded`: each guest is a `no_std` library and its `main`, and each has a host.

- Off the VM, `leanvm_guest` keeps its hashing (`Blake2s`, `Template`, `hash_with`, `keccak`), `Words` and `PublicValues`, in portable Rust. So a host runs its guest's library natively, to sign, encode and compute the output the guest must give.

- Values are `u64` words, never byte arrays. A byte-aligned word costs eight `lbu`. The advice entries are `repr(C)` word structs, read in place.

- Keep a hash's length known at compile time (`&[u64; N]`, `#[inline(always)]`). Each call then folds to its stores and one `blake2s`. A runtime length brings back `memcpy` and `memset` calls, which cost more than the hash.

- **Pick the hashing form by what repeats.** A hash repeated in one shape (a chain step, a tree node, a few-time leaf, an encoding) is a `Template`: the instruction writes only the compression, so the words the next hash shares (the IV, the parameter, the padding) stay in its block and each hash writes only what changed. A message ending inside its last word (leanSPHINCS's encoding, whose counter is 4 bytes) is a `Template` too, its bytes past the end zero and its length given to `digest_prefix`. A one-shot message of words (a tweak hash, a one-time key's leaf over its chain ends, leanSPHINCS's few-time key over its roots) is `hash_with`: its `Stream` writes straight into the block the instruction reads, absorbing a full block only once more of the message follows, and `write_each` takes the pieces of a message produced piece by piece from a closure and puts a block's arrays at fixed places, so no array of them is built first. A hasher that lives across calls stays on `Blake2s`: `Blake2s` copies its message into a fresh block at each compression, which is what keeps a long-lived hasher's state in registers; a hasher owning its block loses that, since once the instruction has its address the compiler neither removes copies of it nor folds what it holds.

- A field narrower than a word, or a slot picked at run time, is `Template::write` at a byte offset: a word index costs a shift to become an address. A tweak's position and index are 32-bit fields, so a hash that changes only those writes two `sw`s. leanXMSS's Merkle path is unrolled this way, its child and sibling placed by the level's bit with no branch.

- A hash chain, each step's digest the next step's value and a counter field its position, is `Template::chain` (both signature schemes' chains): on the VM its loop is written by hand in `precompile.rs`, eight instructions a step with the compression, which is what the compiler's own loop could not reach. A guest calls `Template::chain`, never the loop, so the loop can change under it. Everything else stays Rust, unrolled where a constant index makes a shift or an offset free (leanXMSS's 42 chain ends, its 32 Merkle levels). leanSPHINCS's tree paths go the other way, one loop that is never inlined (`fold`): its tweak's level is the high half of a word, which a loop keeps as a running sum, where an unrolled path builds each level's word as a constant with a shift.

- **A saved instruction pays only where it takes a table under a power of two** at the size proved: every class's table pads to a power of two, so read `bench --cycles-only`'s per-table heights, not the total. A rewrite that trades ALU rows for SHIFT or LOAD rows can double another table.

- rv64im has no carry-less multiply, so leanDA's membership check uses the extension-field precompile, which works on extension registers and reads no memory: per symbol `ld` its word and `L_x`'s three limbs, make the word an element (`mul_base` by `ONE`), and add its product by each limb to one of three accumulators (`mul_add_base`); the sum is `f3 + y f4 + y^2 f5`, checked zero by `mul_add_is_zero`. Four `ld` and four EXT rows a symbol: watch LD's height.

- `falcon` is Falcon-512 verification as the round-3 specification defines it, integer-only (signing, with its floating point, is the host's: `tide-fn-dsa`'s PQClean mode, seeded so the advice never moves). The NTT is three radix-8 passes per transform, eight coefficients in registers for twelve butterflies; a product by a twiddle is Plantard's (two `MUL`s, `ntt::mul_twiddle`), a product of two transforms Montgomery's (three, `mulw` written as such since LLVM splits it into `mul` and `srai`), and no sum is ever reduced: 64-bit registers hold every intermediate the bounds in `ntt.rs` allow. Hash-to-point leaves its samples unreduced and the final Montgomery reduction takes `c` and the product together (`ntt::sub_centered`): a loop subtracting `q`, or a centering written as one, compiles to a `MULHU` division. SHAKE256 is a sponge over the SDK's Keccak-f[1600] (`leanvm_guest::keccak`), XKCP's lane-complemented round, at the instruction floor of rv64im without rotates.

- `stateproof` is an Ethereum L1 state proof as `eth_getProof` (EIP-1186) gives it: the block hash is keccak256 of the header, whose fourth field is the state root; each read walks the state trie to an account at `keccak256(address)`, then its storage trie to a slot at `keccak256(slot)`, a missing key proven absent. keccak256 is the SDK's (`leanvm_guest::keccak`, software, no precompile), absorbing a node's bytes as little-endian lanes; the walk reads only the RLP headers it needs, a hash at any byte offset assembled from two words since a misaligned load traps, and refuses an embedded node, which no trie keyed by 32-byte hashes has. The fixture is real (`host/fixture/mainnet.json`, written by `fetch.py`: one finalized block's header and `eth_getProof` of slot 0 for 32 accounts), so a read costs what it does on mainnet.

- `shielded` is a privacy-pool spend, the statement of soispoke's minimal shielded pool (BLAKE2s edition, https://github.com/soispoke/evm-spend-challenge/blob/main/SPEC.md): two notes in, two out, a depth-20 tree, the nullifier bound to the note's index, values balancing over `u128` with no wraparound, one statement digest out; the signature, the root's freshness and spent nullifiers stay on chain. Every hash is a one-byte tag then fixed-width fields, so each field sits one byte off its word: `message::Tagged` writes a word as `carry | next << 8` straight into the instruction's block, and `hash_prefix_with::<LEN>` takes the exact byte length, the multi-block twin of `Template::digest_prefix`. The host makes spends in the specification's 1,680-byte input format (three shapes: a transfer, a withdrawal, a dummy input) and lays them out as `repr(C)` words; its test pins the guest to a byte-level reference of the statement. The specification's own fixtures are not checked in (its repository has no license); the guest reproduces their digests and refuses their invalid cases with the same rule.

- The KATs in each host pin the first five to the reference implementations (Falcon's to NIST's round-3 vectors, `programs/falcon/host/kat/`; the state proofs to what a mainnet node answered and to `alloy-trie`'s proofs).

`conformance/act4/` holds the official RISC-V architectural tests ([ACT4](https://github.com/riscv/riscv-arch-test), riscv-arch-test 4.1.0 at `6e8a4512`), their `I` and `M` suites, 64 tests, for an `rv64im` profile with no misaligned access. ACT4 runs each test on the Sail reference model and builds it again with Sail's results inside, so that the ELF file checks itself. The configuration is `test_config.yaml`, `leanvm-rv64im.yaml` (for the unified database, UDB, which defines `MXLEN` through `Sm` and so needs `Zicsr` claimed too: `rvmodel_macros.h` leaves `STANDARD_SM_SUPPORTED` undefined, so no test touches a CSR), `sail.json` (Sail's regions: leanVM's text and RAM), `link.ld` (the code in the text, everything else in RAM, RAM the smallest power of two holding the image) and `rvmodel_macros.h` (a test ends in `exit` with the output zero on a pass, `a0 = 1` and `a1` the caller when the framework halts on a failure). A failing check's handler reads the check back from the text, which leanVM cannot read, so it traps there, and `leanvm_core/tests/verifiers/act4.rs` reports the check's description, the value computed and Sail's. `generate.sh` builds the Docker image of `Dockerfile` (Ubuntu 24.04 by digest, riscv-gnu-toolchain 2025.08.08 with GCC 15.1, Sail 0.13.1 and mise 2026.9.17 by checksum, the Ruby and Python tools locked by riscv-arch-test itself) and generates `elf/I` and `elf/M` byte for byte: it strips the symbol naming the compiler's temporary object file, which is random, and clears the compressed-instructions flag that ACT4's alignment directives set though nothing is compressed. **The ELF files are not checked in** (`elf/` is ignored), so `act4.rs`'s two tests are `#[ignore]`d: run `conformance/act4/generate.sh` once (Docker), then `cargo test --release -p leanvm_core --test verifiers -- --ignored act4`. CI (`.github/workflows/riscv.yml`) runs them on every PR, caching the generated files under a hash of every file in `conformance/act4/`, so the image is only built when one of them changes. Left out by design: `Misalign` (a misaligned access traps, and the configuration says so), `Zicsr` (no CSRs), `Zifencei` (no self-modifying code), and `Zmmul`, whose tests are M's multiplication tests again. `act4.rs` runs every test on the interpreter, proves each and checks the proof with the Rust verifier, and with the Python verifier the first test to reach each table.

## Building / Testing / Formatting

- `.cargo/config.toml` pins `-C target-cpu=native` and `-D warnings` for rustdoc
- always run in `--release` mode any test or benchmark touching the VM
- **One test binary per crate, not one per file** (`leanvm_core/tests/verifiers/main.rs`).

An x86-only arm never compiles on an Apple dev machine, so a typo in one ships. Lint the other target before pushing anything `cfg`-gated (CI's "Clippy on the AVX-512 backends" step runs the same command):

```bash
RUSTFLAGS="-C target-feature=+avx512f,+avx512bw,+avx512vl,+avx512vbmi,+vpclmulqdq,+pclmulqdq,+gfni,+avx2,+aes" \
  cargo clippy --release --workspace --all-targets --target x86_64-unknown-linux-gnu -- -D warnings
```

It needs `rustup target add x86_64-unknown-linux-gnu` and nothing else, since clippy does not link. Use `RUSTFLAGS`, not `CARGO_TARGET_X86_64_UNKNOWN_LINUX_GNU_RUSTFLAGS`: cargo lets a set `RUSTFLAGS` (as in CI) beat the target's, and it also replaces the pinned `target-cpu=native`, which no cross target recognizes. The `x87` note is the bare cross ABI, not a finding. To confirm an arm is really being reached rather than silently skipped, drop a `compile_error!` in it and watch the lint fail. The x86 kernels have AVX2 arms too, with and without GFNI, which CI's "SIMD" legs build and test: lint them the same way with `-C target-cpu=x86-64-v3 -C target-feature=+vpclmulqdq,+pclmulqdq`, and with `+gfni,+aes` added.

```bash
cargo testall                     # release workspace tests
cargo clippyall                   # clippy, -D warnings
cargo docall                      # rustdoc, -D warnings
cargo machete --with-metadata     # unused dependencies, dev ones and the guests included
cargo fmt --all                   # max_width = 120
ruff format --line-length 150 python-verifier/verifier.py   # and `ruff check` it
```

Heavy benches are `benches/` targets (`harness = false`), which `cargo test` never builds; run one with `cargo bench -p <crate> --bench <name>`: flock's `hash_batch` and `arithmetic_batch` (with `--features bench`, the feature that builds the code only they and the tests run; an argument picks the operations, e.g. `-- mul_wrapping`), pcs's `throughput` (commit, open, and the commit's NTT alone), primitives' `hash_throughput` and `kernels` (the field products, squares and inverses, `mul4`, and the bit transposes, each alone on one thread, as time per call). All of them, and the CLI, time through `bench::Plan` (one warmup pass, then `BENCH_REPEAT`/`--repeat` measured ones, each after a cooldown, reported as mean ± 95% interval). With `-- --json` each prints, in place of its report, Bencher Metric Format JSON, what CI compares.

**Where a proof's time goes is the `tracing` span tree, and only that**: `--tracing` on the CLI, `BENCH_TRACING=1` on the `benches/` targets, `RUST_LOG` to change the level. It records the final measured pass only (`bench::suppress_tracing`). Each span shows its time, its share of its parent's, its heap peak (the most bytes live while it was open, above those live when the root opened, so a parent's equals that of the child holding it) and the allocations made in it. A new stage worth timing gets an `info_span!` (in `leanvm_core`, `stage!`), never an `Instant` behind an env var. To look inside one stage, see Profiling below.

## Benchmarking

The benchmarks we care about:

- `cargo leanvm fibonacci --n 2000000 --log-inv-rate 1 --repeat 3` (Fibonacci mod 2^64, on registers)
- `cargo leanvm guest programs/hash/hash.elf --advice 50000 --repeat 3` (the hash precompile, from a Rust guest)
- `cargo leanvm leanxmss --n 400 --repeat 3`, `leansphincs --n 104`, `leanda --blobs 1`, `falcon --n 28`, `stateproof --n 21`, `shielded --n 1020` (the Ethereum workloads and Falcon-512, the most one proof holds)
- `cargo leanvm aggregate --program leanxmss --n 400 --leaves 16 --arity0 4 --arity 4 --repeat 3` (an aggregation tree: each kind of node's rows, committed words and times, then the whole tree; the leaves are proven at `--leaf-log-inv-rate`, 2 by default, the tree's own proofs at `--log-inv-rate`)
- `cargo leanvm bench --cycles-only --markdown` (every program above, flock aside: RISC-V cycles and committed words, exact, no proof: `cpu::Program::measure`, which CI's `Counts` workflow, `counts.yml`, puts in each run's summary; and two aggregation trees over leanXMSS-400 leaves at `--leaf-log-inv-rate`, 2 to 1 (`cargo leanvm aggregate`'s default shape) and 4 to 1 (the tree above), each kind of node's rows per table and committed words, from its circuits alone: `LeafShape::measured` gives the leaf shape a measured run's proofs announce, so the tree's key needs no proof)
- `BENCH_REPEAT=3 FLOCK_N_LOG=18 cargo bench -p flock --features bench --bench hash_batch` (flock alone, on its hand-optimized circuit)
- `cargo bench -p primitives --bench kernels` (the field and bit kernels, one thread, time per call)

To compare a change with its base on this machine the way CI does, run `scripts/ab.sh`: it builds the working tree, uncommitted changes included, and the merge-base with `upstream/riscv-exploration` (in a temporary worktree with its own target directory, so the tree and its build are left alone), runs each benchmark on both in turns, and prints what moved as the PR's comment would (main's `pr_comment.py --dry-run`). A benchmark is named as in CI: a case of `proven()`, a `benches/` target's name in the script (`kernels`, `blake2s-batch`, ...), or `counts`, the exact counts. `--help` says the rest.

```bash
scripts/ab.sh hash-50000                    # a case of `proven()`, against the merge-base
scripts/ab.sh kernels --rounds 3            # a `benches/` target, 3 rounds a side
scripts/ab.sh counts leanxmss-100           # the exact counts, then a case
scripts/ab.sh --base HEAD~2 pcs-throughput  # against another base
```

## Profiling

The span tree says which stage the time goes to and which stage holds the heap peak, and it stays the only place for stage timings. Two tools look inside a stage, with no code change and no `perf`: gperftools' sampling profiler says which functions, and which of their callers, a stage's time is in; heaptrack says which allocation sites hold the peak heap. Start from the span tree, then profile the stage it points at.

Install them with the package manager (`apt install google-perftools heaptrack valgrind`, the last for `callgrind_annotate`, then `export L=/usr/lib/x86_64-linux-gnu`), or without root by unpacking the packages (Ubuntu 24.04's names; `ldd` on a tool names any library still missing, fetched the same way):

```bash
T=/tmp/prof-tools && mkdir -p $T && (cd $T && apt-get download google-perftools libgoogle-perftools4t64 libunwind8 \
  heaptrack libheaptrack libboost-program-options1.83.0 libboost-filesystem1.83.0 libboost-iostreams1.83.0 valgrind \
  && for d in *.deb; do dpkg -x "$d" root; done)
export PATH=$T/root/usr/bin:$PATH L=$T/root/usr/lib/x86_64-linux-gnu
```

**Function profile**: build with frame pointers, preload `libprofiler` into the CLI, read the profile with `google-pprof`.

```bash
RUSTFLAGS="-C target-cpu=native -C force-frame-pointers=yes" cargo build --release -p leanvm-cli --target-dir target/fp
LD_PRELOAD=$L/libprofiler.so.0 LD_LIBRARY_PATH=$L CPUPROFILE=/tmp/leanvm.prof CPUPROFILE_FREQUENCY=1000 \
  LEANVM_NUM_THREADS=1 target/fp/release/leanvm --cooldown 0 leanxmss --n 100
```

## Read-write arrays

The registers, RAM and the advice are read-write, by timestamped offline memory checking (`doc/leanvm` §sec:memchan). What to keep in mind before touching it:

- **A timestamp is an integer**, `2^40 | cycle << 5 | slot` read as the `K` word with those bits (`tables::SEED_CLOCK`, `CLOCK_START`, `LIVE_BIT`). **The clock rides the state tuple**, `(pc, ts)`, with slot zero, and a row's access in slot `k` carries `ts ^ k`, a column plus a constant, which is what lets one row touch the same cell twice (`add a0, a0, a0`). Slots are `rs1` at 0, `rs2` at 1, the RAM access at 2, `rd` at 3, and a row that skips an access leaves its slot unused (a load reads no `rs2`, a store and a hash write no `rd`); a hash row's sixteen block words take slots 2 to 17. Seeds are at cycle 0 (`2^40`), so the run starts at cycle 1: an access must be strictly later than the one before.
- **Each table has a second flock circuit, its clock circuit** (`tables::clock_circuit`, reference `tables::clock_step`): ports the row's clock `ts`, each access's previous timestamp `prev`, and `step`, all virtual columns of the table, packed in a witness of its own (`class_flock::N_FLOCKS` is 25: every class circuit, `tables::N_CIRCUITS` of them, then every table's clock circuit). An access pulls `(addr, prev, old)` and pushes `(addr, ts ^ k, new)`; the circuit checks `prev`'s bit 40 equals `ts`'s and, on a live row (bit 40 set), `prev < ts ^ k` over 40 bits; `ts`'s five slot bits are empty positions, forced zero, so the order check's `ts | k` is the `ts ^ k` the tuple carries. **Strictness is the soundness**: with `prev = ts ^ k` a read pulls the tuple it pushes and returns anything. The verdict goes to bit 41 of `step`, and the next clock is `ts ^ step`: one cycle on for a live row, `ts` itself otherwise, bit 41 set on a failure. Every timestamp port is 41 bits wide, so no row pulls a clock with bit 41, and the verifier requires the announced final clock to be live at slot zero with nothing above bit 40 (`CpuError::FinalClock`): a failed row leaves its next state unmatched, the exit row's included.
- **Padding rows have clock zero**, which lacks the live bit: their clock does not advance, so their state tuples close around a fill block, and their access in slot `k` pulls and pushes timestamp `k`, cancelling itself. The live-bit equality is what keeps them away from the run: a padding row cannot pull a seed, and a live row cannot pull a padding row's tuple. They are written out by `cpu::Program::execute`, not executed, and touch no memory. **The verifier's notion of a padding row is a clock without the live bit and nothing else**, so a prover may close such rows around any cycle of the program's own control flow rather than a fill block; that is inert too, and the fill blocks exist to make the fill exact, not to make it safe. Any new table has to keep this true: every memory tuple's timestamp must be `ts ^ k` or a `prev` its clock circuit checks, nothing else.
- **Two committed columns per array**: what it holds after the run, and each cell's last timestamp. What it holds before is public for the registers (zero) and RAM (`Coord::Sparse`: the image, then zeros, evaluated in time proportional to the image), and a third committed column for the advice (`ADV_INIT`), which is the prover's. RAM and the advice share `SEP_MEM`; they never share an address, every region's base being a multiple of its largest size (`rv::TEXT_BASE`, `rv::ADVICE_BASE`, `rv::RAM_BASE`), so word `z` of a region sits at `base ^ (z << 3)` and the seed block's address is the free `Coord::IntIndex`.
- **A padding row rewrites what it writes**, its `old` column set to its `new` (the register write's `vd_old`, the hash's `out_old`), which is why a row can never update a cell in place: the hash reads `h` and writes `out` in different words, since no chaining value is a fixed point of the compression.
- **A run is capped below `2^35 - 1` cycles** (`tables::MAX_CYCLES`): past that the cycle count would carry into the live bit. The executor refuses a longer run, and one commitment (`pcs::MAX_MU`) holds far fewer rows anyway. Soundness needs no row bound: a run whose clock wrapped could never reach a live final clock.
- `a_stale_read_unbalances_the_bus` is the soundness regression test (a forged run that serves an overwritten register), `a_forged_load_unbalances_the_bus` its RAM counterpart, `a_forged_store_unbalances_the_bus` the same for a store's `rs2` read (both for `ld`/`sd` and `lw`/`sw`), `a_doubleword_moves_its_value_unchanged` the binding of the word `LD` and `SD` move as a column, `a_misaligned_doubleword_names_no_cell` their bus address, `a_read_of_its_own_push_is_out_of_order`, `a_padding_row_cannot_pull_a_seed`, `a_live_row_cannot_pull_a_padding_tuple`, `the_final_clock_cannot_carry_a_failure` and `a_clock_with_slot_bits_cannot_read_its_own_push` (in `tables/clock.rs`) the clock circuit's checks, `a_write_to_x0_unbalances_the_bytecode_read` the zero in `x0`, `a_forged_bytecode_read_unbalances_the_bus` and `a_wrong_multiplicity_unbalances_the_bus` (in `crates/leanvm_core/src/cpu/program.rs`) the bytecode lookup's, `a_forged_extension_product_is_refused` and `a_forged_extension_padding_row_is_refused` the extension-field identities' (a forged product whose bus balances, live and padding), `a_checked_extension_product_is_zero` the checked form's, `a_forged_extension_operand_unbalances_the_bus` and `a_base_field_operand_has_no_high_limbs` its registers' accesses, and `leaf::tests::unmatched_leaves` (test-only, taking the producer alongside the push and pull blocks) names the tuples a forged run leaves unmatched, which says more than a failing proof. `leanvm_core/tests/verifiers/programs.rs` holds the hand-assembled programs checked by both verifiers, `guests.rs` the Rust guests.

## The RISC-V machine

`leanvm_core::rv` is the machine, `leanvm_core::tables` and `leanvm_core::cpu` prove it. What to keep in mind:

- **The program is public, so decoding is free.** `rv::Entry::decode` turns each word into an `Entry` once: an instruction class, a `flags` word selecting what the class's one function does, the three register cells the row touches, the immediate already sign-extended, and the branch or jump target. `LUI`, `AUIPC` and `JAL`'s link fold to constants added to `x0`, `JALR` is the ALU's flags `INDIRECT | ALWAYS`, `ECALL` is a jump to the halt slot, and everything rv64im does not define (reserved shift encodings, `EBREAK`, CSRs) is an illegal entry. The bytecode lookup returns those fields; no table ever decomposes an instruction word. An entry whose class has no table has tag zero, which no row can read.
- **The statement is about the decoded table**, so the rules that make it RISC-V are checked where a table enters, on both sides (`rv::Entry::is_well_formed` in `Program::new`, `check_bytecode` in Python): two registers below 32 are read, the cell written is in `1..=32`, the successor is `pc + 4`, the flags are ones the class defines, only a branch, a `jal` or the exit has a jump offset (`dt`), a `jal` reads `x0` twice and has `pc + 4` as its immediate, and a field a class's table holds at a constant has that value (a load's `rs2` is `x0`, a store's and a hash's `rd` is `SINK`, a hash's immediate is 0, an `ld`'s or an `sd`'s flags are 0). The proof system itself is sound for any table.
- **`x0` is hardwired by the decoder.** Every entry names two registers read and one cell written. An instruction with fewer reads `x0`; one with no destination, or with `rd = x0`, writes `RegisterFile::SINK` (cell 32), which nothing reads. So cell 0 is never written, and its seed is zero. A class whose `rs2` is always `x0` (LOAD, LD) or whose `rd` is always `SINK` (STORE, SD, HASH) makes no such access at all: its table reads the register number off the entry as a constant (`ClassSpec::reads_rs2`, `ClassSpec::writes_rd`), and the interpreter skips that write.
- **Registers are a read-write array of their own**, under their own separator `REG`, so that loads and stores cannot reach them: 64 cells, a public zero seed, committed final values and timestamps, the same clock and clock circuit as memory. **The extension registers are a third one**, under `SEP_EXT`: 128 cells of three limbs each (`rv::ExtReg`, `ExtRegisterFile`), so a tuple has three values and one access moves one element; their seed is public (`1`, `y`, `y^2` in cells 0 to 2, zero elsewhere, `Coord::Public` columns), their final limbs three committed columns (`Shared::ExtFin0..2`) and their timestamps a fourth. A register's number comes straight from the bytecode, so an access needs no address arithmetic.
- **No integer addition happens on the bus.** A load's or a store's address is its circuit's word, with the misalignment bits ORed back in (`rv::WordAccess::bus_address`), so a misaligned or out-of-range access names no seeded cell and the bus does not balance; a doubleword's misalignment bits are all three low ones, so `ld`'s and `sd`'s word is the sum itself (`rv::WordAccess::word_address`). A hash row's block words are at `v1 ^ 8k`, which is `Coord::Sum(Col(v1), Const(8k))`, the XOR being the sum in `K`. The `EXP` lookup of the leanISA days is gone.
- **State is `(pc, ts)`**, `pc` the real byte address. Instruction `z` sits at `TEXT_BASE ^ (z << 2)` and the bytecode block's address coordinate is `Coord::IntIndex { base, shift }`, whose MLE is linear. Everything sits inside one 2 GiB window and below `0x7FFF_F800` for the code models' sake. A computed or misaligned jump target needs no check: the next row's bytecode read finds no entry.
- **A trap is the absence of a proof** (`rv::Trap`): an illegal or unmapped `pc`, a misaligned or unmapped access, an `ecall` that is not `exit`. Those are ISA behavior; the prover's own limits, the cycle cap and a run that would not fit one proof, are `cpu::ProveError::TooLong`. An illegal word follows the text, so a run falling off it traps instead of sliding into the padding blocks or the halt slot.
- **The halt is an exit.** The run ends on the last slot of the padded text, which is never executed. The verifier claims `a7 = 93` and `a0..a3 = output` on the committed final registers at the Boolean points naming them; the output seeds the transcript with the program's digest, which covers the decoded table, the entry and halt `pc`, RAM's and the advice's sizes and the image. Nothing the program fixes is read from the prover; the Python verifier gets the same things through `public.bin`.
- **The precompile is a class like the others** (`Class::Hash`, table `HASH`): `blake2s rs1, rs2` (custom-0 opcode `0x0b`, `funct3 = 1` on the final block, `rd = funct7 = 0`) compresses the 128-byte block at `rs1` (`h` in words 0..4, the result written to 4..8, the message in 8..16, `rv::Hash`), with the counter in `rs2` and the finalization word in the bytecode's flags; a base that is no word address traps, an unaligned one permutes the words deterministically (a guest bug, not a forgery). Its row has no `rd`, `imm` or `out` columns (constants `SINK` and 0 in its bytecode tuple), and eighteen accesses.
- **The extension-field multiplication is a class too** (`Class::Ext`, table `EXT`, `rv::Ext`), on the extension registers: custom-1 opcode `0x2b`, `funct3` bit 0 accumulating into `c`, bit 1 making `b` the base-field word of the integer register `rs2`, bit 2 requiring a zero result, which is how a guest asserts an equality (`Ext::ACCUMULATE`, `Ext::BASE`, `Ext::ZERO`, the flag word; a checked form that is not zero is `Trap::NonZero`). A register number is seven bits, its five-bit field then two bits of `funct7` (`fd`'s lowest); `fd < 3` is illegal, so the constants `f0 = 1`, `f1 = y`, `f2 = y^2` are never written, and a base-field `rs2` is below 32. **Two classes move an element between memory and an extension register** (`Class::Eld`, `Class::Esd`, tables `ELD` and `ESD`, custom-2 opcode `0x5b`): `eld fd, imm(rs1)` has a load's fields and `esd fs2, imm(rs1)` a store's, the register's number its five-bit field then `funct3`'s two low bits, whose third tells the two apart. Limb `k` is the word at `address ^ 8k` (`rv::ElementAccess`), so an element belongs on a 32-byte boundary; elsewhere the words are permuted, a guest bug and no forgery. Their circuit is LD's address adder, the three limbs moved are committed columns on both tuples as a doubleword's cell is (`ClassSpec::copies`, `Ram::Element`, `ElementColumns`), and a row makes five accesses: the base register, the extension register in slot 1 (a store's read) or 3 (a load's write), and the three words in slots 4 to 6. A word also enters as `1 * w`. The row makes three accesses, `a`, `b` and `c` in slots 0, 1 and 3 (`ClassSpec::wide`), each one tuple of three limbs, `c` rewritten, so `fd` may be `fs1` or `fs2`, and its register numbers are seven-bit fields of the register word. **It is the one class with no circuit**: `y^3 + y + 1` has its coefficients in `GF(2)`, so each new limb is a sum of products of limbs in `K`, and the table proves `c' = accumulate·c + a·b` by three degree-2 identities over its committed limb columns, then `base·b_1 = base·b_2 = 0` and `zero·c'_i = 0` (`ClassTable::identities`, `_ext_identities` in Python, eight in all), folded into the table sumcheck at the powers of `xi` past the two bus forms'. Its three selectors are committed 0-or-1 columns read off the bytecode entry, which holds them in its flags, immediate and jump-offset slots (`Lookup::columns`, `check_bytecode`): the program is public and checked, so no circuit splits them, and its clock circuit is the plain three-access one. A base-field `b`'s tuple is under `SEP_EXT + base·(SEP_EXT + SEP_REG)` (`Coord::Scaled`), the one bus separator that is not a constant.
- **The interpreter is the reference** (`rv::Machine`), tested against an executor written from the specification on byte-addressed memory that shares no code with it, and against the RISC-V architectural tests' `I` and `M` suites (ACT4, `conformance/act4/`). `cpu::Program::execute` is that interpreter plus the memory argument's bookkeeping.

## Instruction classes and their circuits

Addition with carries, comparisons, shifts, AND/OR, multiplication and division are Boolean relations no degree-2 identity over `K` expresses, so each instruction class is a Boolean circuit proven by flock (`doc/leanvm` Annex C), and a table only does plumbing. The extension-field product is the exception: it is degree 2 over `K`, so its table states it as identities and has its clock circuit alone.

- **One generic table, specialized by a `tables::ClassSpec`**: the state step, the bytecode read, the `rs1` read, the `rs2` read and the `rd` write where `reads_rs2` and `writes_rd` say so (exactly when the table's circuits take `v2` and give `out`, or for `ClassSpec::copies` move the word, which `ClassTable::new` asserts), and the class's RAM accesses (`Ram::None`, one cell `Read` or `Write`n at the circuit's address, or the hash's `Block`), every successor linear: a row pushes `pc4`, or for the class with control flow (`ClassSpec::control`, the ALU: branches, `jal`, `jalr`, the exit) `pc4 + jump`, its circuit's output `jump = taken·(dt ^ indirect·(sum ^ pc4))` (bit 0 left out of the indirect part) gating the bytecode's offset bit by bit, and `rd` receives `out`, which a `jalr`'s circuit sets to `pc4`. **A table with a class circuit flushes only linear tuples** (`ClassTable::new` asserts it), so its columns but its register numbers are sent at the bus point `zeta[..tau]` and that share comes off the bus totals (`Layout::reduce_tables`): the table sumcheck runs EXT, the bytecode's producer and each such table's forms on its register numbers alone (`ClassTable::summed_columns`, `summed_form`). A new class is a spec, a circuit beside its reference function in `rv::semantics` returned by `Class::circuit`, its flag-word type and reference function in `rv::semantics` (`Alu`, `Div`, ...), a no-op word in `cpu::filler`, its decoding, and the same in Python (`Table(...)` in `TABLES`, its gate list, its flags in `check_bytecode`). A class with no circuit (`ClassSpec::circuit` is `None`) goes after the circuit tables (`N_CIRCUITS`, so packed witness `t` stays table `t`'s class circuit), states its function as `ClassTable::identities` (which `cpu::batch` weights at the powers of `xi` past the bus forms', in table order), and takes any 0-or-1 selector it needs as a committed column read off the bytecode entry, where the public program fixes it; in Python its `Table` has `circuit=None` and its `identities`.
- **Every word the circuit reads or writes is a virtual column** of the table, living in the class's packed witness (`Q_BASE + t`, one committed column per table with a circuit, instance `j` being row `j`; the clock circuit's are at `Q_BASE + N_CIRCUITS + t`): `flags` and `imm` from the bytecode tuple, `v1` and `v2` from the register tuples, a load's `address` and `cell`, a hash's block words, `out`, an ALU's `dt`, `pc4` and `jump`. The bus is the whole binding. `FlockId::instance` asserts that what the circuit computed is what the interpreter did. A hint (`DIV`'s quotient and remainder) is a port in no column, and what a circuit asserts (`Word::Bad`) rides bytecode slot 10 (`tables::BAD_SLOT`), where the program is zero. **`LD` and `SD` (`ClassSpec::copies`) move a doubleword unchanged**, so their circuit is the address adder alone (`rv::Ld`'s, which `rv::Sd` shares, `k_log` 8) and the word moved is a committed column: `LD`'s `cell` is what its `rd` write pushes, `SD`'s `v2` what its RAM access pushes, one column on both tuples; their table has no flags column (the bytecode tuple holds 0). `LOAD` and `STORE` keep the narrower widths and make no gate for the 8-byte one: bit 2 of their bus address is empty, a load shifts only the cell's low half into place and a store only `v2`'s.
- **Circuits are gate lists over word ports** (`flock::circuit`): inputs, outputs, the constant, then products in the order they are made. A port bit with no gate is an empty row, hence zero, which is what makes a one-bit output a 0 or 1 field element: give such an output a word to itself and never put a free wire on its spare bits. What Rust and Python must agree on is the port layout and the ORDER PRODUCTS ARE MADE IN; XOR order is free. `alu_is_its_reference` pins a circuit to its reference function, and the end-to-end tests pin the Python mirror.
- **One batched reduction for all circuits, one opening for all**: one zerocheck and one lincheck over every packed witness under shared challenges (`flock::reduction::{prove, verify}`, `doc/leanvm` §flock:batch), every class circuit in table order then every clock circuit, after the exit claims, each circuit leaving a claim on its own witness. Both sumchecks are front-loaded like the table sumcheck: every circuit takes part from the first round and is done after its own rounds (the zerocheck binding each circuit's lowest variable first, lincheck its top inner coordinate, as for one circuit), and a done circuit adds only to the coefficient the round's claim fixes. Circuit `f`'s zerocheck takes `λ^f` and its lincheck `α^{4f}`; the zerocheck sends every circuit's `v_a, v_b, v_c` and checks their `λ`-combination. Lincheck sends each circuit's 64 slices, then the value of its matrices' form, and checks the batch's final claim against those values and each circuit's closed terms (pin and `C`); each value is left as that circuit's deferred matrix claim, so the verifier's core builds no circuit. A batch of one is how the recursion machine proves its hash rows. The zerocheck prover is a per-circuit state machine (`zerocheck::CircuitProver`) stepped one round at a time, so all twenty-one circuits' folded tables are alive at once. `pcs::stack_open` takes one ring-switched region per witness, then one for the bytecode's multiplicity column, then one per register word, and ring-switches all their claims as one family under one map challenge; claims whose points are prefixes of one another (the circuits of one block size) share one pass of the Frobenius products (`ring_switch::PrefixGroup`, also the rows' grouping, by wire), each region closing once.
- **A row's register numbers `a1`, `a2`, `ad` are not committed columns**: they are bit fields of a committed register word (`cpu::layout::RegisterWord`, in a register column after every table's span; `Source::Sliced`), five bits per register read and six for the cell written (the sink is 32), packed low first in that order, the fields the class has. Tables of one height share a word: in table order each joins the first word of its height with room, else opens one in its own register column (`RegisterWord::of`, `register_words` in Python), since they share their table-sumcheck point and so one ring-switched claim. The table sumcheck folds every table's numbers, a table the bus point settles keeping only those, so that all words sit at prefixes of its point: read at the bus point instead, they would be a second prefix group the opening and the rows pay for. It sends each number's bits' evaluations in place of its own (`constraints::BitColumns`), the verifier recombines `sum_b x^b s_b`, and each word's claim is its tables' slices in order, then zeros (`doc/leanvm` §sec:regpack). The bytecode lookup still binds the numbers; the opening binds the bits and zeroes the unused ones (`a_forged_register_number_unbalances_the_bus`, `a_packed_register_word_is_its_slices`).
- **Batch floors.** Flock needs eight instances and a zerocheck cube of `2^13` bits for each of a table's circuits (`ClassSpec::n_blocks_log`); padding rows supply them, as honest instances on zero registers.
- **Witness generation is word arithmetic wherever a circuit has a generator, and the generic walk of the gate list, bit by bit, elsewhere**: ALU, LOAD, STORE, LD, SD, SHIFT, MULH and HASH fill by `Fill::Instance` (`ClassCircuit::fill`), MUL by `Fill::Batch8` on AVX2 only, and every clock circuit has one (`ClassSpec::clock_witness`, which is `Clock::witness`); DIV and MUL off AVX2 walk. Each generator computes the circuit's values natively and writes its rows in the order the circuit makes its products (all but the multipliers' through `rv::circuits::Products`), so a change to a circuit's gate list must change its generator too. Each is pinned to the walk by a test that covers edge words (zero, all ones, the sign bits, every shift amount, every misalignment) and random instances: `semantics::tests::word_witness_is_the_walk` for ALU, the memory classes and SHIFT, and their own for MUL, MULH, HASH and the clock circuits (`clock::tests::the_word_witness_is_the_gate_walk`, every table's). A new generator needs such a test. HASH's generator is unrolled, so every carry run's place is a constant.
- **Circuit sizes are structure, not measurements**: `k_log` (its `ClassCircuit`'s) and `clock_k_log` per class are pinned in its `ClassSpec` and asserted against the built circuits; product counts are in `doc/leanvm` Annex C. A product can be committed straight at an output port's position (`flock::circuit::Builder::and_output`), which saves the copy; the clock circuit's step uses it.

CI compares every PR with its base, never with a history. The base is the merge commit's first parent; a workflow builds and runs both on one runner and saves both as an artifact, and a `workflow_run` workflow on the default branch (`main`, the only branch GitHub runs those from) posts them on the PR as one comment, edited on every run and deleted once nothing changed. The posting workflows never run the PR's code: they take only the PR number from a run's artifact, a fork's included, post nothing unless GitHub's API says that PR's head is the commit the run measured, and check every name and number before it reaches the comment. **Exact counts**: `counts.yml` runs `cargo leanvm bench --cycles-only`, every program at the sizes above without a proof (`cycles`, the program's own instructions; `proven-rows`, table heights after padding; `committed`, witness words) and the two aggregation trees above, one case per tree and kind of node (`aggregate-leanxmss-400-2to1-first` and `-node`, `aggregate-leanxmss-400-4to1-first` and `-node`, from `counted_trees()`: `rows`, the circuit's own; `proven-rows` and `committed` as for a program), puts the tables in each run's summary from the same pass (`--markdown-file "$GITHUB_STEP_SUMMARY"`, which appends what `--markdown` prints), saves the artifact `counts` and fails on any increase; `counts-comment.yml` posts the counts that changed. A tree's name says its shape, `Nto1` for N proofs combined into 1 at every node; `-first` is a first-level node (the RISC-V verifier in rows over N leaf proofs) and `-node` a higher node (the recursion verifier in rows over N child proofs). **Proving**: `bench.yml` runs one job per testbed and benchmark: each case of `proven()` in `bins/leanvm/src/tracked.rs` (at the sizes a 16 GB runner holds: leanXMSS, leanSPHINCS, Falcon, the state proofs and the shielded transfers at a quarter, no leanDA; leanXMSS also on 1, 4 and 8 threads, `leanxmss-100-1thread`, `-4thread` and `-8thread`, each of which the CLI proves in a process of its own with `LEANVM_NUM_THREADS` set to the count `THREADS` gives it, since the pool is sized once per process, and unpinned to cores, since each job has its VM to itself), each of `proven_trees()` (the two aggregation trees above over leanXMSS at a quarter, `aggregate-leanxmss-100-2to1` and `aggregate-leanxmss-100-4to1`: the leaf proven once, then one first-level node and one node over copies of it, the two benchmarks `<case>-first` and `<case>-node`, each node's stages the children of a `Prove` span around it and the node's peak memory including the first-level node's; both trees also on 1, 4 and 8 threads, `aggregate-leanxmss-100-2to1-1thread`, `-4thread` and `-8thread` and the same for `4to1`, each proven whole, leaf included, in a process of its own like `leanxmss-100-1thread`), and each `benches/` target above with every benchmark it prints (flock's two at `FLOCK_N_LOG=18`, pcs's `throughput` at its default size). Each job builds both sides and runs them in turns, base, PR, PR, base, for `ROUNDS` rounds: `cargo leanvm bench --only <case>` gives the proving time, the proof's size in bytes (exact: the inputs are seeded and grinding takes the smallest nonce), the time of each of the proof's stages (`stage.<name>`, the `Prove` span's direct children, `--tracing`'s first level, timed by a `tracing` layer that enables spans only), the process's peak resident memory (`peak-memory`, that case's alone since each job proves one), the proving passes' heap as the global allocator counts it (`heap-peak`, the most bytes live at once above those live when a pass began, and `allocations`, its allocations and reallocations, each the largest over the measured passes; host-side setup is outside them), and the verifying time, and a target's `--json` its own measures: `latency` for a whole operation (flock's proving times with the witness excluded, pcs's commit and open), `per-op` in nanoseconds per call for `kernels`, a hashed block of `hash_throughput` and one NTT encode. `bench-comment.yml` posts a size that changed and a time that moved the same way in every round with a median ratio at least 1% from one, every result collapsed beneath; it gates nothing. Run in turns on one runner, the comparison does not depend on which machine the job landed on, which a history across GitHub's runners does (one runner label spans CPU models of different speeds). The testbeds are self-hosted runners, `x86-64` on `size-attester7870-x64` (an Intel Xeon Gold 6548N, 32 vCPUs, 64 GB) and `arm64` on `size-attester7870-arm64` (an Arm Neoverse-V2, 16 vCPUs, 64 GB), each built for `target-cpu=native` since base and PR build and run on that one machine: x86-64 measures the AVX-512, VPCLMULQDQ and GFNI arms, and arm64 the NEON field kernels, which are chosen at compile time on `aes` and `sha3` (a generic aarch64 target enables neither, so the arm64 job fails early if its build does not enable them or the CPU lacks what the build enables). Each job prints the CPU and its relevant features, and keys its cache on the CPU model so a native build is never reused on another CPU. In a fork's own repository, which has no such runners, the testbeds fall back to GitHub-hosted runners with a pinned ISA, since a cached native build dies of SIGILL on an older CPU: `ubuntu-latest` built for `target-cpu=haswell`, and `ubuntu-24.04-arm` built for `target-cpu=neoverse-n2` plus `+aes,+sha3`. A benchmark's name is what base and PR are matched by, so renaming one or changing its input shows it as new, as does one the base cannot run (it cannot build the target, or its first base run fails or prints no JSON, and the job carries on with the PR's runs alone).

`bench.yml`'s jobs each run `scripts/ab.sh --ci` on their benchmark, and the script owns the whole comparison (which benchmarks are `benches/` targets, the settings they run with, the order of the rounds, the tolerance of a base that cannot run, `ab.json`), so a local run of it makes the comparison CI makes. `counts.yml` keeps its own steps; `scripts/ab.sh counts` is the same comparison. Run from the Actions tab (`workflow_dispatch`), `bench.yml` compares any two refs on the same testbeds (inputs `head`, default the branch it runs on, and `base`, default the head's first parent, passed to `ab.sh --base`) and leaves its artifacts only, since `bench-comment.yml` posts for PRs alone.

## The recursion machine (`rec`)

A second machine, proven by the same bus, table sumcheck, flock and opening as a RISC-V run, whose rows are a circuit (`doc/leanvm` Annex E). What to keep in mind:

- **Six tables** (`rec::table::Table`): `EMUL` (`a·b + d` in `E`), `EXK` (`a·k + d`, `k` in `K`), `HASH` (one BLAKE2s compression, the RISC-V `HASH` class circuit's packed witness, proven by flock), `SPLIT` (a word and its 64 Boolean bits), `CAST` (four words as a digest, an `E` element, two halves, four words) and `PUB` (the constants and the statement, public, committing nothing). Each table's slot kinds, slot forms, identities and column count are methods of `Table`; its committed columns are filled from the slot forms, so a new table is its kinds, its forms and its identities.
- **Wires are copy cycles** (`rec::bus`: `SlotKey`, `BusBlocks`; `rec::fixed::FixedColumns`, every slot's `next` and the `PUB` constants, the columns a circuit's wiring alone fixes). Slot `g` of row `z` pulls at key `g << 32 | z` and pushes at a public `next`, the key of the next slot of its wire, so the bus balances only if every slot of a wire carries one value. A wire in one slot (a value the prover chooses) and every padding row (`next` its own key) cancel themselves. A table holds at most `2^32` rows (`RecError::TooManyRows`).
- **The rows never depend on values**: the verifier rebuilds the circuit with `rec::transcript::ProofSource::Shape`, zeros in place of the proof. Folding a product by the constant one or zero, or a sum with zero, into no row is structural (constants are the circuit's own wires), and so is folding an `EMUL` or `EXK` row whose input wires repeat an earlier row's into that row (`Builder::emul_key` orders the factors, and a sum's terms), so both keep that true; a constant made from a proof's value would not.
- **The statement is bound by the transcript's seed, not by the bus**: `Circuit::prove` and `Circuit::verify_to_raw` (in `rec::proof`) absorb the hash of the statement's limbs (`statement_seed`) after the caller's `iv`. The bus checks a `PUB` row at one random point, which leaves a `K`-linear kernel of a word's four limbs (`a_statement_moved_along_the_bus_kernel_is_refused`).
- A circuit whose witness exceeds one commitment is `RecError::TooLong`, on both sides.
- **`rec::verifier::ProofShape::verify_core`** is a RISC-V proof's `verify_core` in rows, built from the program, the table heights and the rate, and leaves its `DeferredClaims` as wires. A read is a free wire a hash row absorbs, an equality merges two wires, and a check that no equality expresses is a recorded failure (`Builder::fail`), so the rows never branch on a value. Write new verifier logic over `arith::Verifier` where it is protocol shared with the native verifier; anything rows-only needs a test pinning it to the native code.
- The verifier's layout carries a zero final clock (`Layout::announced`), and `Layout::reduce_tables` adds the announced clock's share to the bus's pull total, which is what lets the rows hold the clock as a wire.
- **Aggregation trees** (`rec::tree`, `leanvm::aggregate`, Annex E §E.6 to E.10). The leaves' rate is their `LeafShape`'s, apart from the tree proofs' `TreeShape::rate`: leaves at a lower rate take fewer queries, so fewer first-level rows, and their provers run in parallel while one aggregator proves every tree proof. A first-level node (`Kind::First`) verifies `arity_0` RISC-V proofs of one program in rows, a node (`Kind::Node`) `arity >= 2` tree proofs of either kind; `arity_0 = 1` is single-proof recursion. Every tree proof states the same words (`TreeStatement`, one flat word list whose layout is `StatementLayout`): its kind, a digest of its leaves' outputs, one claim on each dense polynomial (`DensePoly`: the bytecode table, RAM's image, the nodes' fixed polynomial `W_node`) and each flock circuit's two matrices at one row and one column point. A node's rows (`design.rs`) verify each child with `rec::verifier::RecShape`, the recursion machine's verifier (`rec::proof::TableArgument::verify` is the native and the rows' code alike) over `Rows::hinting`, which takes every evaluation of a fixed column as a hint; the hints become claims on `W_node` at the child's kind bit, and only the root's verifier settles them, against the circuits `Tree::new` builds from the shapes alone. Both circuits share their heights, the bounded fixed point of `Tree::converge`. Each node's claims are reduced (`tree::reduce`) by a small proof the node's prover makes natively (`DenseProver`, `MatrixProver`, on the pool) and its rows verify through `arith::Verifier`; the same verifier code runs natively in the tests. A claim whose scale is zero is not reduced: a first-level node carries no claim on `W_node`, and a parent scales the one it carries by the child's kind. Forgery tests hand the rows a forged reduction proof or a fake child circuit (`a_fake_child_circuit_is_refused_at_the_root`); nothing in the production code branches for them.

## Recursion on the RISC-V machine (`rec::program`)

The verifier of a leanVM proof as a RISC-V program, generated: the fourth thing the shared verifier code is run over.

- **`record::Gen` implements `Arith`, `Verifier` and `OpeningVerifier`** by appending one operation per call and computing its value on the side. The operations depend on the shape alone, so a program built from `ProofSource::Shape` is the one built from a proof (pinned by the test); the advice (the proof as read, then the hints) depends on the proof.
- **`lower` turns the operations into text.** An element lives in an extension register while used (the register whose element is used furthest on is given up); one given up while still needed is stored to scratch by `esd` and reloaded by `eld`. Every element in memory sits on a 32-byte boundary, three limbs and a padding word, an opened row's words three to a slot (`record::leaf_slot`). Integer registers: six scratch, five holding the hash blocks' bases and the constant 64, fourteen holding page bases (`lui` on a miss).
- **Three static hash blocks.** A transcript step and a leaf chain alternate between a block's two halves (base and base ^ 32), so the result of one compression is the chaining value of the next with no copy; the third block keeps the parameter block's chaining value for one-block hashes (Merkle nodes, the proof of work). A check is a `beq` over an illegal word, or a checked extension-field product.
- **The image is empty**: the program writes its constants itself, so two verifier programs differ by their text alone.
- **What a run leaves open**: its output is the hash (`statement_hash`) of each verified run's output and of the deferred claims its core leaves, which `settle` checks natively. `Prover::prove_at` pads tables to given heights, for proofs of one shape.
- **Aggregation trees of verifier programs** (`rec::program::tree`: `ProgramTree`, `ProgramTreeProof`). Two programs: the first-level one verifies `arity_0` leaf proofs, the node one `arity` tree proofs of either kind, itself included. Both programs' proofs have ONE shape (table heights, bytecode, RAM and advice sizes): the least fixed point of the two programs' own shapes, counted statically from their texts, each instruction running exactly once; `Prover::prove_seeded` pads to it and `padded` fills the text with illegal words. The node verifies a child through a stand-in program of that shape, since `Layout::verify_core` reads nothing of a program's bytecode. A tree program's transcript is seeded with the tree's seed (`ProgramTree::seed`), not its digest, which the node program could not hold of itself; what binds a child to its program is its kind, a word of its statement, and the claim its core leaves on its bytecode table, which the node moves to the two programs' tables stacked under the kind (`DensePoly::Fixed`). The statement, the claims and their reduction are the circuit tree's own (`TreeStatement`, `NodeClaims`, `tree::reduce`, run over the recorder); a tree program outputs the hash of its statement, and the parent recomputes that hash from the child's statement, a hint. `ProgramTree::verify` checks the root's proof, its digest of the outputs and every carried claim. `a_fake_child_program_is_refused_at_the_root` is the soundness test: a program verifying nothing, proven on the tree's seed at the tree's shape, wrapped by the honest node program.
- `cargo leanvm recursion --program leanxmss --n 400 --leaves 8 --arity0 2 --arity 2` proves the leaf, then the tree over copies of its proof, and verifies the root.

## Memory

A proof's buffers are plain `Vec`s on the global allocator. The prover allocates gigabytes of short-lived buffers per proof, so what costs time is the kernel faulting fresh pages in, not the allocator's bookkeeping: an allocator that returns freed pages to the kernel makes every proof fault them in again. The CLI and every proving `benches/` target therefore install jemalloc with dirty pages that never decay (`bench::Jemalloc` and its `malloc_conf` in `crates/bench/src/allocator.rs`, one `#[global_allocator]` line in each binary, where the CLI's `system-alloc` feature puts the system allocator instead for heaptrack), so a freed buffer's pages serve the next proof; the price is that the process keeps its peak resident until it exits. On Linux the same configuration asks for transparent huge pages on jemalloc's mappings (`thp:always,metadata_thp:always`), so a first touch faults a 2 MiB page rather than a 4 KiB one; other targets leave it out, since jemalloc would warn there. The libraries impose no allocator: a host embedding `leanvm` picks its own, and a retaining one is what makes repeated proofs fast (`leanvm::Prover`'s doc says so). glibc's default is the slow case: it unmaps a large block on free.

Resident memory (`peak-memory`) therefore mixes what the code needs with what jemalloc keeps and how the kernel rounds its mappings, and is the process's maximum, setup included. Each binary wraps its allocator in `bench::Counting` (`crates/bench/src/heap.rs`), which counts the bytes live and the allocations made, over any allocator it wraps: `heap-peak` and the span tree's heap say what the code needs, so a change can lower them and still raise `peak-memory`, and `allocations` measures churn (fresh buffers, regrowth), exact on one thread and varying slightly with the pool's scheduling on many.

A buffer every slot of which the caller writes before reading skips the zero-fill: it is `Box::new_uninit_slice` (or a `Vec`'s `spare_capacity_mut`), written through its `MaybeUninit` slots and made a vector by `assume_init` (or `set_len`) only once every slot is written. A kernel typed over `&mut [T]` that writes before it reads takes those slots through `primitives::write_only` (`T: Copy`).

## The thread pool (`parallel`)

No rayon. Every parallel site is "N independent items, each writing its own disjoint slice", so the pool is a claim counter, not a work-stealing deque: `NUM_THREADS-1` workers plus the dispatcher inline, and a dispatch allocates nothing (a reduction allocates its per-worker slots once per call, the slot type being the caller's). Primitives: `for_each{,_chunk}`, `chunks_mut{,2,_zip}`, `Chunks`, `fill`, `map_collect`, `map_reduce`, `fold_reduce`, `map_reduce_with_state`, `find_first`, `SendPtr`.

- **Nested dispatch panics**, because it would deadlock the dispatch lock.
- **Both core clusters share one queue** (P at `USER_INTERACTIVE`, E at `UTILITY`); guided self-scheduling means a slow core claims fewer batches. Do not add a second pool: that was `primitives::epool`, now deleted.
- **The default holds back one performance worker when efficiency workers exist.**

`LEANVM_NUM_THREADS` sets the **performance**-worker count, leaving E-workers in place. `1` = strictly sequential.

## One protocol, three verifiers

The same verification algorithm is written out three times. Any change to the snark protocol has to land in all three: nothing fails at compile time when one is left behind, and the pinning tests catch a divergence only where they exercise it.

1. **Rust**, `leanvm_core::cpu::Program::verify`. The native verifier.
2. **Python**, `python-verifier/verifier.py` (no dependencies), for readability and simplicity. Pinned by `leanvm_core/tests/verifiers/python_verifier.rs`, which feeds it the raw proof `cpu::Program::verify_to_raw` returns.
3. **Rows**, `leanvm_core::rec::verifier`: the core as rows of the recursion machine (below). It shares the GKR, the bus decomposition, the table sumcheck, the program claim, the flock reductions (`flock::reduction::verify`), the opening (`pcs::verify`, over `pcs::verifier::OpeningVerifier`) and the driver that runs them from the commitment to the end of the proof (`Layout::verify_core`, and `TableArgument::verify_core` for a recursion proof) with the native verifier, which are written once over `fiat_shamir::arith` (`Arith`, `Verifier`: native over `VerifierState`, rows over the circuit builder and the in-circuit transcript; `Verifier::scope` names a stage, under which the rows report a failed check). `rec::verifier::tests` checks the rows leave the native `DeferredClaims` value for value, and that a forged proof fails both at one stage.

Both are split in two, `verify` being one then the other: `verify_core` runs every check that depends on the proof and returns the claims it leaves on polynomials only the program or the VM's circuits fix (`cpu::DeferredClaims`: the table sumcheck's final identity short of the bytecode producer's program columns and RAM's image, and each circuit's lincheck terminal identity short of its matrix form), and `check_deferred` evaluates them. A recursive verifier carries the claims out of the proof instead of evaluating them; a caller of `verify_core` must never drop them. `check_deferred` refuses a malformed claim with `CpuError::MalformedClaim`, never a panic. `python_leaves_the_same_deferred_claims` pins the two sides' claims to each other (`verifier.py --deferred`).

A query batch's positions are stratified (`pcs::whir::strata`, Annex B's `def:strata`): each binary digit of the query count is a group whose `j`-th query has its top bits fixed to `j`, which keeps the i.i.d. query bound and lets the rows hash the top subtree once and each query's path only below it (`rec::verifier::authenticate`); the three verifiers cut positions alike. Neither the prover nor the verifiers compute the WHIR parameters: each reads a table of query counts (`WHIR_QUERIES` in `pcs::whir::config` and in `verifier.py`) and builds the rest from the integer level ladder, so no floating point reaches a proof. The floating-point soundness derivation that chooses them is test-only (`pcs::whir::config::tests`): `the_table_is_the_derivation` pins the Rust table to it, and `whir_query_table_matches_rust` the Python table to the Rust one. Changing a constant the derivation reads (the security target, a folding factor, the grinding bits, the size window) fails the first, whose message holds the rows to paste over the Rust table; then the second fails with the line to paste over the Python one. Moving the size window also changes the Rust table's type: give each rate that many rows first (`&[]` will do) so that `pcs` compiles.

## Conventions that bite

- **The prover can be memory-bandwidth bound.** Reduce memory traffic before assuming that more workers or fewer instructions improve throughput. `primitives::stream::Stream` publishes a buffer without the read-for-ownership an ordinary store pays, but ONLY where nothing reads the destination again before it is evicted. Where a consumer follows in the same pass, the fetch it avoids becomes that consumer's miss: fold kernels earn it by building their round message from registers, or by folding into an L1 stage first (`whir::fold_and_msg_blocks`). That fetch is an x86 cost only: on Apple silicon a store-only fill already sustains what a read-only pass does and `STNP` measures identical to `STP`, so `Stream` is a plain copy there and the L1 stage earns its keep for the read locality alone, which is still better than writing through.
- **NEON is the width ceiling on Apple silicon**, so an AVX-512 win that is purely width has no counterpart: the M4 has no SVE, and its SME2 is streaming-mode matrix work with no polynomial multiply. What does port is *shape*. A fused NTT pass wants a butterfly at a time over whole rows, not the register-resident tile the AVX-512 arms use: they transpose anyway and want to pay for it once per pass, while NEON transposes nothing and a tile leaves only its own width of independent work to cover the reduction's dependent PMULL folds, where a row leaves the whole lane count. Measured both directions: the tile costs the extension NTT, and costs the base encode's `Commit` again.
- **A `[F192; N]` in a NEON kernel is a memory object, where on AVX-512 it is the register.** Four tower products are four independent PMULL chains wanting most of the 32 vector registers, so an array of them spills and the spill costs more than batching the products saves; the same array is free on AVX-512, where the quad IS one register. Keep the quad as a tuple or as named values and let arrays exist only inside the batched-product helper, on the target that wants them (`flock::zerocheck::multilinear`'s `mul_quad`). The symptom is indirect, so suspect the shape rather than the arithmetic: the products measure the same either way, destructuring the results changes nothing, and forcing the helper to inline recovers almost none of it.
- **On Zen 4, 512-bit cross-lane data movement is half-rate** (every 512-bit shuffle is two 256-bit uops), so packing scalars into vector lanes with `vpermi2q`/`vpermq` and extracting with `vextracti64x4` loses to the scalar moves it replaces. Widening the arithmetic still pays: `mul4` beats the same products issued one at a time. Prefer kernels where both qwords of every 128-bit lane carry a product and nothing crosses lanes.
- **On Zen 5 the carry-less multiplier is the scarce unit, and a CLMUL costs the same at 128, 256 or 512 bits.** Spend it on products only: reduce modulo `x^64 + x^4 + x^3 + x + 1` with shifts and XORs (`gf2_64::reduce`, or its lane-wise twin in the batched kernels), not with the two CLMULs by `0x1B` that NEON prefers, and count CLMUL instructions rather than products when sizing a kernel. The exception is the scalar `F64` product (`gf2_64::x86_64::mul`), whose reduction would cross to integer registers and back: on Zen 4 that loses to the two CLMUL folds, which stay in the vector register. Masked or 512-bit loads of `F192`s passed by value defeat store-to-load forwarding, so the batched kernels pack from scalars.
- Use comments only when necessary: uncommented but readable and simple code is better than commented slop. And when you use comments, be concise.
- **Never put a measurement in a comment, a doc comment, or this file.** Timings, throughputs, percentages and speedup factors go stale the moment the code, the compiler or the host changes, and nothing ever rechecks them, so they end up asserting something false with the authority of a comment. The commit message is where they belong: it is dated, it is immutable, and it says what was true when the change landed. A comment may say which way a result went and why (that a tile lost to whole rows, that one reduction beat another), never by how much.
- Commit tests only that are useful in the future, to prevent regressions / failures. Don't add trivial tests that will always pass.
- Simpler is better.
- **Import types, traits and derive macros at the top of their module**, including test modules; use their short names in signatures, fields and bodies: `proof: Proof`, never `proof: transcript::Proof`. Put function-local imports there too, preserving their configuration gates. When two types would share a name, they are two concepts: rename one (`fiat_shamir`'s wire `ProofTranscript` beside the RISC-V `Proof` it carries), never alias it and never qualify it. The one exception is a standard-library name that conflicts with the prelude.
- **Use full paths for function calls when the module makes their meaning clearer**, for example `std::array::from_fn(...)` rather than importing `from_fn` and calling it by its short name. The import rule above applies to types, traits and derive macros; it does not require short names for these function calls.
- **Keep test-only imports and helpers inside test modules**, with the narrowest visibility their callers need. Share fixtures across crates through a module behind a development-only feature. Keep platform gates on production backends and native coverage of guest code. Delete unused helpers and experimental implementations whose only callers test the experiment itself.
- **Errors derive `thiserror::Error`**, with no hand-written `Display`. A variant carries what a reader needs to find the fault (the level, the table, the address). A wrapper that adds nothing is `#[error(transparent)]` with `#[from]`; one that adds context prints `"context: {0}"` and declares no source, so a chain never prints a message twice.
- **Fiat-Shamir:** `add_scalar`/`next_scalar` bind into the Fiat-Shamir state as a side effect. The public statement seeds the transcript at construction; the transport exposes no separate observe operation. Never re-observe data that rode the stream, which silently desynchronizes the two sides. A step is one BLAKE2s compression with the state as its chaining value (`fiat_shamir::step`), not a hash of the state from the parameter IV, which keeps it apart from every one-block hash (`sec:e2e-fiat-shamir`), and absorbs up to two scalars: an observed scalar waits, a squeeze absorbs the waiting ones in its own step, and grinding and `state()` absorb them first. The Rust state, `verifier.py` and the rows (`rec::transcript`) buffer identically; the in-rows pin is `the_circuit_replays_the_native_transcript`.
- **Prover and verifier derive the layout identically** from announced sizes. Changes to `placements_of` or the schema land on both sides. The framework's blocks, the lookup arrays' producers and the shared columns are described once, by `Framework::ALL`, `Lookup::ALL` and `Shared::ALL` in `cpu/layout.rs` (mirrored by `verifier.py`), and every kappa, block, producer and placement derives from them; keep it that way. Each enum's declaration order is that protocol order: `Shared::col()` is the discriminant, and a compile-time check pins `Shared::ALL` to it.
- **The L0 lane fold binds the committed witness's TOP `INITIAL_FOLDING_FACTOR` variables**, because lane `l` of the interleaved commitment is the stack block `q[l·2^(μ-k) ..)`. That makes the witness's zero tail whole lanes, so `whir::commit` encodes only `StackShape::n_lanes` of them, and the opening's dense weight, its first `k` sumcheck rounds and the stack allocation shrink with it. **A leaf image is still `2^k` words**, the absent lanes contributing their codeword's zeros, but those zeros LEAD it (codeword lane `t` is stack block `n_lanes-1-t`): their whole 64-byte blocks are then one shared chaining value (`hash::zero_prefix_state`) the committer hashes once rather than per leaf, and only the image's tail rides the proof, so `PrunedMerklePaths` stores `n_lanes` words per L0 row while `RawMerklePath` (what the Python verifier reads) carries the full image. Both verifiers therefore derive `n_lanes` from the announced layout to read a row. Since `mu = log2_ceil(placed)`, `n_lanes` is always in `[2^(k-1)+1, 2^k]`: the encode saving caps near half, the hashing saving is quantized to whole blocks of 8 lanes, and both are ~0 just above a power of two. The cost is that fold challenges arrive in round order while every transparent weight is written in witness coordinates, so both verifiers rotate the terminal point left by `k` before evaluating it (`whir/verify.rs` before `eval_b_at`, `verifier.py` before `evaluate_basis`). Anything else that reads the opening's point (per-level induced weights, the residual) stays in round order.
- **One symbol, one meaning, across the whole leanVM document.** All notation is defined in `doc/leanvm/preamble/macros.tex`: define a new macro there rather than inline, and check the letter is free first. Annex B's "Symbols" table maps its letters back to WHIR/Ligerito/BCHKS25, so read it before renaming one. A sumcheck round challenge is `\fc` everywhere, which is what keeps `\rho` free for the rate; `r` is the point a claim is made at, not a challenge. **A rename in the document is a rename in the implementations**: the Rust prover and verifier and `python-verifier/verifier.py` name their variables after the document's symbols, so the three have to move together.
- **Doc labels are an API.** `crates/pcs` cites `thm:rbr` and `thm:mca-johnson` by name and several crates cite `doc/leanvm/main.tex` sections, so renaming a label breaks those pointers with nothing to catch it. `doc/leanvm/body/NN-*.tex` prefixes match section numbers, so inserting a section renumbers the rest.
- **No em-dashes or en-dashes in prose**, anywhere a human reads it: docs, LaTeX, comments, commit messages. Restructure with a comma, colon, parentheses, or two sentences.
- **Never hard-wrap prose in Markdown or LaTeX.** One paragraph is one line; let the editor wrap it. Artificial line breaks make every later edit a reflow, so diffs show rewrapped lines instead of changed words. Applies to `.md` and `.tex` alike; code blocks, tables and list items keep their own line.
