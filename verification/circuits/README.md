# Clean-authored circuits and their proofs

This Lean project holds the circuits Lean authors for leanVM and their proofs: Boolean adder and BLAKE2s compression circuits written in Clean, lowered to checked artifacts; the recursion machine's tables, exported to `crates/leanvm_core/src/rec/clean.rs`; a model of the recursion circuit builder with a contract per method; and the leanXMSS and leanSPHINCS signature verifier circuits for the recursion machine, with their proofs against the Ethereum XMSS specification and a Lean transcription of leanSPHINCS.

## Reproduce

The project pins Lean `v4.33.1`, Clean revision `b449bf590f93e13827c3c7e747e392d6969aa380`, and all transitive dependencies in `lake-manifest.json`. Regenerating `rec/clean.rs` uses Rust `1.97.0` with `rustfmt` and the repository's formatting configuration. Rust builds use the checked-in generated file and need no Lean.

From this directory:

```sh
lake exe cache get Mathlib.Tactic Mathlib.FieldTheory.Finite.Extension Mathlib.RingTheory.AdjoinRoot Mathlib.Algebra.Polynomial.SpecificDegree
lake build
lake env lean Audit.lean
shopt -s globstar nullglob
for source in LeanVMCircuits/**/*.lean Spec/**/*.lean; do
  module="${source#Spec/}"
  module="${module%.lean}"
  lake env leanchecker "${module//\//.}"
done
lake env lean --run GenerateRec.lean /tmp/rec-generated.rs
diff -u ../../crates/leanvm_core/src/rec/clean.rs /tmp/rec-generated.rs
(cd ../.. && cargo run --release -p leanvm-cli --features circuits -- circuits /tmp/circuits)
lake exe checkrec /tmp/circuits/aggregate-*.txt
lake exe checkxmss /tmp/circuits/xmss-*.txt /tmp/circuits/sphincs-*.txt
scripts/check-xmss-spec.sh
```

`lake build` builds every module: the root `LeanVMCircuits.lean` imports every `module` file of the library, the bridges to the vendored specifications (which import non-module files, so cannot be imported by a module) are roots of their own in `lakefile.toml`, and the specification libraries are default targets. `Audit.lean` prints the axioms of every listed theorem and fails on any outside `propext`, `Classical.choice` and `Quot.sound`. Stock `leanchecker` replays the modules matching a prefix concurrently, each with an imported environment, so the loop checks one module at a time to bound memory.

The `Clean circuits` workflow (`.github/workflows/clean-circuits.yml`) runs the build, the audit, the kernel recheck of every library and specification module, a check that the root imports every `module` file and declares nothing, and the regeneration diff of `rec/clean.rs`. The `Recursion builder model` workflow dumps the circuits and runs `checkrec` and `checkxmss`. `scripts/check-xmss-spec.sh` fetches the specification from GitHub, so it is a manual step.

## Boolean circuits

These are Boolean circuits over `F2 = ZMod 2`, not Clean's prime-field `Addition32` gadget. Input and output vectors are little-endian bits; each element of `F2` is necessarily zero or one. Wrapping sums are modulo `2^64` or `2^32`, with 63 or 31 products in least-significant-bit order and no discarded-overflow product. The carry adder uses 64 ordered products and returns a 64-bit sum and one carry bit.

`FullAdder.soundness` proves the integer identity `sum + 2 * carry_out = x + y + carry_in` from the defining Boolean product constraint. Its completeness theorem checks the Clean witness generator. `Adder.circuit` composes those circuits with a proof of the full word identity. `WrappingAdder.circuit` removes the unused high carry product and proves the modular sum.

`Flock.lowerAffine_correct` and `Flock.lower_correct` prove evaluation and constraint equivalence for every assignment. `Flock.flatten_correct` proves that successful bounded flattening returns exactly Clean's flat operations; the bound is an explicit export error, not a silently truncated circuit. `Flock.adder64_source` identifies the exact checked artifact with lowering of the actual Clean source. `Flock.adder64_layout` checks 63 ordered product variables starting at 128 and 64 outputs. `Flock.adder64_soundness` proves that every assignment satisfying that artifact's product constraints has the correct modular output. It does not assume that an assignment was generated honestly.

`Flock.witness_exists` constructs satisfying assignments for acyclic product rows. `Flock.adder64_wellFormed` checks the concrete artifact's dependency order, and `Flock.adder64_complete` proves that every assignment of the 128 input bits extends to a satisfying assignment. Completeness therefore does not stop at an unfulfilled witness-generation premise.

`Flock.adder32_source`, `adder32_layout`, `adder32_soundness`, `adder32_wellFormed`, and `adder32_complete` establish the corresponding exact-artifact claims for the 32-bit wrapping adder. Its product variables are 64 through 94, after 64 input bits. `Flock.carryAdder64_source`, `carryAdder64_layout`, `carryAdder64_soundness`, `carryAdder64_wellFormed`, and `carryAdder64_complete` establish them for the carry adder. Its input variables 0 through 127 name the operand bits, input 128 names the carry-in, and product variables 129 through 192 name 64 ordered products. The 65 output bits represent the exact integer `x + y + carry_in`, so the theorem covers both the low sum and final carry. Each completeness theorem extends every input assignment to a satisfying assignment.

Artifact support, layout, and well-formedness are checked by `decide +kernel`, not `native_decide`.

## BLAKE2s compression

`LeanVMCircuits.Blake2s.Rfc7693.F` is the compression function F of RFC 7693 written from the RFC's pseudocode, and `Rfc7693.abc` checks it in the kernel against the RFC's Appendix B test vector. `LeanVMCircuits.Blake2s.Compress.circuit` is the Clean circuit: a register program (`Blake2s.program`, ten rounds of eight G functions in the RFC's order) run as Clean subcircuits for its word operations `Add32` (Clean's 32-bit wrapping adder), `AddOdd` and `AddEven` (a literal addend; an even one leaves the low bit and adds `k / 2` to the upper 31 bits with Clean's 31-bit adder), and `XorRotr`. Each word operation names its 32 result bits as witnesses constrained to affine expressions of earlier variables, so that the source's expressions stay small. `Compress.soundness` proves, for every witness satisfying the constraints, that the output is `F h m t f` whenever the 32-bit finalization port is `0` or `0xFFFFFFFF` (`f` false or true); `program_correct` carries the RFC's working vector through the registers. The class's legal flags are exactly those two words.

`LeanVMCircuits.Gates` lowers such circuits: a witness constrained to an affine expression becomes an uncommitted XOR definition, one constrained to a product of two affine operands becomes the next product, and anything else (other witnesses or assertions, lookups, interactions) is an error. `Gates.lower_correct` proves that the steps hold exactly when the Clean constraints do, and `lower_wellFormed` that every step defines the next variable from earlier ones, which gives `witness_exists`. `Compress.lowered` proves that the lowering of the actual Clean circuit at the ports' variables (`t` at 0, `f0` at 64, `h` at 96, `m` at 352) is `Compress.artifact`, a closed form built operation by operation; nothing is evaluated outside the kernel's proof checking. `Export.soundness` and `Export.completeness` state the arbitrary-witness soundness against `F` and the existential completeness of that artifact.

`Export.adder32_call` and `Export.adder31_call` prove that each addition's products and sum bits in the artifact are the `adder32` and `adder31` rows and outputs under the call's binding of operand and product variables; `adder31` has the same source, layout, soundness, well-formedness and completeness theorems as `adder32`.

No Rust is generated from these Boolean artifacts here: the RV `blake2s` instruction class and the recursion machine's `HASH` table prove their rows with the circuit of `Hash::circuit` in `crates/leanvm_core/src/rv/semantics/hash.rs`. That a `HASH` row's columns are the ports of an assignment satisfying `Compress.artifact` is the `HashRow` premise of the recursion proofs below, trusted here.

## Recursion tables

The recursion machine's tables are not Boolean circuits: their columns are elements of `K = GF(2)[x] / (x^64 + x^4 + x^3 + x + 1)` and its extension `E = K[y] / (y^3 + y + 1)`. `LeanVMCircuits.Rec.Field` builds `K` as Mathlib's `AdjoinRoot` and proves `Rec.modulus_irreducible` in the kernel: carry-less word arithmetic (`Rec.mul`, proven to be `K`'s product by `Rec.ev_mul`) checks the 64 squarings `x^(2^64) = x` (`Rec.chain_squares`, `Rec.root_pow_two_pow_64`) and an inverse of `x^(2^32) - x` (`Rec.cofactor_mul`), and Mathlib's degree theorem for factors of `X^(q^n) - X` turns those into irreducibility. `K` is then a Clean `FiniteField` whose `val` is the element's coefficient word, the machine's own representation (`Rec.toWord_ofWord`, `Rec.toWord_injective`). `LeanVMCircuits.Rec.Ext` gives `E` and its limb formulas: `Rec.toE_mul` (the product of `c0 + c1 y + c2 y^2` by limbs, `y^3 = y + 1` and `y^4 = y^2 + y` folding the high terms), `Rec.toE_add`, `Rec.toE_smul`, and `Rec.toE_injective` (limbs are coordinates).

`LeanVMCircuits.Rec.Tables` writes every slot of `EMUL`, `EXK`, `HASH`, `SPLIT` and `CAST` as `Form` data, the prover's `leaf::Coord` shape (`Const`, `Col`, `Prod`, `Sum`), read as Clean expressions by `Form.expr` (`Form.eval_expr`), and the identities of `HASH` and `SPLIT` as `Identity` data, a Clean `FormalAssertion` per table (`Rec.identities`, sound and complete for its identities). The theorems, for every row: `emul_spec` (slot 3 is `a·b + d` in `E`, its fourth limb zero), `exk_spec` (`a·k + d`), `hash_mux` (the mux bit is 0 or 1, and the mux limbs are the message's first half at 0 and its second at 1), `split_spec` (every bit column is 0 or 1 and the word's coefficient word is the number those bits spell), and `boolean_spec`. `CAST`'s slots are views of its four columns and `PUB` has no columns. `GenerateRec.lean` prints the same data as `crates/leanvm_core/src/rec/clean.rs`, which `Table::slot` and `Table::identities` in `rec/table.rs` now read in place of the hand-written forms, and `K_PRODUCTS`, products computed by `Rec.mul`, which `f64_products_are_the_proven_field` checks against the prover's `F64` product.

`STEP` and `LINK` carry hash chains on the dynamic bus: besides their slots (`Coord::Scaled` and `ScaledProd` terms, `Form.scaled` and `Form.scaledProd`), each row pushes and pulls a tuple of a key and two words (`stepPull`, `stepPush`, `linkPush`, `linkPull`, printed into `clean.rs` as `step_pull()` and the rest; the bus appends the table's activity column and a zero). `step_spec`: a `STEP` row satisfying its identities (nine Boolean position bits, the carry `u = s0·s1`, a Boolean activity) has the tweak word `T = B + X^32 p` (`tweakK`) of its base slot `B` and the position `p < 2^9` its bits spell, pulls `(X^63 + T + j, v0, v1)` and pushes `(X^63 + T + j + a·(X^32 + X^33 s0 + X^34 s0 s1), o0, o1)`, `s0`, `s1` the position bits of `T + B`. Callers wire `B` to a constant `b < 2^32` (`2^8` for leanXMSS, `tweak0(1, lay, 0)` for leanSPHINCS's layer `lay`), so that `T` is the word `b + p · 2^32` (`tweakWord`, `ofWord_tweakWord`). `stepPush_next`: with `a = 1` and `T` the tweak word of chain `c`, position `s` over a base `B`, the push's key is the pull key of position `s + 1` modulo eight of chain `c` over `B`. `link_tuples`: a `LINK` row pushes `(X^63 + w + X^32 d0 + X^33 d1 + X^34 d2, t0, t1)` and pulls `(X^63 + w + (X^32 + X^33 + X^34)·a, e0, e1)`.

Trusted: the printer of forms and words into Rust; that `F64` and `F192::from(F64(w))` are the `K` element with coefficient word `w` and its embedding in `E` (the test samples products, it does not prove the Rust field); `F192`'s product, pinned by `emul_and_exk_outputs_are_e_arithmetic` against the forms, not proven. `LeanVMCircuits.Rec.Rows` states what the builder's row patterns mean, the bus equalities a pattern relies on taken as hypotheses on its slots: `inverse_row` (an `EMUL` row `a·i + 0` held to one makes `i` the unique inverse of `a`, so `inv` of zero is unsatisfiable), `add_row`, `pack_row` (a `SPLIT` row whose bits past `n` are held to zero spells a number below `2^n`), `cast_views`, `hash_outputs` (a hash row's first-three-word `E` view, not a general buffered duplex challenge), and `node_row` (a Merkle node's mux places `acc` as the first or second half by its Boolean bit). `LeanVMCircuits.Rec.HashPorts` joins a hash row to its compression: `hash_ports_compress` and `hash_row_compress` prove that when the row's packed witness satisfies the exported BLAKE2s artifact and the witness's ports are the row's port columns (64-bit words, 32-bit word `r` of `h`, `m` and the result being half `r % 2` of port word `r / 2`), its output columns are RFC 7693's compression of its chaining value and message columns with its counter column, for both finalization words. `LeanVMCircuits.Rec.Merkle` and `LeanVMCircuits.Rec.Statement` lift this to the hashes the recursion circuit computes in rows, against RFC 7693 section 3.3 (BLAKE2s-256 with `kk = 0`, `nn = 32`, from the parameter IV): `chain_digest` and `chain_rows` prove that hash rows chained output to chaining value, at RFC 7693's byte counts and finalization, output the hash of their message columns (`Builder::chain`, a Merkle leaf's blocks, with `blocksFrom_append` folding a leaf's zero prefix into the chaining value it starts from); `node_row_digest` and `path_root` that node rows chained output to accumulated child output the RFC 7693 Merkle root of the leaf and the bits and siblings the rows hold (`Builder::node`), `opening_node` the two composed (`open_row`); `parent_row_digest`, `parent_right` and `tree_root` that parent rows over a subtree's levels output the root of its bottom level (`Builder::parent`, `authenticate`); `statement_digest` that a tree statement's digest rows output the hash of its header block (tag, item count, zeros) and its items' words (`Kind::digest_rows`). `LeanVMCircuits.Rec.Duplex` models the duplex transcript: `Duplex` is `fiat_shamir::Blake2sDuplex` on whole 64-bit words (every message the recursion verifier absorbs or squeezes is whole little-endian words: the instance's, a scalar's three limbs, a root's four, a nonce, so its byte buffers hold whole words), started by `Duplex.init` from a session id's four words, each compression RFC 7693's `F` at the node's counter (`Role::absorb(first, last).counter(len, previous)`, `Role::Seed.counter(0, 0)`, `Role::Output.counter(0, 0)`), final; `RowState` and the `...Rows` relations are `rec::transcript::Transcript`'s bookkeeping, every compression a hash row whose output is the next chaining value and every squeezed word read from the output row that computed its block. `run_rows` proves that rows replaying absorbs, squeezes (a verifier message's three words, a digest's four) and proof-of-work steps reach the native state and squeeze the native challenge words, `seed_row` that the constant seed chaining value `Transcript::new` takes (the seed node of the session id's words and four zero words) is `Duplex.init`'s, `pow_rows` that the proof-of-work check in rows (no row at zero bits; else the four-word challenge squeezed, the nonce absorbed as one word, a one-block hash row of the challenge, the nonce, two zero words and `ProofOfWork::TRIAL_TAG`, and a `SPLIT` row of its first word with its top `bits` bits held to zero) is `ProofOfWork::verify` of the nonce on the native challenge (`powOk`, by `trial_rows` and `pack_row`). The cursor bound: `Duplex.Bounded` runs (a squeeze only within `MAX_SQUEEZE`, which `Blake2sDuplex::squeeze` and `Transcript::squeeze_word` assert) keep both cursors within it (`run_fits`), and within it an absorb counter names its role, block length and cursor (`tweak_injective`) and is neither the seed nor the output counter (`tag_ne_tweak`). The rows' words become `E` challenges and scalars, and four of them a digest, through `k_to_e`, `e_to_k` and `k_to_d`, whose contracts `LeanVMCircuits.Rec.Contracts` proves (`Model.kToE_good`, `Model.eToK_good`, `Model.kToD_good`). The Rust constants `PARAM_IV`, `zero_prefix`, the seed and output counters, `ProofOfWork::TRIAL_TAG` and `Role::absorb(first, last).counter(len, previous)` are pinned to these Lean definitions by `the_native_constants_are_the_lean_transcriptions` over the values `GenerateRec.lean` prints (every absorb role at full and partial lengths and both cursor ends, four zero prefixes). Not modeled: the byte-level duplex on unaligned input, which the recursion verifier never calls, and `SessionId::new`'s derivation of a session id, which is native. `LeanVMCircuits.Rec.Bus` proves the bus's copy argument: with distinct slot keys (`slotKey_injective`, `SlotKey`'s slot index and row below `2^32`) and each slot linked to the next slot of its class in slot order, the class's first after its last (`classNext`, the links `FixedColumns::new` builds; a permutation, `classNext_injective`), pulls of each slot's key and limbs balancing pushes of its link's key and the same limbs modulo two (characteristic two, so as multiplicities mod 2) make every slot of a class carry the same limbs (`copy_argument`). `LeanVMCircuits.Rec.ExtField` proves `y^3 + y + 1` irreducible over `K` (a root would have order dividing 7 and `2^64 - 1`, so be 1, which is not a root), so `E` is a field and every nonzero element has the inverse an `inv` row needs (`exists_inverse`). Not proved here: that the bus's log-derivative sums balance only when the multiplicities do (GKR and the fingerprint's soundness), that `FixedColumns::new` builds the `classNext` links in configurations other than the tracked ones (`checkrec` checks the links of the tracked trees' circuits, below; elsewhere its fold is their transliteration), GKR, the table sumcheck, the PCS; that the Rust builder emits exactly these patterns (it writes each row at the slot indices `GenerateRec.lean` prints from the names these theorems use, `Rec.hashSlotMux` as `clean::HASH_MUX` and so on, but which wire or public constant it writes at each is trusted, as is the chaining of rows), and that the native constants `PARAM_IV` and `zero_prefix` are `paramIV` and `absorb paramIV 0` of zero blocks, that the hash table's port columns are the packed witness's port words (`HashBatch::new`), and the composition of rows into the transcript, Merkle paths, chains and the verifier in rows; and the binding of public rows to the statement.

The duplex definitions above are a mathematical whole-word transcription, not a formally verified equivalence to the Rust byte-level `fiat_shamir::Blake2sDuplex`. Their counters are natural numbers without the native squeeze cursor bound. The row replay theorems establish the stated model's behavior; they do not discharge those omitted native domain checks.

## Recursion builder model

`LeanVMCircuits.Rec.Builder` is `rec::circuit::Builder` as a Lean program over wire numbers: each method allocates wires, appends rows, records wire equalities and adds public rows as the Rust method does, in the same order, without values (the rows never depend on them). `LeanVMCircuits.Rec.Contracts` proves each method's contract (`Model.Call.exec_good`, and `Model.inv_good`, `Model.node_good`, `Model.chain_good` and the rest for the methods themselves): from a state keeping the builder's invariant (`Model.Inv`: constants and units have their public rows, cached arithmetic rows are in the circuit under their keys), the method keeps it, only adds to the circuit, and in every assignment satisfying any circuit containing its rows (`Model.Sat`: wires held equal carry equal limbs, every row's slots carry the limbs its table's forms give columns satisfying the table, `HASH` columns a packed witness of the exported BLAKE2s artifact, public rows their constants and statement words) its output is what it computes. Among them: `a·b + d` in `E` through unit folding and the row cache (`Model.emulKey_sem`), `a·inv(a) = 1`, a word's bits and a packed word, the `CAST` views, RFC 7693 compressions (`leaf_block` at a constant counter and finalization word, `block`, modeled as `Model.hashBlock`, at a wired one, `Model.leafBlock_eq` relating the two), Merkle nodes with a Boolean bit and a free sibling, parents of two wired children, and `chain`'s BLAKE2s-256 of a word message. `Model.replay_sound` lifts them to any sequence of calls naming wires already made.

`Model.chainStep` and `Model.link` model `chain_step` and `link`. `Model.Sat` holds every `STEP` and `LINK` row to its table's identities; that the dynamic bus balances is a property of the whole circuit, `Model.Balanced` (the multiset of the rows' pushed tuples is the multiset of their pulled ones), and the machine accepts an assignment when both hold (`Model.Accepts`). `Model.chainStep_good`: the step's `HASH` row hashes `[T, idx, p0, p1, v0, v1]` as `chain` does, its challenge (the `STEP` row's output slot) holds the hash's first three words, `T` is the base wire's value plus `X^32 (8c + s)` (`tweakK`) for some `c < 64`, `s < 8`, and the row pulls `T`'s key with `v0, v1` and, when active, pushes the key of position `s + 1` modulo eight with the hash's first two words. `Model.link_good`: the `LINK` row's activity is Boolean and its tuples are `link_tuples`'. `Model.Balanced.count_key` (per key, as many pushes as pulls) and `Model.Balanced.unique` (a key pushed exactly once is pulled exactly once, with the pushed words) read the balance key by key. The leanXMSS and leanSPHINCS circuits walk their chains on these rows, and both `accepted_iff` are stated over `Model.Accepts`. Trusted: that the bus's grand product over the dynamic blocks, the activity column one exactly on the circuit's rows, balancing gives `Model.Balanced` (padding rows' tuples, activity zero, are apart from the circuit's, and bit `X^63` sets every dynamic key apart from the slot keys).

The Rust builder records the calls made of it from outside its methods behind the `circuit-trace` feature, which no ordinary build enables. `cargo run --release -p leanvm-cli --features circuits -- circuits <dir>` writes, for each tracked aggregation tree (leanXMSS-400 and leanXMSS-100 leaves, 2 to 1 and 4 to 1, each with its first-level and node circuit), the calls and the finished circuit (every slot's wire class, every public row's source in statement-first order, the statement's length). `lake exe checkrec <files>` replays the calls through the model, checks each names wires already made and has the sizes its method takes (`Model.Valid`), finishes the circuit as `Builder::finish` does, and checks it is the dumped circuit, and that the verifier's bus links (`FixedColumns::new`, dumped for every slot of the circuit's rows) are each class's cycle in slot order, the `Rec.classNext` the copy argument assumes. CI runs both (`.github/workflows/rec-builder-model.yml`). This is finite evidence for those eight circuits: that the Rust builder's methods emitted, for the calls the recursion verifier made of them, exactly the rows, classes and public rows the model emits, and with them the parameter IV and finalization constants the model takes from RFC 7693. Other configurations are covered by the model only as a transliteration of the Rust builder. Not covered: which calls the recursion verifier makes (the verifier in rows itself), `checkrec`'s parser, class numbering and link computation (executable Lean, not proved), that a proof the Rust verifier accepts yields an assignment satisfying the circuit in the sense of `Model.Sat` (the bus's copy argument is `Rec.copy_argument`; its sums balancing, the table sumcheck and the hash flock are not proved here), and the verifier's public value columns (`FixedColumns::public_values`, which put statement word `i` on public row `i`, the order `checkrec` checks).

The same command writes the leanXMSS batch circuit `rec::xmss` builds, for 1, 2, 3 and 400 signatures, to `xmss-<n>.txt`, and the leanSPHINCS batch circuit `rec::sphincs` builds, for 1, 2, 3 and 104 signatures, to `sphincs-<n>.txt`. `lake exe checkxmss <dir>/xmss-*.txt <dir>/sphincs-*.txt` replays each dump as `checkrec` does, then checks that the dumped circuit and its bus links are those `LeanVMCircuits.Xmss.Circuit.circuit n` or `LeanVMCircuits.Sphincs.Circuit.circuit n` builds: the circuit Lean authors is the one Rust proves.

## leanXMSS

`LeanVMCircuits.Xmss.Circuit.circuit n` verifies `n` leanXMSS signatures on the recursion machine, written against the builder model; `rec::xmss` makes the same builder calls in Rust, and `checkxmss` checks the circuits it builds are this one. Signature `j`'s statement is five `E` words: the public parameter, the message's two halves, the epoch and the Merkle root, each holding 64-bit words (`Xmss.Encodes`). Its chains run on the dynamic bus: chain `i` has a `LINK` row pushing its element at the key of position `8i + d_i` (`d_i` its digit) and pulling its end at that of `8i + 7`, and the signature has 99 `STEP` rows (`7 · 42 - 195`), each pulling its input at its position's key and pushing the hash at the next position's. Keys carry `j · 2^41`, which keeps the signatures' tuples apart while `n ≤ 2^22` (the Rust builder refuses more).

`Xmss.accepted_iff` is the end-to-end statement: for `n ≤ 2^22`, the machine accepts the circuit of `n` signatures under statement words `st` with some assignment (`Model.Accepts`: the assignment satisfies its rows, `Model.Sat`, and balances its dynamic bus, `Model.Balanced`) exactly when, for every `j < n`, statement words `5j` to `5j + 4` state a public key, a message and an epoch below `2^32` (`Xmss.Statement`: words whose little-endian bytes are the key and the message) under which some signature passes the specification's `EthCryptographySpecs.Xmss.verify`. It combines three layers that meet at `Xmss.Words.verify`, verification restated over the 64-bit words the circuit carries:

- `Xmss.sound`: in every assignment the machine accepts the circuit with, each statement encodes a key, a message and an epoch for which some signature passes `Words.verify`.
- `Xmss.complete`: every family of statements with signatures passing `Words.verify` extends to an assignment the machine accepts the circuit with.
- `Xmss.Spec.verify_eq`: `Words.verify` is the specification's `verify` on the words' little-endian bytes. Its core, `Xmss.Spec.hash_wordsBytes`, proves the specification's byte-level BLAKE2s (its private compression, lanes, block reader, counters and serializer) is RFC 7693's on whole words, `hashWords`; `Xmss.Spec.tweakHash_eq` lifts it to the tweakable hash, and the encoding, chains, leaf and Merkle climb follow (`wotsEncode_eq`, `chain_eq`, `leaf_eq`, `computeRoot_eq`). `signature_onto`, `publicKey_onto`, `message_onto` and `epoch_onto` show every specification input is the bytes of some words, so the bridge loses nothing.

The chains' two directions are `Xmss.Paths`. `paths_sound`: when 99 steps and the 42 links balance and the digits sum to 195, counting per key forces each chain to have exactly one step at each of positions `d_i .. 6` and none elsewhere, so every link's end is its element walked to position 7; `local_sound` states it over a signature's tuples. `paths_complete` and `local_complete`: the steps the digits need, chain by chain (`cells`), balance. `count_circuit` counts `99 n` `STEP` and `42 n` `LINK` rows, so the rows the signatures name are all of them (`rows_perm`), and the whole bus balances exactly when each signature's tuples do (`local_of_balanced`, `balanced_of_local`).

The specification is `Spec/EthCryptographySpecs/Xmss`, vendored verbatim from `ethereum/cryptography-specs` at `d1331f02e308fe6d0aedda8601e4d5b0fc360318`; `scripts/check-xmss-spec.sh` checks it is that commit's `Xmss` modules. The field facts the digit sum check relies on (`Xmss.target_eq`, `Xmss.eq_195`: `X^195` names the target and no other digit sum up to 294 reaches it) are proved in `Xmss.FieldFacts`.

Trusted, in `Model.Sat`: that a satisfying assignment's wires held equal carry equal limbs (the bus; `Rec.copy_argument` proves balanced multiplicities give this, the log-derivative sums balancing only when the multiplicities do is not proved here); that every `HASH` row's columns are the ports of an assignment satisfying `Compress.artifact` (`HashRow`); and that public rows carry their constants and statement words (`FixedColumns::public_values` putting statement word `i` on public row `i`). Trusted, in `Model.Accepts`: that the dynamic bus balancing gives `Model.Balanced`, as above. Not covered: that a proof the Rust verifier accepts yields such an assignment (GKR, the table sumcheck, the PCS), and the Rust builder beyond the circuits `checkxmss` checks.

## leanSPHINCS

`LeanVMCircuits.Sphincs.Circuit.circuit n` verifies `n` leanSPHINCS signatures on the recursion machine; `rec::sphincs` makes the same builder calls in Rust, and `checkxmss` checks the circuits it builds are this one. Signature `j`'s statement is four `E` words: the root, the public parameter and the message's two halves, each holding 64-bit words (`Sphincs.Encodes`). Its chains run on the dynamic bus as leanXMSS's do, through the same `Xmss.Circuit.chains`: in layer `lay`, chain `i`'s `LINK` row pushes its element at the key of position `8i + d_i` and pulls its end at that of `8i + 7`, and the layer has 103 `STEP` rows (`7 · 42 - 191`), each hashing one step over the base tweak word `tweak0(1, lay, 0)` plus its position at bit 32. Keys carry the tag `(3j + lay) · 2^41`, which keeps every layer of every signature apart while `n ≤ 2^20` (the tag stays below `2^22`; the Rust builder refuses more).

`Sphincs.accepted_iff` is the end-to-end statement: for `n ≤ 2^20`, the machine accepts the circuit of `n` signatures under statement words `st` with some assignment (`Model.Accepts`: the assignment satisfies its rows, `Model.Sat`, and balances its dynamic bus, `Model.Balanced`) exactly when, for every `j < n`, statement words `4j` to `4j + 3` state a public key and a message (`Sphincs.Statement`: words whose little-endian bytes are the key and the message) under which some signature passes `LeanSphincs.verify`. It combines three layers that meet at `Sphincs.Words.verify`, verification restated over 64-bit words:

- `Sphincs.sound`: in every assignment the machine accepts the circuit with, each statement encodes a root, a parameter and a message for which some signature passes `Sphincs.Words.verify`.
- `Sphincs.complete`: every family of statements with signatures passing `Sphincs.Words.verify` extends to an assignment the machine accepts the circuit with.
- `Sphincs.Spec.verify_eq`: `Sphincs.Words.verify` is `LeanSphincs.verify` on the words' little-endian bytes, for signatures whose counters are below `2^32` (the specification serializes each in four bytes); `Sphincs.Spec.counters_lt` shows word verification accepts no other. Every hash but the encoding is `th_eq` over `Xmss.Spec`'s BLAKE2s bridge; the encoding hashes one short block (`hash_short`, `encDigest_eq`), and the message digest, the encoding, the chains, the trees and the hypertree follow (`messageDigest_eq`, `encode_eq`, `fold_eq`, `layerRoot_eq`, `recover_eq`). `signature_onto` (with counters below `2^32`), `publicKey_onto` and `message_onto` show every specification input is the bytes of some words.

The chains reuse `Xmss.Paths` over the tag `3j + lay` and 103 steps: `Sphincs.walk_stepHash` makes the walk of a step's hash `Sphincs.Words.chainFrom`, `Sphincs.layer_good` reads a layer's balanced tuples as its chains' ends, and `Sphincs.Complete.layer_cg` places the steps the digits need (`cells_digits191`). `Sphincs.count_circuit` counts `309 n` `STEP` and `126 n` `LINK` rows, so the rows the `3n` layers name are all of them (`rows_perm`), and the whole bus balances exactly when each layer's tuples do (`local_of_balanced`, `balanced_of_local`).

What it is proved against: leanSPHINCS has no reference specification outside this repository, so `Spec/LeanSphincs` transcribes the guest's verifier (`programs/leansphincs/guest/src`) definition by definition, over the bytes its words stand for, with the vendored BLAKE2s. `LeanSphincs.Kat` pins the transcription to the host's known answer (`leansphincs_is_the_specified_scheme`): it accepts the pinned signature of the pinned key and rejects it with one byte changed. These checks are `#guard`s run by Lean's evaluator, not the kernel, so the transcription's agreement with the guest rests on this known answer and on reading the transcription against the guest. `Sphincs.target_eq` and `Sphincs.eq_191` are the digit sum's field facts. The trusted premises in `Model.Sat` are leanXMSS's.
